# AI 协作开发 · 错误复盘与铁律

> **这份文档是干什么的**：一次真实项目（约 1.7 万行生产代码 + 1.9 万行测试，一个人 + 多个 AI 子代理，
> 一个下午到一天的量级）结束后，把 **AI 主控/实现者/复查者实际犯过的错**逐条写下来，
> 抽象成**可复用的规则**。
>
> **怎么用**：整份复制到新项目的 `docs/` 里，开工前读一遍；协作时把它当"裁判依据"引用
> （例如："这里违反 R3，请改成留档失败就放弃操作"）。
>
> **它不是道德说教**：每条规则后面都跟着**真实的失败案例**与**怎么发现它的** ——
> 因为"知道了但还是会犯"是这类错误的常态，**唯一有效的防线是把它变成可执行的检查动作**。

---

## 第 0 部分 · 十条最贵的铁律（其余都是它们的展开）

| # | 铁律 | 一句话由来 |
|---|---|---|
| **R1** | **"读不出来"永远不等于"空的/没有"** | 两次真实数据丢失都是它造成的 |
| **R2** | **说出去的话必须与事实一致**（统计、日志、界面文案） | 报告用"推测值"当事实值 → 每次分析都多报 |
| **R3** | **覆盖/删除之前，必须能证明旧内容被留住了**；留档失败就**放弃操作** | "留档失败 `pass` 掉、接着覆盖" = 静默不可逆丢数据 |
| **R4** | **断言的牙只有变异能证明**：写完问"我把实现改成什么，它仍会通过？" | 多条"看起来在测"的断言实测全绿 |
| **R5** | **假绿与假红是同一枚硬币**：跑它，看它**为什么**红/绿 | 一条断言读错层级 → 正确实现下也红 → 变异的"牙"是假的 |
| **R6** | **夹具必须真的造出被测的那个条件** | "争键"测试的夹具根本没争键，测的是"另一个原因造成的绿" |
| **R7** | **别拿代理指标当判据** | 要判"全名是否相等"，却用"键是否等于全名" → 误报档位 |
| **R8** | **复用项目已有的口径**（清洗/取整/归一化/判空函数），别另写一套 | 另写 `int(layer)` 而不用项目自己的 `_as_int` → 一条手改坏的记录让整步崩 |
| **R9** | **承诺"收尾"时，遇到"会丢数据/会说假话"必须让路**，并明说为什么食言 | 我说"这是最后一轮"，复查查出静默丢数据 → 正确的食言 |
| **R10** | **计划是假设，不是事实**：写"实测 / 契约 / 不可达"时要标证据强度 | 计划里的期望值/逻辑/夹具被实现者和复查推翻 15+ 次 |

**为什么是这十条**：这十条每一条都对应"**用户会丢掉数据、或被自己看到的东西骗了**"这一类不可逆损害。
其余的（风格、抽象、性能）都能事后补；这十条不能。

## 第 1 部分 · 写计划 / 写规格时

### 1.1 期望值不要凭记忆写（R10）
**案例**：计划里给了某个归一化函数对某串输入的期望输出，实现者一跑就红 —— 我记错了它的行为。
**做法**：
- 关键期望值**当场跑一遍**再写进计划（哪怕是 `python -c` 一行）；
- 写不了就**标明"未验证"**，让实现者自己定，并允许它推翻；
- **绝不在计划里写"实测"两个字，除非真的跑过**。

### 1.2 别给"带未来的签名"下断言
**案例**：我假设内部调用是 `builder(jd_text, cfg, **kw)`，于是让实现者"闭包直接塞 `reuse=`"。
实际调用点是**两个位置参数**；按我写的做，会让一批既有替身在自己的函数体之前 `TypeError`。
**做法**：
- 决定"怎么注入"之前，**先 `grep` 调用点**（`grep -n "builder(" .`），以真实签名为准；
- 计划里写"注入方式"时，同时写清**为什么不能更简单**（否则后人会"顺手简化"掉适配层）。

### 1.3 计划里的任务顺序要能自洽
**案例**：某个任务的测试依赖后一个任务才建的模块。
**做法**：写完计划后**通读一遍依赖顺序**；每个任务的"前置"必须已经存在。

### 1.4 计划里的名字必须先在仓库里查一遍
**案例**：计划里的测试类名与仓库里已有的冲突；某个函数名与既有函数重名。
**做法**：命名表先 `grep` 一遍；冲突就换名，并写进命名表。

### 1.5 变异要设计成"真的能打到那条断言"
**案例**：我设计的变异（把字符类放宽成 `.`）打不到"中文括号不建键"那条断言 ——
因为相邻的 ASCII 字符类仍然挡住了两字中文。**看起来做了变异取证，其实那条断言没被验证。**
**做法**：
- 变异**做完必须问**："它真的会经过那条断言的代码路径吗？"
- 更狠的做法：**写断言时就先想好"谁会把它打红"**；想不出来就说明这条断言可能是摆设。

### 1.6 别把"不可达"当结论——它通常是"我没想到那种形状"
**案例**：实现者枚举了 1521 个术语证明某去重分支不可达，建议删掉；
我构造出它漏掉的形状（"术语本身就是括号"），**实测分支可达**。若照它删了，就是基于错误的证明删掉承重代码。
**做法**：
- 说"不可达"必须给出**输入空间的论证**，不能只给"我枚举了 N 个"；
- 删分支之前，**先问"什么输入能让它到达"**，并真的试试。

### 1.7 计划里不要写"做完第 N 条，这句话就成真了"
**案例**：我在计划里断言"做完留档那条，'盘上字节也会留'就成真了"。复查实测证伪：
有一种场景（快照好 + 盘上不符）盘上字节会在**全树范围内**消失。
**做法**：只在**跑过之后**写"成真了"；否则写"预期"。

## 第 2 部分 · 写代码时

### 2.1 "读失败 → 用空值继续"是数据丢失的头号来源（R1）
**案例**：非 UTF-8 的知识库文件被 `read_text(path, "")` 吞掉解码错误 → 看起来是"空库" →
后续写回把它覆盖掉，**145 张卡变 0 张**（另有简历快照被 0 字节覆盖、状态文件被清空）。
**做法**：
- 凡是"读出来为空"的地方，都要能区分**三种**：文件不存在 / 文件存在但读不出来 / 文件存在且真的是空的；
- 中间那种**必须让流程停下来**并如实报告；
- 判据要看**原始字节**（`len(raw) > 0`），不要看"解码后的字符串是否为空"。

### 2.2 覆盖/改名/删除之前先留档；留档失败就放弃整个操作（R3）
**案例**：把旧快照改名到旁挂（`.stale-<sha8>`）失败时被 `except OSError: pass` 吞掉，
紧接着就写新内容 → 旧字节**永久消失**（复查构造证明："整棵树里再也搜不到"）。
**做法**：
```python
if not archive_old(old):        # 留档失败
    raise Abort("没能留档，本次不修")   # ← 而不是 pass
```
- 留档用"**直接写一份副本**"比 rename 更简单、更可测；
- 同名撞车要**判内容**（同名且内容相同才算留过），并且**换名**而不是跳过。

### 2.3 复用项目已有的口径函数（R8）
**案例**：写 `int(card["layer"])`，而项目自己有 `_as_int`（就是为"用户手改坏的数据"写的）。
结果：一条 `layer: "abc"` 的记录让**整步崩**（而项目里别处早就把它当"不许抛"的形状）。
**做法**：动手前先 `grep` 有没有同类函数（`_as_int` / `clean_*` / `normalize_*` / `_as_list`）；
有就用它，**并在注释里写明"为什么这里也用它"**（防止后人改回裸 `int()`）。

### 2.4 推测值永远不要当事实值写出去（R2）
**案例**：报告里"本次联网 N 条"写成 `总数 − 复用数`（**推测**），而真实搜索次数还受
"单次分析搜索上限"约束。真实数据里每次分析 51/53/55 个节点、上限 40 ⇒ **每次都多报**；
更糟：**排在上限之外、根本没搜**的那张卡，报告仍写"已联网补全"。
**做法**：
- 只有**真实发生的事**才能写进用户可见的地方；
- 拿不到真实值时，**回填**真值（让做这件事的那一层把计数报出来），而不是在旁边算一个近似；
- 特别区分"**没跑**"与"**跑了但结果是 0**"（本项目有专门的字段区分，界面文案也必须分开）。

### 2.5 日志/异常里的用户内容要收口
**案例**：异常日志原样落盘，而 HTTP 报错的异常文本里常带整段 prompt/回复。
**做法**：`str(exc)` 与 traceback 截断；把"截断后仍可能含用户内容"**如实写进文档**，
不要声称"不会泄漏"（做不到就别说）。

### 2.6 别让"适配层"变成静默失效
**案例**：为了让老替身可用，注入时先查被调用函数的签名（`_accepts_reuse`）。
它是对的，但**必须同时钉住两个方向**：真的实现**确实收到**参数（否则功能静默失效）；
老替身**不被塞**参数（否则 TypeError）。
**做法**：任何"探测式适配"都要有**双向断言** + 注释写明"为什么不能简化掉"。

### 2.7 两条闸门语义重叠时，别急着合并
**案例**：同一个约束在两层各实现一次（判定层"不许认领已占用的卡" + 填充层"一张卡只落一个节点"）。
拆掉任一处，端到端测试**仍是绿的** —— 看上去像冗余。
**做法**：这是**有意的纵深防御**。要求：**每层各有独立测试**，并在代码里写明"别删任何一处"。

## 第 3 部分 · 写测试时

### 3.1 写完断言就问："谁会把它打红？"（R4）
**做法**（**最有效的单一动作**）：改一处实现 → 跑**全量** → 确认红点**就是你预期那一条** →
用编辑器改回。**红了别的条、或者一条都不红，都必须追下去。**

### 3.2 假红的识别（R5）
**案例**：一条日志断言写成 `ev[-1].get("searched")`，而日志把附加字段放在 `rec["data"]` 里 →
**正确实现下也红**（`None != 1`）。后果：它对应的"变异"根本红不到这条断言上，**牙是假的**。
**做法**：
- 测试**第一次跑就红**时，先读**红的原因**：是"行为不对"还是"取值路径/夹具/环境不对"；
- 后者是**测试写错**，改测试的取值方式（**不是**削弱断言）；
- **绝不允许**为了让测试变绿而放宽断言 —— 那是把一道检查作废。

### 3.3 夹具必须真的造出被测条件（R6）
**案例**：想测"同一把键被两张卡争用时先到先得"，夹具用了**两个相同 term** 的卡 →
第二张在"同 id 只进一次"那一步就被丢掉，**根本没走到争键那条路径**。那条测试是"因为别的原因"绿的。
**做法**：写完夹具先问"我要测的那个条件，**真的发生了吗**？"（可以打印中间状态确认）；
一个 fixture 最好只制造**一个**被测条件。

**案例（同一个坑的另一种长相，"非 UTF-8 夹具"）**：主线程要验"配置文件读不出来时必须拒绝写入"，
就把 JSON 用 `.encode("gbk")` 写盘 —— 但那份 JSON **全是 ASCII**（没有中文），
于是 GBK 与 UTF-8 的字节**完全相同**、文件其实**是合法 UTF-8** ⇒ 守卫当然放行。
主线程据此报了一次**假警报**（"实现没生效"）。
**做法**：凡是要造"非 UTF-8/被改坏"的夹具，**先断言它真的非 UTF-8**：
```python
try:
    raw.decode("utf-8");  raise AssertionError("夹具又错了：这份内容其实仍是合法 UTF-8")
except UnicodeDecodeError:
    pass          # 这才是真的坏了
```
同类还有：**猜系统函数的路径/名字**（用了 `current_profile_path()`，真名是 `current_profile_file()` →
写到错的路径 → 又报一次假警报）。⇒ **探针里凡是用到"我以为叫这个名字"的 API，先 `dir()`/`inspect` 确认。**

**案例（第 4 次，同一个根因的第三种长相：猜参数顺序）**：主线程要验某入口在坏库下会不会覆盖，
调的是 `f(term, None, {"state": …})` —— 而真实签名是 `f(term, state, meta=None)`。
于是 `state=None` 命中入参守卫、**函数提前返回、根本没走到库那一步**，主线程据此又报了一次**假警报**
（"它没按文档说的留档后写"），而实现与文档其实一致。
**做法（把"先读签名"变成动作，而不是提醒自己小心）**：
```python
import inspect
sig = inspect.signature(f)            # 先打印出来，再决定怎么调
assert list(sig.parameters) == ["term", "state", "meta"], sig
```
**一条规律**：主线程在**验证**阶段的错误，几乎全是"我以为我知道这个接口" ——
而实现者在**实现**阶段反而更少犯，因为它必须读代码。⇒ **验证前先读代码，别凭记忆下判断。**

**案例（第 5、6 次：环境假设）**：同一天还连着栽了两次**环境**：
- `subprocess.run(..., text=True)` 用**父进程的 locale 代码页（GBK）**去解子进程的 **UTF-8** 输出
  → 解码抛错、`p.stderr` 变 `None` → 后续 `in` 判断崩成 `TypeError`。
  **做法**：跨进程一律 **按字节收**（`capture_output=True`、不加 `text=True`），
  再**显式** `p.stdout.decode("utf-8", "replace")`。
- 把探针脚本写到 `%TEMP%` 再按路径运行 → Python 把**脚本所在目录**加进 `sys.path`（不是 cwd）
  → `ModuleNotFoundError: No module named 'store'`，而我看到的却是"退出码 1 + Traceback"，
  一度误判成"实现没生效"。
  **做法**：跨进程探针要么显式 `sys.path.insert(0, <repo>)`，要么给子进程设 `PYTHONPATH`；
  并且**先看 stderr 原文**再下结论（这两次都是"错误信息里写着真正的原因"，我差点没看）。

**结论**：验证脚本本身就是代码，**它自己的失败会伪装成"被测对象失败"**。
⇒ 探针跑出"不符合预期"时，**第一件事是确认探针真的打到了那条路径**（打印路径/参数/中间状态），
第二件事才是怀疑被测对象。

**案例（第 10 类错误：把"转述别人的结论"当成"已验证的事实"）**：
主线程把审计报告里的两条**读码结论**（"`_restore_profile` 少一道根保护"、"试跑表 `after` 恒等于 `before`"）
当成事实写进需求下发；实现者在隔离根里一跑，**两条都不成立**——
前者写成 `if dirpath != root and not dirnames and not filenames`，**与另一处的 `continue` 语义等价**（审计只比了字面）；
后者的"after=before"是**尺子巧合**（真实数据两边 distinct id 恰好都是 2 个），真正的毛病是另外两条。
**做法**：**转述 = 断言**。下发前把每条结论标成
「**已实跑** / **只读码** / **未验证**」三档之一；只读码的那一档，要在任务书里**明写"这是读码推出的，请你先核实前提再动手"**。
（本项目里"只读码"的结论被实测推翻，已经不是第一次了。）

### 3.4 不要用代理指标（R7）
**案例**：判断"是否同名命中"时用"命中的键是否等于卡片全名" —— 于是
"节点叫 `WER`、库里叫 `词错率（WER）`"被错报成"同名命中"。
**做法**：判据必须**直接**对应你要断言的那件事（"两边全名归一化后是否相等"）。

### 3.5 分类断言要成对（正向 + 反向）
**案例**：一批"丢弃侧"测试**全都在喂"整条回复只有坏东西"** → 一个"见到坏元素就整条丢"的实现
会让它们**全绿**，而那个实现在生产上几乎全废（5 对里 1 对胡诌 → 5 对全丢）。
**做法**：每个"该被丢掉"的测试里**混一条合法的**，断言它**活下来**；
反过来，"该通过的"测试里混一条坏的，断言只有坏的被丢。

### 3.6 名字/注释/docstring 与断言必须一致
**案例**：抓到过好几处——用例名说"钉住 A"，实测 A/B 都不敏感；docstring 说"都在旧实现上实测为红"，
其中一条其实在旧实现上也绿。
**做法**：改名比改注释重要；**"实测为红"这种话要么真的跑过，要么不写**。

### 3.7 别用"跑单个"代替"跑全量"
**案例**：一条断言散落在别的测试文件里 → 只跑本文件会误判"没牙"。
**做法**：变异/改动的判据永远是**全量 + 看清红在哪一行**。

### 3.8 偶发红必须查清或明确标注
**案例**：一条并发测试偶发 `WinError 5`（拒绝访问），14 次全量里 0 次、单跑必绿 → 从未查清根因，
一直污染变异判定（有一次变异"红了"，其实是它）。
**做法**：偶发红要么**修根因**，要么在纪律里写清"**它红了不代表你打中了什么**"，并在报告里标注。

## 第 4 部分 · 验证与取证的纪律

### 4.1 任何会写真实数据的探针，**第一步**必须隔离（R11）
**案例（本次最严重的事故）**：主控为了复现一个缺陷，写了段临时探针，第一行就是
`store.save_knowledge({"nodes": []})` —— **直接打在真实数据目录上**，
把用户 **145 张卡的知识库清成 0 张**（509687 字节 → 19 字节）。
之所以能恢复，是**子代理之前复制仓库做复查时把数据目录一起带走了**，临时目录里留着两份逐字节相同的副本。
**做法（三条，缺一不可）**：
1. 探针**第一件事**：把数据根指到 `tempfile.mkdtemp()`（并且**同时**改日志文件路径），
   然后 `assert` 确认它真的在临时目录里 —— **不通过就直接死**；
2. 探针**前后各打一次基线**（见 4.2）—— 只在后面打，就分不清"数据本来就长这样"还是"探针把它改成这样"；
3. 项目里所有测试都走"隔离基类"，**只有人的临时探针不隔离** —— 所以"测试全绿"**不能**证明"没写真实数据"。

### 4.2 基线要"打全"并且前后各一次（R15）
**做法**：把"用户真实数据的关键指纹"固定成一组（文件大小 + 内容哈希 + 关键字段计数 + 文件总数），
**每次核验前后各打一次**；值不同就是有东西被改了，先查清再继续。
> 本次用的就是这一组：主数据文件（大小/哈希/条数）、日志前缀哈希、关键文件哈希、目录文件数。

### 4.3 数据被误改后的**恢复预案要比事故先写**
**案例**：本次能恢复，纯属侥幸（临时副本）。
**做法**：
- 让"复制整个数据目录"成为**复查/实验的默认动作**（那些副本就是最后一道保险，**别随手删**）；
- 事故留档约定：把被损坏的那份**改名留档**（`xxx.DAMAGED-BY-<原因>-<时间戳>`），**不覆盖、不删除**；
- 恢复之后**立刻跑全量测试 + 再打一遍基线**，证明恢复没弄坏别的东西。

### 4.4 核验要看**内容**，不只看**文件清单**（R17）
**案例**：实现者汇报"9 条都落地"，我只核对了"提交里只有它说的那些文件"，
**没有逐条核对那 9 条各自做了没有** → 实际上有 2 条完全没做、1 条只做一半。
**做法**：给实现者的汇报模板里**强制**要求"逐条 → 改在哪个文件哪一行"，
并且**写"做了"之前先 `git diff` 确认那几行真的变了**；主控抽验时**抽查内容**（随机挑 2-3 条去看那几行）。

### 4.5 汇报"实测/契约/不可达"这类断言时要标证据强度（R10）
**案例**：我给文档者的"诚实缺口清单"里 **3 条是错的/过期的** —— 因为我抄的是**更早的笔记**，
而那两条缺陷在那之后已经被修掉了。**文档者没有照抄，而是逐条去核实，才发现。**
**做法**：转述任何"已知问题"时，**带上"我在什么版本上看到的"**；
并要求下游**逐条核实后再写**（"我核实后不成立"是合格的结论）。

### 4.6 别信"预验"（R22）
**案例**：我说"我已经替你预验过这份代码"（我确实跑了那段函数、核对了值），
但**没有验证变异的牙** —— 结果那段计划里的断言有多处是假红/没牙。
**做法**：预验只能声称"**值对**"，**不能**暗示"测试/变异已验证"。

## 第 5 部分 · 协作（多代理 / 主控与实现者）

### 5.1 并行的边界是**文件**，不是"任务"（R12）
**案例**：两个实现者并行时，"全量测试绿"这个证据变成**有歧义**的（每个人跑到的都是对方的中间状态）。
**做法**：
- 并行前先看**文件集合有没有交集**；有交集就**串行**；
- 无交集时**允许**并行，但要求：只碰自己清单里的文件、**绝不 `git add -A`**、
  汇报里要如实标注"哪些红是别人的中间状态"。

### 5.2 `git commit` 提交的是**整个索引**（R13）
**案例**：A 暂存了文件，B 这时裸 `git commit` → **B 的提交把 A 的改动卷了进去**（同类事故真发生过一次 `--amend`）。
**做法**：多个写入者时，一律 `git commit -F <消息文件> -- <自己的路径>`；
（注意：带路径提交取的是**工作树内容**，所以**同一个文件也不能两人同时改**。）

### 5.3 不要 amend 共享历史（R14）
**案例**：一个实现者 `--amend` 时，把主控刚提的提交折进了它自己的提交（因为共享同一个工作树/HEAD）。
**做法**：子代理**永远不许** `--amend`、`push`、`checkout/restore/stash`；
主控也**不要**在子代理正在写文件时提交。

### 5.4 待办状态是承诺（R18）
**案例一**：我在待办里把某任务标成"进行中"，但**根本没派出去** → 用户等了很久来问"是不是卡住了"。
**做法**：写完状态**立刻**执行对应动作；"要么有东西在跑，要么我在汇报"。

**案例二（同一天，第二次犯，形态更隐蔽）**：批 1 的计划里写着 **1.10（测试基础设施三项）**，
我**从头到尾没派活**，却在验收报告里写了"**十项落地 10/10**"。
是独立复查把仓库复制到别处跑全量——**11 条与代码无关的红**——才把这条揪出来的。
根因不是"忘了"，而是**我在一个 10 项的清单里逐项派活，却没有一个"逐项打勾"的动作**：
波次推进得越顺，越容易把某一项**静默漏掉**。
**做法（比"立刻执行"更硬）**：
1. **收工时逐项对照清单打勾**：清单里每一项后面必须能填上**"派过活的证据"**（子代理 id 或提交号）。
   **填不出来的那项，不许写"已完成"** —— 只能写"未做"，或者当场补派。
2. **写任何"全部完成/10 项落地/全绿"之前，先问自己：这句话我拿得出证据吗？**
   （这条同时命中 R2"说出去的话必须与事实一致"与 R7"别用代理指标"——
   "我按计划派了 10 项"是**我的意图**，不是**事实**。）
3. **"全量 OK"必须说清适用范围**：只在"本机 + 这个路径 + 这个环境"下绿，就要这么写。
   反例见本轮：全量在这台机器上 `1214 OK`，把仓库复制到别处就是 **11 条红**（测试依赖仓库外的同级目录）。

### 5.5 实现者说"我做了但和你说的不同"，先看它的理由
**案例**：多次出现 —— 我要求用 `copy.deepcopy`，它用了项目自己的清洗函数（同样保证"新对象"，
而且不丢形状收口）；我要求"直接塞参数"，它加了签名探测（否则既有测试全红）。
**它的判断几乎都对。**
**做法**：把"与指示不同"当成**信号**而不是**不服从**；要求它**写明理由**，然后**你复核理由**。

### 5.6 复查颗粒度是**取舍**，说清楚再放宽
**做法**：把"哪些轮次单独复查、哪些折进下一轮"明说（并说明风险：修轮可能藏问题到下一轮才暴露），
**给用户否决的机会**。

### 5.7 修轮必须**再验证**（尤其修数据/修文案时）
**案例**：第一轮修完"两条静默丢数据"，修的过程中**又引入**一条（留档失败 `pass`）——
如果没人复查修轮，它就会带着"已修复"的标签上线。
**做法**：**修轮 = 新改动**，按新改动对待：TDD + 变异 + （碰到数据/诚实性路径时）独立复查。

## 第 6 部分 · 工具与环境（踩过的具体坑）

| 坑 | 现象 | 正解 |
|---|---|---|
| PowerShell 5.1 无 `&&` / `\|\|` | **整条命令解析失败、什么都不执行**（很容易被当成"跑了但没输出"） | 用 `;` 分行；或分多次调用 |
| `python -c "…"` 里的转义引号 | pwsh 解析器把引号吃掉 → **整条命令一个字符都不执行** | **多行脚本一律 here-string + `python -`** |
| `2>&1 \| Select-Object` | **退出码变成假失败**（全绿却 EXIT=1） | 判据只看 `$LASTEXITCODE`；别把 stderr 混进管道 |
| `WriteAllText($f, $array)` | 字符串**数组**被按 `$OFS`（空格）拼成**一行** → 多行提交消息被压扁 | 用 python 落盘（保留换行、无 BOM）；或先 `-join "\`n"` |
| `Out-File -Encoding utf8` | PS 5.1 会写 **BOM** | 用 python 写 `wb` |
| 中文文件名 | git 输出**带引号的八进制转义**，用 `-like '*.md'` 过滤会**漏判** | 过滤前先 `git -c core.quotepath=false diff --name-only` |
| 长命令超过前台时限 | 命令被移到后台作业，看起来"卡住" | 核验命令拆小；或接受后台并 `job_output` 取回 |
| 一次性迁移脚本 | 跑完就该退场，但还留在仓库里、还有引用 | 明确标注"一次性、不要再跑"，或归档到 `scripts/` |
| 临时副本 | 子代理留下 1.7 GB 副本 | 用完即删；但"用于恢复的整目录副本"要**保留**到确认安全 |

## 第 7 部分 · 文档与代码的漂移

### 7.1 文档里的**行号 / 数量 / API 名**一定会过期
**案例**：文档说"抛异常的唯一地方在 app.py:1040"，一天之内就漂了 14 行；
文档里写"当前 872 条测试"，很快就变成 1085 条；规格里写过一个"最终 API"，
实现时换成了另一套（文档没跟着改）。
**做法**：
- 引用时**优先引用语义锚点**（函数名/类名/字段名），行号只作辅助；
- 数量类信息写"**截至某次实测**"，并写清测法；
- 在**长期文档**顶部加一句"这是**当时的**记录，以代码为准"，并列出已知漂移点。

### 7.2 提交消息也是"说出去的话"
**案例**：一条提交消息写着"订正了某节的口径"，但那个提交的 diff **只加了另一节**（我以为改了、实际没改）。
**做法**：提交消息写完**对着 `git diff` 核一遍**；消息里别写 diff 里没有的东西。

## 第 8 部分 · 可直接当 checklist 用的最短清单

**改动之前**
- [ ] 我要动的数据在哪儿？碰不碰**真实数据**？（碰 → 先隔离 + 前后基线）
- [ ] 这些代码里**已有的口径函数**是什么？（`_as_int` / `clean_*` / `normalize_*` / `_as_list`）
- [ ] 我要改的判据/签名，**真实调用点**长什么样？（`grep` 过没）

**写代码时**
- [ ] "读失败"会不会被当成"空"？三种情况分开了吗？
- [ ] 覆盖/删除前留档了吗？**留档失败会放弃操作吗**？
- [ ] 我写出去的数字/文案，是**真实发生的事**还是**推测**？
- [ ] "没跑"与"跑了得 0"分得开吗？

**写完测试后**
- [ ] 每条新断言：**改哪一行会让它红**？真的跑过吗？
- [ ] 第一次红，是"行为不对"还是"测试写错/夹具没造出条件"？
- [ ] 我的夹具**真的制造了**被测条件吗？
- [ ] 我用的判据是**直接指标**还是代理指标？

**汇报前**
- [ ] 我声称"做了"的每一条，`git diff` 里**真的**有那几行吗？
- [ ] 我声称"实测"的，**跑过**吗？没跑就标"未验证"。
- [ ] 我的核验是"对了文件清单"还是"逐条对了内容"？

**与别人（或别的 agent）协作时**
- [ ] 我俩改的**文件**有交集吗？（有 → 串行）
- [ ] 提交用**带路径**的吗？（多写入者时）
- [ ] 我汇报里的红点，有没有**别人的中间状态**混进来？

## 第 9 部分 · 这次做得对的地方（别只记错的）

复盘里也要留下**有效**的做法 —— 它们同样可复用：

1. **每个任务：先写测试 → 再实现 → 再变异取证 → 独立复查（规格 + 质量）→ 修轮再查。**
   本次共推翻主控的计划/说法 **15+ 次**，**没有一次流到用户手上**。
2. **"红在哪一行"比"红了"重要得多**（它区分了"行为变了"和"测试写错了"）。
3. **要求实现者如实申报**："这条测试在旧实现上也绿"、"这条变异没红"、"我没隔离" ——
   **主动申报的缺陷比被查出来的便宜十倍**。
4. **让下游反过来核实上游的结论**：文档者查出我给的 3 条缺口是错的；
   复查者查出"某条统计在真实数据上每次都会多报"。
5. **"没找到问题"是合格结论**：本次多处写"这一类没找到"、"这条变异确实不红"，比编条目有价值。
6. **把纪律写进仓库**（不是留在聊天里）：下次会话/别人接手时，它还在。

## 附 · 一句话版本

> **凡是要写到用户能看见的地方（数据、日志、界面、提交消息），先问一句：这是真的吗？**
> **凡是要覆盖用户已有的东西，先问一句：旧的还在吗？留档失败我停手了吗？**
> **凡是说自己测过了，先问一句：我改坏它，它真的会红吗？**
