# 批 7.1 设计：把「指向岗位的引用点清单」收成一处

> 目标（体检报告 §8.1）：清单现在散在 **4 个模块**里各列一遍，**实测已经漏了两处**
> （`report_state/<报告id>.json`、`interviews/*/feedback.json`）⇒ 删完 JD 后它们变成盘上孤儿、预演里也不列。
> **下次再加一个"指向岗位"的产物还会漏，而漏的那一刻没有任何机制报警。**
> 所以这一项的价值**不在重构本身，而在"以后再也不会漏"**。

## 1. 现在有哪些引用点（全量清点）

| # | 引用点 | 谁写 | 现在谁在维护清单 |
|---|---|---|---|
| 1 | `jds.json` 的 `jds[].id`（**本体**） | `jdid` | 4 处各列一遍 |
| 2 | `jobs.json` 的 `jd_id` | `app` / `jdid` | 同上 |
| 3 | `knowledge.json` 的 `nodes[].from_jds[].id` | `kb` | 同上 |
| 4 | `interviews/*/status.json` 的 `job_id` | `interview` | 同上 |
| 5 | `report_state/<报告id>.json` 里的 JD 维度 | `app`（报告勾选） | ❌ **漏了** |
| 6 | `interviews/*/feedback.json` 的 jd 键 | `interview` | ❌ **漏了** |
| 7 | `jobs.json` 里的 `merged_into`（悬空引用） | `jobdup` | 特殊：见批 7.2 |
| 8 | `reports/*.html` 内嵌的 JD 数据、`jd/<id>.txt` 原文 | `app` | **策略上不重写**（报告/原文按 id 命名；改名由 `身份迁移` 重建）⇒ 需在**白名单**里写明理由 |

`重构清单的"4 处"= `jdid.rename_jd` / `jddelete._plan`+`_purge_locked` / `jobdup.merge_jobs` / `身份迁移.py`。

## 2. 目标接口：`jdrefs.py`（新文件，零依赖，只 import store/log）

```python
Ref = namedtuple("Ref", "kind path count how")     # 只读探测的结果

KINDS = {                                            # 单一真源：新增产物只在这里加一行
  "jds":        Kind(detect=..., rewrite=...),       # #1 本体（改名时改 id 本身）
  "jobs":       Kind(...),                           # #2
  "kb":         Kind(...),                           # #3
  "iv_status":  Kind(...),                           # #4
  "report_state": Kind(...),                         # #5（今天漏的）
  "iv_feedback": Kind(...),                          # #6（今天漏的）
  "merged_into": Kind(..., note="悬空引用：批 7.2 处理"),
}

def refs_of_jd(jd_id, key=None) -> list[Ref]         # 全仓扫描"这份 JD 被谁引用"（纯读）
def rewrite_jd_refs(old_id, new_id, refs=None, key=None) -> list[(kind, ok, err)]
def unregisterd_writers() -> list[str]               # 守卫用（见 §4）
```

**硬约束**：
- `refs_of_jd` **只读**（一律走 `store.read_*_strict`；**读不出来 ≠ 没有** ⇒ 返回带 `err` 的 Ref 或抛，
  **绝不允许**把"读不出来"当成"这份 JD 没被引用" —— 那正是今天两次事故的形态）；
- `rewrite_jd_refs` 每一项写盘前必须过既有的 `*_safe_to_write` 口径（坏文件就**整次拒绝**而不是跳过 ✓）；
- 锁：`refs_of_jd`/`rewrite_jd_refs` 自己**不取**外层业务锁（`_JD_LOCK`/`_MERGE_LOCK`/`_KB_LOCK` 由调用方持有 ✓），
  只在写 knowledge 时用 `kb._with_kb_write`（内部持 `_KB_LOCK` ✓）⇒ **锁序不变** ✓。

## 3. 四个调用方怎么改（每步独立提交）

| 步 | 调用方 | 现状 | 改成 | 风险 |
|---|---|---|---|---|
| 1 | —— | —— | **只加 `jdrefs.py` + 守卫测试**，不动任何调用方 | 极低（新增文件 + 新测试；全量应零变化）|
| 2 | `jddelete.preview_purge` | 自己列清单 | 直接用 `refs_of_jd` 的结果 ⇒ **今天漏的那两处会当场出现在预演里** | 低（只读路径），**可见收益最大** |
| 3 | `jdid.rename_jd` | 自己 repoint 三处 | 调 `refs_of_jd` + `rewrite_jd_refs` | 中（持 `_JD_LOCK`，内部会取 `_KB_LOCK` ⇒ **必须复跑锁序 AST 断言 + 可重入**）|
| 4 | `jobdup.merge_jobs` | 自己的 `_repoint_kb` + status | 同 `rewrite_jd_refs`（drop→keep 语义） | 中（有 `_MERGE_LOCK` + 快照/回滚 ⇒ **必须复跑回滚用例**）|
| 5 | `身份迁移.py` | 自己扫 `from_jds`/`migration` | 与 `KINDS` 对齐（或直接调同一份扫描） | 低（一次性脚本）|

⚠️ `jddelete` 的**删除**路径（`_purge_locked`）在第 2 步之后单独做，并且必须满足：
**预演列出的条数 == 实际清理的条数**（防"预演说一套、真删做另一套"）。

## 4. 守卫测试（**这一条比代码本身值钱**）

- 扫 `app.py` / `kb.py` / `interview.py` / `jdid.py` / `jddelete.py` / `jobdup.py` 里所有
  "构造 profile 内路径"的调用（`store.p_path(...)`、`store.profile_dir()`、`log.LOG_FILE` 除外）；
- 凡是**内容里会带 jd id** 的产物，必须在 `jdrefs.KINDS` 里登记；与身份无关的（`reports/*.html` 内嵌数据、
  `jd/<id>.txt`、`logs/`）走**显式白名单 + 一句理由**；
- **新增产物忘了登记 ⇒ 红**，报错里直接给"要么登记、要么加白名单并写理由"的指引。
- ⚠️ 这条测试自己要有牙：**先做一次变异**（从 `KINDS` 里摘掉 `report_state`）⇒ 它必须红。

## 5. 验收清单

1. 在"造齐 6 种引用"的隔离夹具上：`refs_of_jd` 返回 **6 条**（含今天漏的两条）✓；
2. 改名后：`refs_of_jd(旧)` 为空、`refs_of_jd(新)` 覆盖全部、**悬空 0 条** ✓；
3. 删除后：预演条数 == 实际清理条数 ✓；
4. **真实数据副本**上跑一次：改名前后 `refs_of_jd` 的条数与实际逐项一致 ✓（只读复制，绝不碰真实 `data/`）；
5. 守卫测试的变异红 ✓；锁序 AST 断言（`test_jdid.LockingTest` + `test_jdfacts.ModuleHygieneTest`）全绿 ✓。

## 6. 不做什么（划清边界）

- **不**改报告/原文的命名策略（`reports/*.html`、`jd/<id>.txt` 仍按 id 命名，白名单里写明理由）；
- **不**引入数据库/索引文件（保持"JSON + 磁盘即真相"）；
- **不**顺手修 `merged_into` 悬空（那是批 7.2，独立一步 + 独立测试）。
