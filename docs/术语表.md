# 术语表（大白话版）

> **这份表是干什么的**：本项目文档里出现的"专业词"，这里都用日常话解释一遍。
> 读文档碰到不认识的词，回来查这里。
>
> **约定**：别的文档里，每个技术段落都先写一段 **「大白话」**（讲清楚它在干什么、
> 不这么做会出什么事），再写 **「技术口径」**（精确的、工程师用来核对的描述）。
> 你只需要读「大白话」；「技术口径」是给以后维护代码的人（或 AI）核对用的。

## 一、这个东西是什么、东西都放在哪

| 词 | 大白话解释 |
|---|---|
| **报告** | 跑完一次分析产出的那份 HTML 文件。一份报告 = 一个岗位 + 一份简历。 |
| **岗位台账** | 程序里那个"我投过/看过哪些岗位"的列表页面。 |
| **知识学习地图**（简称**知识地图**） | 报告里那一大块"这个岗位会考哪些概念"的内容：每个概念有专业定义、通俗解释、真实来源链接、"前世今生"时间线。 |
| **知识点** | 知识地图里的**一条**，比如「语音识别」这一条。程序内部管它叫**节点**（node）。 |
| **知识库** | **跨岗位累积**的概念本子。同一个概念不管你分析过几个岗位，都只占**一张卡**。程序内部管一张就叫**卡片**（card）。 |
| **`knowledge.json`** | 知识库存在磁盘上的那个文件。**你积累的东西都在这里面。** |
| **`jobs.json`** | 岗位台账存在磁盘上的文件（每次分析的记录）。 |
| **`jds.json`** | "岗位身份库"。它比台账多存了**每个岗位的稳定 ID**，以及**这个岗位已经算过的知识地图缓存**（所以它能长到几百 KB）。 |
| **`data/profiles/default/`** | 你所有数据所在的那个目录。`default` 是"默认用户"；程序支持多个用户目录，现在只用这一个。 |
| **快照** | 某一刻**原样复制**下来的内容。报告里嵌的就是它诞生那一刻的知识地图快照 —— 所以以后知识库更新了，**老报告不会跟着变**。 |
| **缓存** | 算过一次就存起来，下次直接用，不重算。（省时间、省 API 额度。） |
| **播种**（seed） | 从**这个岗位自己的旧报告**里把知识地图捡回来用 —— 不花钱的"回收利用"。 |
| **API 额度** | 你花钱买的模型调用次数/搜索次数。省额度 = 省钱。 |
| **搜索额度** | 联网搜索（Tavily / 博查）的配额。知识地图是**吃配额最大的那一块**。 |

## 二、知识库与复用（这次新功能涉及的词）

| 词 | 大白话解释 |
|---|---|
| **`term`**（术语） | 一条概念的**名字**，比如「词错率（WER）」。 |
| **`from_jds`** | 卡片里的一个清单，记着"**这个概念是从哪些岗位来的**"。它只是一份**记账**，不拥有内容 —— 所以把它清掉不会让卡片消失。 |
| **引用**（指的就是 `from_jds`） | 同上一行。文档里说"清引用"= 只把这份记账里指向某个岗位的那几行划掉。 |
| **`sources`**（来源链接） | 那条概念底下的真实网页链接（维基百科等）。**有没有来源链接，是"这条知识可不可信"的标志。** |
| **`state`**（掌握度） | 你自己标的"待学习 / 学习中 / 已掌握"。程序**永远不会**自动改它。 |
| **复习优先级** | 自测复习时"先考哪个"的排序。一个概念**在越多岗位里出现过**，就被排得越前。 |
| **`normalize_id`**（身份键） | 判断"两个名字是不是同一个概念"的办法：把大小写、空格、标点、括号都去掉后**完全一样**才算同一个。所以「ASR」和「语音识别」在程序眼里是**两个**概念。 |
| **命中** | 报告需要某个知识点，而这个知识点**在你知识库里已经有卡了**。 |
| **确定性匹配** | 只看名字（含别名、括号里的英文缩写）就能确定是同一个概念 —— **不会认错**，但也认不出"同物不同名"。 |
| **模型判定** | 名字对不上时，让 AI 判一次"这俩是不是同一个概念"。能认出「词错误率与字错误率」=「词错误率」，但**偶尔会认错**。 |
| **够格复用**（`reusable`） | 那张卡**定义、通俗解释、至少 1 条真实来源链接**三样齐全，可以直接拿来用，不用联网重查。 |
| **`kb_reuse`** | 报告里每条知识点上挂的一个小标签，记着"这条是从知识库复用的、来自哪个岗位、什么时候"。**报告里那行出处说明就是它。** |
| **`kb.absorb`**（写回） | 把这次分析得到的知识点**合并进知识库**的动作。它只做"变长/补全"，**从不覆盖你的掌握度和复习记录**。 |
| **更长者胜** | 合并卡片时的规则：新内容**比旧的更长**才替换，否则保留旧的。所以写回**不可能让卡片变短**。 |
| **写回** | 把新查到的内容存进知识库。 |
| **时间线**（前世今生） | 报告里那条"这个概念从哪一年怎么发展过来的"列表。它是**模型写的**（基于已有的来源链接），**不需要联网搜索**。 |
| **`term_original`** | JD 里原本的写法。比如库里叫「语音识别」而 JD 写的是「ASR」，报告里就会括注「JD 里写作 ASR」。 |

## 三、删除与安全（"删东西"这件事为什么这么啰嗦）

| 词 | 大白话解释 |
|---|---|
| **预演**（preview） | 真要删之前，先**只看不动**地列一份"我打算删掉什么"的清单给你过目。 |
| **指纹**（fingerprint） | 那份清单的"防伪码"。你确认之后到真正执行之间，只要数据变了一点，防伪码就对不上 → 程序**拒绝执行**，让你重新看一遍。 |
| **回滚**（rollback） | 删到一半失败时，把已经动过的文件**从备份恢复回去**，当作什么都没发生。 |
| **逐字节**（byte-for-byte） | 恢复出来的文件与原来**一模一样到每一个字节**（不是"看起来一样"）。 |
| **字节** | 文件在磁盘上的最小编号单位。一个汉字通常占 3 个字节。**"逐字节相同"是最严格的"相同"。** |
| **`sha256`** | 一种"文件指纹算法"：内容变一个字节，算出来的这串码就完全不同。用来证明"文件真的没被动过"。 |
| **备份** | 动手前先复制一份放着。本程序删岗位时会自动备份，并告诉你备份在哪。 |
| **硬 kill** | 程序被强制结束（断电、任务管理器强杀）。这时它来不及做任何收尾动作。 |
| **原子写** | 先把新内容写到一个临时文件，再"整体替换"过去。这样中途断电也不会留下半截坏文件。 |
| **锁**（lock） | 同一时刻只让一个操作改同一份数据，避免两个人同时改出乱子。 |
| **并发** | 同时发生多个操作。 |
| **换行符（LF / CRLF）** | 文本文件里"换行"在磁盘上怎么存。Windows 用两个字节（CRLF），Linux 用一个（LF）。**混用会导致"文件内容一模一样，但字节不一样"** —— 所以有"逐字节回滚"这种要求时它是个坑。 |
| **编码（UTF-8 / GBK）** | 汉字在文件里怎么存。用错编码保存，程序读出来就是乱码或直接报错。本项目踩过一次 GBK 的坑。 |
| **`mtime`** | 文件"最后修改时间"。回滚时也要一起还原，否则某些判断（谁比谁新）会错。 |
| **不可恢复** | 删了就是删了。本项目"真删除岗位"的语义就是不可恢复（但磁盘上会留一份备份，那是可回滚的余地，**不等于"原件还在"**）。 |

## 四、测试与验证（"我怎么敢说它是好的"）

| 词 | 大白话解释 |
|---|---|
| **测试** | 一段自动跑的程序，用来检查功能对不对。本项目有 **872 个**，跑一遍约 40 秒。 |
| **全绿 / OK** | 所有测试都通过了。 |
| **回归测试** | 专门盯着"以前修过的毛病别再犯"的测试。 |
| **夹具**（fixture） | 测试用的**假数据**（临时造一个假的知识库、假的岗位），这样测试**不会碰你的真实数据**。 |
| **变异取证** | 本项目最看重的一招：**故意把程序改坏**，看测试会不会红。**测试不红 = 那条测试根本没在测东西**（叫"假绿"）。 |
| **假绿** | 程序其实是坏的，测试却通过了。本项目的头号敌人。 |
| **假红** | 程序其实是好的，测试却报错。通常是测试自己写错了。 |
| **注入 / spy** | 测试里把某个"真动作"（比如联网搜索）换成假的计数器，就能断言"这一步**真的没发生**"。 |
| **探针** | 一段用 Node 跑真实前端代码的小程序，用来验证界面上的字**真的是那么写的**（而不是靠"源码里有这个词"来猜）。 |
| **断言** | 测试里那句"我要求它必须是 X"。 |
| **单飞**（single-flight） | 同一个岗位同时被点两次，只真算一次，第二次等结果。 |
| **幂等** | 做一次和做十次，结果一样。 |
| **隔离** | 测试完全在自己的临时目录里跑，**绝不碰你的真实 data 目录**。 |

## 五、文档与流程

| 词 | 大白话解释 |
|---|---|
| **spec**（设计文档） | 动手写代码**之前**先把"要做什么、为什么这么做、边界在哪"写清楚。在 `docs/superpowers/specs/`。 |
| **plan**（实施计划） | 把 spec 拆成一个个能单独验证的小任务。在 `docs/superpowers/plans/`。 |
| **两阶段独立审查** | 先让一个"没参与实现"的角色检查"**做的是不是当初要的**"（规格符合性），再检查"**代码写得好不好、有没有新毛病**"（代码质量）。 |
| **YAGNI** | "用不上的就别做"。防止顺手加一堆没人要的功能。 |
| **`file:line`** | 比如 `kb.py:372` = 文件 `kb.py` 的**第 372 行**。工程师按这个定位代码。 |
| **前端 / 后端** | 前端 = 你看到的界面（网页）；后端 = 在后面干活的 Python 程序。 |
| **接口 / 路由**（API） | 前端和后端约定好的"问话方式"。比如"要删岗位"要往 `/api/jd/purge` 发一个请求。 |
| **404 / 409 / 500** | 后端回答的"状态码"：404 = 没找到；409 = 现在这状态不允许（有冲突）；500 = 出错了。 |
| **`GET` / `POST`** | 两种请求方式：`GET` 是"我只看看，别改东西"；`POST` 是"我要提交/改东西"。 |
| **CSV / JSON** | 两种存数据的文本格式。本项目的数据都是 JSON（人也能读，用记事本打开就能看）。 |
