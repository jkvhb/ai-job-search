# 批 6（性能）+ 批 7（结构性）实施计划

> 来源：`docs/全项目体检报告-2026-10-15.md` §6（P4-1…P4-5）与 §8（结构性风险 1/2/6）。
> 原则同前几批：**先写会红的测试 → 改 → 变异跑全量 → 主控隔离探针复现 → 提交**；
> ⚠️ 性能项的判据**尽量不用墙钟**（会 flaky），优先用**可数的量**（迭代次数、渲染次数、请求数、比较次数）。

## 批 7 · 结构性（建议单独设计一轮再动手）

### 7.1「指向岗位的引用点清单」收成**一处**（收益最高）
- **现状**：清单 = `jds.id` / `jobs.jd_id` / `knowledge.from_jds[].id` / `interviews/*/status.json.job_id`，
  在 **`jdid.rename_jd`、`jddelete._plan`、`jobdup.merge_jobs`、`身份迁移.py` 四处各列一遍**；
  实测**已经漏了两处**：`report_state/<报告id>.json` 与 `interview.feedback.json`（删完 JD 后它们变成盘上孤儿，预演里也不列）。
- **做法**：造一个**单一真源**（例如 `jdrefs.py`）：
  `refs_of_jd(jd_id, key=None) -> [(kind, path, 说明/怎么改)]` + `rewrite(kind, path, old, new)`；
  四个调用方改用它；`jddelete` 的**预演**必须列出全部引用点。
- **防复发机制（这条比代码本身值钱）**：加一条**守卫测试** —— 扫描 `app.py`/各模块里所有"往 profile 下写文件"的路径，
  凡是带 `jd_id` 语义的都必须在 `jdrefs` 的登记表里出现过；**没登记就红**（新增产物时当场被抓）。
- **测试**：改 ID 后 `refs_of_jd(旧)` 为空、`refs_of_jd(新)` 覆盖全部产物；删 JD 后四个调用方**逐一**核对；
  **变异**：把 `report_state` 从登记表摘掉 → 预演/删除的断言必须红。

### 7.2 `jddelete` 删掉"合并的保留方"⇒ `merged_into` 悬空 ⇒ 记录**永久消失**
- **现状**：`A` 与 `B` 合并（`B.merged_into=A`）→ 删 `A` → `jobs.json` 剩 `{jd_id:B, merged_into:A}`，
  而 `app._ledger_rows()` 把所有 `merged_into` 非空的记录**全过滤** ⇒ 该记录**界面上再也看不到、也删不掉**（报告与原文还在盘上）。
- **做法**：删除时**先把悬空引用清掉或重指**（`merged_into` 指向已不存在的 id ⇒ 清空/改成 `B` 自己）+ **预演里列出**受影响记录 + 测试。
- **测试**：合并→删保留方→断言该记录**仍在台账里可见**（或至少被预演与日志点名）；变异：退回"直接删"→ 必须红。

### 7.3 备份轮转 / 清理入口
- **现状**：`jddelete` 每次删岗位留一份**含整份 knowledge.json** 的备份（只增不减）；`resumelib` 的 `.stale-*` **只能手工删**。
- **做法**：给维护脚本加一个 `--备份体检` 子命令：列出**目录 + 体积 + 对应版本/时间 + 是否被引用**，**人工确认后**再删。
  ⚠️ **绝不自动清**（"留档"的意义就在这），只提供"看得见 + 好删"的入口。
- **测试**：列出的条目与实际目录一致；**不删任何东西**（对照组：跑完盘上文件数不变）。

   必须**先设计再派**（并先跑一遍现有 `tests/test_jddelete.py`/`test_jdid.py`/`test_jobdup.py`/`test_migration.py` 拿到基线）。
