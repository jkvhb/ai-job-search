# JD 稳定身份 + 一个 JD 多份分析 · 设计文档（阶段 4A）

> 本阶段是用户提出的**根治方案**，取代"事后判重"：
> **给每个岗位 JD 一个稳定的 ID，在它下面做「多个简历 × 同一个 JD」的分析。**
> 它同时是之前 F（大卡片 + 多简历子报告）的落地形态。

---

## 1. 目标与背景

### 根因（本项目反复栽的同一个坑）

**岗位身份 = 报告文件名**（`20261003_语音文本评测_75分`）——里面嵌了**日期与分数**。
于是"换个简历重分析"必然产生新身份 → 知识库 `from_jds` 越叠越多 →
「被 N 个岗位提到」（复习优先级的乘性因子）**算错**。

已经发生的证据（阶段 3.6 实测）：用户 6 个概念的 `multi_jd` 全部来自**同一份 JD 的两次分析**。
阶段 3.6 用**模糊指纹**做了补救（治标）；本阶段把**身份本身**改对（治本）。

### 用户已确认的决策

| 决策点 | 用户选择 |
|---|---|
| JD ID 形态 | **结构化、可读、可手改** |
| ID 字段 | **学历 + 单位 + 职责 + 领域 + 城市 + 薪资 + 编号** |
| 缺失信息 | 填 **【未知xx】**（如 `【未知单位】`），让用户一眼看出缺什么 |
| ID 可编辑 | **用户可改**（AI 会认错）；改后**与全库比对，重复则报警、不保存** |
| 换简历成本 | **拆两段**（JD 级只算一次）—— 本阶段只建结构，省成本的实现放 B 段 |
| 删除 | **真删除（不可恢复）** —— 本阶段不做，放 D 段 |

### ID 长这样（分隔符用 `_`，**因为薪资里本身有 `-`**）

```
本科_【未知单位】_标注质检_文本_北京_13-26K_0001
└学历 └单位        └职责   └领域 └城市 └薪资    └编号（全局递增 4 位）
```

### 关键发现：**ID 的字段现在就有，不需要改提示词**

现有报告的 `REPORT_DATA` 里已经包含：

| ID 字段 | 现有来源 |
|---|---|
| 学历 | `education`（或 `hard_gates` 里 name=学历 的 `jd`） |
| 单位 | `company`（空 → `【未知单位】`） |
| 职责 | `job_category`（`数据标注/质检` → 去掉 `/` 等非法字符） |
| 领域 | **没有现成字段** → 用**关键词规则**从标题/JD 原文推（语音/文本/视频/图片/多模态/Agent），推不出 → `【未知领域】` |
| 城市 | `location` / `address` |
| 薪资 | `salary`（已经是 `13-26K` 这种格式） |
| 编号 | 全局递增 |

## 2. 范围

### 本阶段做

- **JD 库**（新文件 `jds.json`）：JD 身份 + **JD 级**信息（含投递状态/结果）
- **结构化 ID** 的生成、校验、**手改 + 全库查重**
- **一份分析挂到 JD 下**：`jobs.json` 的记录**只留分析级字段 + `jd_id`**
- **台账改成"大卡片 + 子报告"**：一行 = 一个 JD，展开看它下面的各份分析
- **迁移现有 6 个岗位**（按指纹归并成 4 个 JD）

### 本阶段明确不做（后三段）

- **B**：两段式分析（JD 段只算一次）—— 本阶段**只把数据结构留好**，仍然每次全跑
- **C**：简历库与版本延续（每次上传留档、上传时间/次数、延续子简历、多份比对）
- **D**：真删除 JD

## 3. 数据模型

### `jds.json`（新建，JD 库 = JD 级真相源）

```json
{
  "version": 1,
  "seq": 4,
  "jds": [
    {
      "id": "本科_【未知单位】_标注质检_文本_北京_13-26K_0001",
      "seq": 1,
      "education": "本科", "company": "", "duty": "标注质检",
      "domain": "文本", "city": "北京", "salary": "13-26K",
      "created_at": "2026-10-03 00:30", "updated_at": "…",
      "id_history": ["旧 id…"],
      "job_title": "语音/文本评测", "job_category": "数据标注/质检",
      "location": "北京", "source_type": "粘贴文本", "source_link": "",
      "jd_text_file": "…txt",
      "status": "未投递", "verdict": "建议投递", "notes": "",
      "outcome_at": "", "outcome_reason": "", "outcome_ai": null,
      "jd_facts": { }           // B 段用来存"JD 段只算一次"的结果；A 段先留空
    }
  ]
}
```

### `jobs.json`（**仍是分析列表**，但记录只留分析级字段 + `jd_id`）

```json
{ "id": "<分析id>", "jd_id": "本科_…_0001", "resume": "周汉钦-母版",
  "score": 75.0, "report": "<分析id>.html", "created_at": "…" }
```

**为什么必须把 JD 级字段搬走**：否则 `status` / `company` / `salary` 会在两个文件里各存一份
—— 本项目反复栽的"同一件事两处各存一份"。**JD 级只存 `jds.json`，分析级只存 `jobs.json`。**

**投递状态与 offer 结果放 JD 级**（你在一个岗位上只投一次，用其中一份简历）；
**匹配打分 / 简历大纲 / 优化方向 / 面试准备放分析级**（这些才随简历变）。

### 引用关系（迁移时要一起改）

| 引用方 | 现在指向 | 改成指向 |
|---|---|---|
| 知识库 `from_jds[].id` | 报告/分析 id | **JD id** |
| 面试记录 `status.json.job_id` | 报告 id | **JD id** |
| 归因数据（`outcome_*`） | 岗位记录内 | **JD 记录内** |

## 4. ID 的生成、校验、编辑

### 生成（新分析时）

1. 从分析结果取 学历/单位/职责/城市/薪资（见 §1 的映射）
2. 领域：关键词规则（`语音→语音`、`视频→视频`、`图片→图片`、`文本→文本`、`多模态→多模态`、`Agent→Agent`），推不出 → `【未知领域】`
3. 缺失 → `【未知xx】`（未知单位/未知学历/未知职责/未知城市/未知薪资/未知领域）
4. **清洗**：去掉/替换文件名非法字符 `\ / : * ? " < > |` 与空白
5. 编号：`seq += 1`，格式化为 4 位（`0001`）
6. 拼接：`字段1_字段2_…_字段N_编号`

### 校验（手改时）

- 段数必须与约定一致（7 段）
- 每段非空、无非法字符
- **全库查重**：与其它 JD 的 `id` 完全相同 → **拒绝保存**，返回 409 + 提示"这个 ID 已被占用"
- 允许把某段改成 `【未知xx】`

### 改 ID 的影响（**本阶段刻意最小化**）

- `jds.json` 里改 `id`，并把旧值记进 `id_history`
- 知识库 `from_jds` 与面试记录里**指向该 JD 的引用同步改**
- **已有的报告文件不重命名**（它们只是产物；台账通过 `jobs.json.report` 找到它们）
- **新报告**文件名用 `<jd_id>__<简历slug>.html`（同一 JD + 同一简历 = 同一个文件，重跑即覆盖）

## 5. 台账 UI：大卡片 + 子报告

- **一行 = 一个 JD**：显示 **JD ID**（可点开改）+ 状态徽章 + **分析份数** + 最高分
- **展开/点开** → 该 JD 下的各份分析：简历名 / 分数 / 日期 / 「📊 打开报告 ↗」
- **「+ 用另一份简历分析」**入口（A 段仍是全跑；B 段会只重跑简历段）
- ID 编辑框：显示 7 段、允许改、重复时**当场报警且不保存**
- 已合并的旧记录（`merged_into`）继续不显示

## 6. 迁移现有数据（**动真实数据，必须按纪律来**）

**现状**（实测）：`jobs.json` 6 条记录，其中 1 条是阶段 3.6 合并掉的（`merged_into` 非空），
所以**活跃分析 5 份**。按阶段 3.6 的指纹体检结果（统本三件套两两 0.990/0.993、
语音那对 0.965、示例无 JD 原文无法比对），迁移结果是 **5 份分析 → 3 个 JD**：

| 迁移后 JD | 归并进来的分析 | 依据 |
|---|---|---|
| 统本标注（视频标注） | `_66分` / `_69分` / `（视频标注AI训练标注师）_69分` | 指纹 0.990 / 0.993 / 0.990 |
| 语音/文本评测 | `20261003_…_75分`（`20261008_…_72分` 已在 3.6 标记为 `merged_into`） | 指纹 0.965 |
| 语音/文本评测（示例） | `示例_语音文本评测_80分` | **没有 JD 原文 → 无法比对 → 自成 1 个 JD** |

> ⚠️ **上表是"预期"，不是硬编码**：迁移脚本**以指纹与缺原文的事实为准**，
> 并把实际的「迁移前 → 迁移后」对照表打印出来给人看。
> **没有 JD 原文的岗位一律自成 1 个 JD**（不猜、不硬塞）。

**迁移脚本 `身份迁移.py`**（与 `报告体检.py` / `岗位去重.py` 同风格）：

```
python 身份迁移.py --试跑     # 在隔离副本上跑，打印「迁移前 → 迁移后」对照表，不动真实数据
python 身份迁移.py --执行     # 先整目录备份，再迁移
```

**纪律**：
1. **先备份 `data/profiles/<key>/` 整目录**
2. **先在 `--试跑` 里给出对照表**（每个旧岗位 → 哪个 JD、ID 是什么、哪些报告受影响）
3. **用户点头后才 `--执行`**
4. 迁移后核对：卡片数不变、`multi_jd` 合理、**报告文件数不变**、知识库里指向 JD 的引用无悬空

## 7. 测试

### Python（stdlib `unittest`，继承 `tests/base.py` 的 `IsolatedCase`）

1. **ID 生成**：字段齐全 → 7 段正确；`company` 空 → `【未知单位】`；领域推不出 → `【未知领域】`；
   含 `/` 的 `job_category` 被清洗；编号 4 位且递增
2. **ID 校验**：段数不对 / 空段 / 含非法字符 / 与库内重复 → **拒绝**（并给出原因）
3. **改 ID**：改成功后 `id_history` 有旧值；知识库 `from_jds` 与面试记录**同步改**；报告文件**不重命名**
4. **JD 库读写**：原子写、容错（垃圾类型）、并发（一把锁）
5. **一 JD 多分析**：同一 `jd_id` 下能挂多份分析；台账聚合出"分析份数 / 最高分"
6. **迁移**：`--试跑` **不写任何文件**（断言跑前后磁盘指纹一致）；
   `--执行` 后：JD 数 == 预期、每个 `jd_id` 都存在于 `jds.json`（**无悬空引用**）、
   **报告文件数不变**、知识库 `from_jds` 全部指向 JD id
7. **路由**：`/api/jds`（列表）、`/api/jd/id`（改 ID，重复 → 409）

### 前端（Node 探针 + 无头 Chrome E2E）

⚠️ 假绿已累计 11+ 次。**断言必须读元素属性/渲染产物，且要细到"个体"那一层。**

- 大卡片显示 JD ID + 分析份数 + 最高分；展开列出**每份**分析（断言到具体简历名与分数）
- 改 ID：重复 → **当场报警且不保存**（断言输入框的值**没变**、且出现了提示）
- 所有来自记录的数据过 `esc()`

### 反向取证（"改坏看是否变红"）

至少 4 处：① 重复 ID 也保存；② 改 ID 后不同步更新知识库引用；③ 台账把同一 JD 的多份分析显示成多行；
④ 迁移产生悬空 `jd_id` 但没被断言拦住。
⚠️ **做取证前先把文件备份到 `%TEMP%`，还原用 `Copy-Item` + sha256 核对**
—— **绝不要用 `git checkout`/`git restore`**（本项目已有两位实现者因此丢掉未提交的实现）。
