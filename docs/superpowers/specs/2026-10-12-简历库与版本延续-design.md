# 简历库与版本延续 · 设计文档（阶段 4C）

> 目标：把"简历"从一个**会被覆盖的文件**，变成**有族谱、有变更记录、能追溯到"这份报告用的是哪一版"**的东西。
> 同时修掉一条今天会**卡住用户**的查重死路。

---

## 1. 背景：现状实测（带证据）

| 项 | 现状 | 证据 |
|---|---|---|
| 简历存哪 | `data/profiles/<key>/resumes/` 下一个文件 | `store.p_path("resumes")` |
| 保存 | **直接截断覆盖**（非原子） | `POST /api/resumes` → `store.write_text` |
| 删除 | `os.remove` **永久删、无副本** | `DELETE /api/resumes` |
| 元数据 | **零**（无时间/版本/备注） | `GET /api/resumes` 只回文件名数组 |
| 取回当时那份 | **完全不可能**：报告**不嵌简历原文**（实测 20 行检测 **0/20 命中**）、`resumes/` **无下载路由** | `REPORT_DATA` 里没有 `resume` 键 |
| 族谱 | **完全没有**父/子或 lineage 字段 | 全库 grep 无命中 |
| 多份比对 | 数据层已有（一个 JD 挂多份分析）、前端已逐份列；**缺并排维度表** | `_jd_row().analyses[]` |
| **查重** | ⚠️ **只看 JD 文本** → 同一 JD 换第二份简历被判重复（409），**而前端无出口** | `find_analyze_duplicate`；`web/index.html` 无 `allow_duplicate` |

**最后一条是卡住用户功能的那种问题**：用户 C 阶段的核心用法正是"**几份简历比同一个岗位**"。

## 2. 用户已定的决策

| # | 决策 | 用户选择 |
|---|---|---|
| 1 | 删除简历 | **移出列表（母版快照保留）** + 另给「彻底删」入口 |
| 2 | 「子简历」含义 | **母** = 从多份里"**选定继续优化**"的那份；**子** = 母的修改版；均可选；"选定"是新动作 |
| 3 | 多份比对 | 加一张 **6 维度并排表**（不做报告文字差异） |
| 4 | 每个族谱在磁盘留几份内容 | **2 份：母版 + 最新版**；其余版本只留元数据与 AI 变更说明 |
| 5 | 变更说明 | 上传子简历时**和母简历比对，AI 写出"改了哪些地方"** |

**由 #4 直接推出的诚实边界（必须写进界面与文档）**：
**旧版本原文不保留** —— 只能看到"改了哪些（AI 写的）+ 那一版当时的分数"，**取不回旧版原文**。
**绝不假装能取回。**

## 3. 数据模型

### 新建 `resumes.json`

```json
{ "version": 1, "resumes": [
  { "id": "rv_0001", "name": "周汉钦-母版",
    "root_id": "rv_0001", "parent_id": null, "rev": 1,
    "at": "2026-09-18 23:06", "size": 2455, "sha256": "…",
    "file": "resumes/周汉钦-母版.md",
    "mother_file": null,
    "chosen": true,
    "ai_diff": { "summary": "…", "changes": [ {"where": "项目经历", "what": "新增语音Agent项目"} ] },
    "ai_diff_error": "",
    "note": "" } ] }
```

- `parent_id` / `root_id`：族谱（独立简历各自是根）
- `rev`：**第几次修改**（族谱内序号，从 1 起）
- `chosen`：「**选定继续优化**」= 母简历标记；**同一族谱内最多一个为真**
- `sha256`：内容指纹 —— 手工在程序外改了文件时**能发现并如实提示**，不假装一致
- `ai_diff`：AI 写的变更说明（`summary` 一句话 + `changes` 逐条）；失败时 `ai_diff_error` 非空

### 磁盘布局（**每个族谱最多 2 份内容文件**）

```
resumes/<名字>.md            ← 该族谱【最新版】内容（保持现有约定，打包分享等照旧）
resumes/快照/<版本id>.md      ← 【母版】快照，只在上传子版、覆盖前留一份
```

**母版同时就是最新版时，不写快照**（避免"一件事两处存一份"；此时"母版内容" = 最新版文件）。

**快照的触发条件**（Task 1.8 定稿；Task 1.9 补了一条**已证明**的例外；
早先"**当且仅当**母版内容 == 盘上内容才写、不符就不写"的写法**已被推翻**——那句话曾在界面上，
是句假话）：
> **只要**「快照文件不存在」**或**「它已证明装的不是这一版的内容（记录 `sha256` 与快照内容不符，
> 而盘上那份**恰好就是**）」**且**「`<名字>.md` 此刻在盘上有字节」**且**
> 「这一版的原文不是 `missing`」→ 覆盖前先把**盘上那份的原始字节**存进 `resumes/快照/<母版id>.md`
> （`store.read_bytes` / `write_bytes`：**不做**编码与换行转换，非 UTF-8 与 CRLF 都逐字节留）。
> **核对通过**（盘上那份就是这一版的原文）才记 `mother_file` = "母版原文的存档"；
> **与记录不符**（程序外改过 / 非 UTF-8 读不出来）时**字节照样留**（免得覆盖后无处可找），
> 但**不记** `mother_file` —— **存档 ≠ 冒充**，取回时 `read_version` 如实报 `mismatch`，
> 界面提示「内容与记录不符」。只有 `missing`（这一版原文**从来没保留过**）**不留**。
> **已存在就不重写**：快照一经生成即**不可变**（这是它能当"参照原点"的前提）；
> 唯一例外是上面那条"**已证明**过时"。⚠️ 记录**没有** `sha256` 时**没有依据判谁对** →
> 那条例外**不生效**（宁可不动，也绝不凭猜测改写快照）。
> 读侧同理：快照**有字节却读不出来**（非 UTF-8）时如实报 `mismatch`，
> **绝不**说成"存过档、内容是空的"（那会让界面显示一份空简历 —— 又一处"读不出来被当成空的"）。

推论：族谱 `母(v1) → 子(v2) → 孙(v3)` 里，v2 生成时已把 v1 快照留下；
v3 生成时 `<名字>.md` 里是 v2 的内容、母版是 v1（快照已存在）→ **不产生新快照**；
v1 的快照只有在"已证明过时"且盘上那份就是 v1 时才被**修正**。

### `name` 的唯一性与"已移出"

- `name` 在**未移出**的简历里必须**唯一**：保存时校验，重名 → **明确报错**（绝不静默覆盖别人的文件）
- 已移出（`removed=true`）的族谱：**不能延续**（要延续先"恢复"）；可"恢复"（置回 `removed=false`，名字冲突时要求改名）

### 分析记录新增 `resume_id`

`ANALYSIS_FIELDS` 增加 `resume_id` → **每条分析钉住它用的那一版**。
报告数据里同时带 `resume`（显示名，兼容旧报告）与 `resume_id`。
**旧分析没有 `resume_id`** → 界面显示"版本未知（早于版本库）"，不猜。

## 4. 流程

### 4.1 保存/上传一份简历

```
保存 → 写 <名字>.md（沿用现有路径）
     → 在 resumes.json 里生成/更新一条版本记录（rev、at=现在、size、sha256）
     → 若是"延续"（见 4.2）→ 覆盖前先把母版快照留下
```

**新增「选择文件」入口**：`.md` / `.txt` 由前端 `FileReader` 读取后按文本提交（**不引第三方依赖**，不做 multipart）。

### 4.2 延续 vs 新开（用户可选）

上传/保存时，若该简历已被"选定"（`chosen`）且内容有变化 → 前端弹选择：

| 选择 | 结果 |
|---|---|
| **延续** | 新记录 `parent_id` = 母版 id、`root_id` 同母版、`rev` = 母版 rev+1；**覆盖 `<名字>.md` 前先写母版快照** |
| **新开一份独立的** | 新记录 `parent_id` = null、`root_id` = 自己、`rev` = 1 |

默认不选任何一项（**不自动延续**；用户没选就是"新开"）。

### 4.3 「选定继续优化」= 标记母简历

新动作（今天没有）。把某版本 `chosen=true`，**同族谱内其它版本置 false**。
界面在简历 tab 与 JD 卡片里都显示"★ 母简历"。

### 4.4 AI 变更比对（**只在"延续"时**触发）

- **触发条件**：这次保存是**延续**（有母版可参照）。**"新开一份独立的"不比对**（没有可比的对象）
- 输入：**母版内容** + **子版内容**（都从 `resumes.json` 指到的文件读）
- 输出：`{summary, changes: [{where, what}]}`（提示词要求"只写确实改了的地方，没把握就少写"）
- 存进 `ai_diff`，**永久可查**（即使旧版原文没留）
- **失败**（网络/额度/JSON 坏）→ 版本**照样保存**，`ai_diff_error` 记原因，**界面如实说"这次没能生成变更说明"**
- **不做**：不为了比对去保留更多历史文件（只有母版 + 最新）

### 4.5 取回

| 要哪一版 | 从哪读 |
|---|---|
| 最新版 | `resumes/<名字>.md` |
| 母版 | `resumes/快照/<id>.md`；若它同时是最新版 → 读最新版文件 |
| **其它历史版本** | **原文没有** → 界面明确写「旧版原文未保留，仅存变更说明」+ 展示 `ai_diff` 与当时的分数 |

**新增下载路由**：`GET /api/resumes/file?version=<id>` 返回该版**原文**（下载/查看）。

### 4.6 删除（用户决策 #1）

| 动作 | 行为 |
|---|---|
| **删除** | 记录标记 `removed=true`（移出下拉/列表，不能再用于分析）；**母版快照与变更说明保留** |
| **彻底删除** | 显式入口 + 二次确认；删记录 + 删它自己的快照文件；**已在历史分析里用过的事实不可撤**（报告里仍留着 `resume_id` 与显示名）→ 界面明说这一点 |

**绝不删除**别人（其它版本/其它简历）的文件。

## 5. 界面

1. **简历 tab 按族谱分组**：母版 → 子版（缩进）；每行显示 **上传时间 / 第几次修改 / ★母简历 / 变更说明入口 / 取回原文**

3. **409 出口**（见 §6.2）
4. 所有用户数据过 `esc()`；每个 fetch 有 `catch`

## 6. 接口

### 6.1 简历相关

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/resumes` | **改**：返回族谱结构（版本列表 + 元数据 + chosen + removed 过滤） |
| POST | `/api/resumes` | **改**：body 增 `parent_id` / `lineage`（延续或新开）；写档 + 生成版本 + 触发 AI 比对 |
| GET | `/api/resumes/file?version=<id>` | **新**：下载/查看某版原文（按 §4.5 的规则，历史版返回明确说明而非空文件） |
| POST | `/api/resumes/choose` | **新**：`{version}` → 标记母简历 |
| DELETE | `/api/resumes` | **改**：= 移出列表（不再 `os.remove`） |
| POST | `/api/resumes/purge` | **新**：彻底删（含该版本自己的快照文件） |

### 6.2 查重粒度（**必须修**）

**现状**：`find_analyze_duplicate(jd_text, overwrite_id)` 只看 JD → 同一 JD 换简历被判重复。
**改成**：**(JD 指纹 + `resume_id`)** 才算重复。

| 情形 | 行为 |
|---|---|
| 同 JD + **不同**简历 | **不是重复** → 正常新建（**这正是用户要的用法**） |
| 同 JD + **同一**简历 | 是重复 → 返回 409；前端弹「**覆盖**（沿用原 id/报告名）/ **仍然新建**」 |
| 已有分析没有 `resume_id`（老数据） | 按"版本未知"处理：**不判重复**（宁可多建，也不误拦） |

## 7. 老数据（**有证据，不是猜**）

```
简历文件 resumes/周汉钦-母版.md  2455 字节  改于 2026-09-18 23:06:24
6 次分析: 09-19 14:29 / 09-19 14:50 / 09-19 15:06 / 09-19 21:18 / 10-03 00:30 / 10-08 16:40
```

（这条清单已按真实数据核对：上面就是 `python 简历迁移.py --试跑` 在真实 `data/` 上打出来的
`6 条分析全在文件时间之后（…）` 那一行。此前这里漏了 `09-19 15:06`、且多写了一个不存在的 `10-12`。）

**文件改于所有分析之前**，而保存简历会更新文件时间 → **这 6 次用的就是当前这份内容**。

迁移（`简历迁移.py`，与既有 CLI 同风格）：

```
python 简历迁移.py --试跑     # 严格只读，打印对照表
python 简历迁移.py --执行     # 先整目录备份，再迁移
```

- 登记 `rv_0001`：`name=周汉钦-母版`、`rev=1`、`at=mtime`、`size`、`sha256`、`chosen=true`、`root_id`=自己
- 6 条历史分析的 `resume_id` → `rv_0001`，并在文档/界面写明**这是推定**（依据 mtime 早于全部分析）
- **不移动、不改名、不删除**任何简历文件
- 备份 + 幂等 + 失败回滚（照 `身份迁移.py` 的既有做法）

## 8. 诚实边界（必须写进界面/文档，不许美化）

1. **旧版原文不保留**（用户决策 #4）→ 只留变更说明与分数；历史版取回时**明确说"原文未保留"**
2. `sha256` 对不上 → **如实提示**"该文件被程序外修改过"，不假装一致
3. `ai_diff` 是**模型写的**，可能漏 → 标注「AI 生成，以原文为准」
4. AI 比对失败 → 版本照样保存，但要**明确显示"没生成变更说明"**
5. 老数据的 `resume_id` 是**推定**（§7），要在界面上标出来
6. **彻底删**不能撤销"它曾在某次分析里被用过"这一事实

- 不保留每一版原文（用户已定）
- 不做报告文字差异比对（用户选了 2）

## 10. 测试与验收

### 测试（stdlib `unittest`，继承 `IsolatedCase`）
1. `resumes.json` 读写：原子写、垃圾容错、锁（并发）、`chosen` 唯一性
2. **版本链**：延续 → `parent_id`/`root_id`/`rev` 正确；新开 → 独立根；母版同时是最新版时**不写快照**
3. **快照**：延续时覆盖前确实留下母版原文，且**逐字**等于覆盖前的内容
4. **AI 比对**：调用 1 次；失败时版本仍保存 + `ai_diff_error` 非空 + **不写假的 `ai_diff`**
5. **取回**：最新版/母版/历史版三条路径（历史版返回明确说明，**不是空文件**）
6. **删除语义**：移出列表后**母版快照与变更说明仍在**；彻底删只删自己那份；**绝不删别人的文件**（反假绿：断言别家文件逐字未变）
7. **查重**：同 JD 不同简历 → 不重复；同 JD 同简历 → 409；**老数据（无 `resume_id`）不误拦**
8. **分析钉版本**：新分析的 `resume_id` 正确；旧分析仍是"版本未知"
9. **迁移**：`--试跑` 严格只读（逐文件指纹不变）；`--执行` 后 6 条都指向 `rv_0001`；**幂等**；失败回滚

### 反向取证（≥6 处，贴红、**注明红在哪一行**）
① 延续时不写快照 → 快照那条应变红；② 覆盖时把母版文件也改了 → 逐字相等那条应变红；
③ AI 失败时也写一个空 `ai_diff`（假装成功）→ 那条应变红；④ 删除时`os.remove` 真删文件 → 那条应变红；
⑤ 查重仍只看 JD → "同 JD 不同简历"那条应变红；⑥ 彻底删连别人的文件一起删 → 反假绿那条应变红

### 验收
- [ ] 上传 A/B/C 三份 → 都有分数；**6 维度并排表**能看出谁在哪一维强
- [ ] 选定 A 为母简历 → 改完再上传 → 选"延续" → A 下出现子版，**且能看到 AI 写的改动**
- [ ] 取回母版原文成功；取回**历史版**时明确说明"原文未保留"（不是空文件）
- [ ] 同一 JD 换第二份简历**不再 409**；同 JD 同简历仍 409 且有**覆盖/仍然新建**出口
- [ ] 删除 = 移出列表（快照仍在）；彻底删只删自己
- [ ] 全部测试通过；**真实数据迁移必须先给你看对照表、你点头才执行**

**纪律（历次教训，逐条适用）**
1. **绝不用 `git checkout`/`git restore` 还原"改坏"** → `Copy-Item` 备份 + sha256 核对
