## 1. 目标与背景

### 用户描述的目标流程（原话）

> "每个岗位 JD 对应一个**面试前报告**（现在已经做好了），然后面试者根据报告去调整和准备……
> 准备好之后面试者去面试，**将面试记录上传，程序通过 AI 模型来进行评估**此次面试的质量
> （包括面试官的提问水平和问题质量、面试者的回答质量等），得到 AI 的分析后再次学习复盘和准备
> 后续可能会有的二面或三面。"

本设计做这个闭环的**中段**：上传面试记录 → 本地转写 → AI 评估 → 复盘报告 → 反哺知识库。

### 已确认的决策

| 决策点 | 用户选择 |
|---|---|
| 复盘结果放哪 | **生成独立复盘报告**（HTML，可打印/导出），**挂在岗位上** |
| 分析产出 | **7 项全要**：问题清单+分类 / 考察重点及占比 / 新词 / 面试官提问质量 / 你回答的逐题点评 / 答砸的知识点 / 二面准备建议 |
| 新词入库 | **不自动建卡**（怕知识库被灌爆）→ 报告里列出 + **手动「➕ 加入知识库」按钮** |
| 转写引擎 | **复用 vidkit 的 faster-whisper**，不自己写；**不用它的 Qwen 润色**（用户已决定） |
| 上传方式 | **网页文件选择器**真上传 |
| 领域词库 | **给 vidkit 加一个 AI 领域**（跨项目改动，用户已批准） |

### 实测的硬约束（来自 vidkit 自己的测试报告）

```
11 分 23 秒的音频 → 转写耗时 613 秒 = 0.898 × 音频时长；峰值内存 1.8 GB
   （faster-whisper medium，CPU int8，产出 3057 字 + 191 个时间片段）
```

**⇒ 30 分钟的面试要转约 27 分钟。绝不能做同步请求，必须后台任务 + 进度。**

同一份报告的另一条结论也被采纳：**原始音频与原始转写必须分别保留**（润色有误改风险；
本轮不做润色，但结构留好）。

## 2. 范围

### 本轮做

- 上传面试录音/视频/文字稿（二进制上传）
- 后台转写任务（复用 vidkit）+ 诚实的进度反馈 + 可重试
- AI 评估（7 段结构化产出）
- 生成**复盘报告**（独立 HTML，挂岗位，可动态套用最新模板）
- 岗位台账的「🎤 面试复盘」入口
- 反哺知识库：答砸回写、复习优先级加「被问过」因子、新词手动入库
- 给 vidkit 加 `ai` 领域词库

### 本轮明确不做（YAGNI）

- **说话人分离（diarization）**：faster-whisper 不做这个；面试官/候选人的角色由模型从内容推断
- **润色**（用户已决定不用）
- **多份录音合并成一次面试**（一段录音 = 一次面试记录）
- **`.docx` / `.pdf` 文字稿解析**：只支持 `.txt` / `.md`（要解析 Office 得引第三方库）
- **offer 结果复盘**（下一轮 E）
- **F 的大卡片 + 多简历子报告重构**

## 3. 数据落点

```
data/profiles/<key>/interviews/<面试id>/
    audio.<ext>       原始录音/视频 —— 保留，永不自动删
    source.txt        原始文字稿（若上传的是文字稿）
    transcript.json   转写结果：text / segments(含时间戳) / language / duration / detected_domain
    analysis.json     AI 评估结果
    status.json       任务状态（供重启后判断"被中断、可重试"）
data/profiles/<key>/reports/<日期>_<岗位slug>_面试复盘.html
data/profiles/<key>/jobs.json   岗位记录新增 interviews: [面试id, ...]
```

- **面试 id**：`<YYYYMMDD_HHMM>_<岗位slug>`，`slug` 复用 `store.slug()`；同秒冲突时加序号
- 复盘报告放进**已有的 `reports/` 目录** → 自动进入现有报告列表、备份工具、动态模板渲染

## 4. 上传通道

**`POST /api/interview/upload`**（`Content-Type: application/octet-stream`）

| 头部 | 说明 |
|---|---|
| `X-Job-Id` | 挂到哪个岗位（必填） |
| `X-File-Name` | 原始文件名，**URL 编码**（中文文件名必须编码，否则 HTTP 头不合法） |
| `X-Kind` | `auto`（默认）/ `audio` / `text` |

- **分块读 `rfile` 写盘**（不要 `read(n)` 一次性进内存）→ 几十 MB 的录音也不吃内存
- 目标文件名由服务端生成（`audio.<ext>`），**原始文件名只作为元数据存进 `status.json`**
  —— 绝不用客户端文件名拼路径
- **大小上限**（默认 500 MB）：超限立即 413 并中止
- 类型判定：扩展名在 `.txt/.md` → 文字稿（**跳过转写**，直接进分析）；否则按音/视频走 ASR
- 返回 `{ok, interview_id}`，**随后立即返回**，转写在后台线程里跑

## 5. 后台任务与进度

### 状态机

```
queued → transcribing → analyzing → done
                    ↘         ↘
                     error（可重试）
```

文字稿上传时直接 `analyzing`（没有 `transcribing` 阶段）。

### 实现

- 模块级 `INTERVIEW_JOBS = {}` + 一把 `threading.Lock`（与 `log.py` 的 `_LOG_LOCK` 同风格）
- 每个任务一个 `threading.Thread`（`daemon=True`）
- **状态落盘 `status.json`**（含 `state` / `started_at` / `elapsed` / `error` / `original_name` / `bytes`）
  → 程序重启后能告诉用户"上次转写被中断，可重试"，而不是永远卡在"转写中"
- **进度**：见下面的「关于预计时长」——只报真实已用时长，**绝不编百分比**

### API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/interview/upload` | 二进制上传（见 §4），返回 `{ok, interview_id}` |
| GET | `/api/interview/status?id=` | 轮询状态（含 `elapsed` / `estimate_hint` / `error`） |
| POST | `/api/interview/retry` | `{id}` 重跑（从失败的那一步开始：已有 `transcript.json` 就跳过转写） |
| GET | `/api/interview/list?job=` | 列某岗位（或全部）的面试记录 |
| POST | `/api/knowledge/add` | `{term, definition?, category?}` → 手动把新词加进知识库（见 §8） |

### 关于"预计时长"（不要编数字）

上传时**拿不到音频时长**（vidkit 只在转写完才返回 `duration`）。所以：
- **能**用 `ffprobe` 拿到时长（ffmpeg 已装）→ 显示「已运行 N 分钟 · 预计 ≈ M 分钟（音频时长 × 0.9）」
- **拿不到**（没有 ffprobe / 探测失败）→ **只显示「已运行 N 分钟」**，不给预计

两种都不给百分比 —— 转写内部不报进度，编一个百分比就是骗人。

## 6. vidkit 集成

### 定位与校验

- 配置项 `vidkit_dir`（`config.json`），默认**自动探测**：本项目的同级目录 `../video-link-extractor`
- 启动任务前校验：`.venv\Scripts\python.exe` 存在 **且** `models\medium` 存在
  → 不满足就**明确报错**（告诉用户缺什么、怎么装），而不是跑一半才失败

### 调用方式：子进程 + 它的 venv + 它的模块

```
<vidkit>\.venv\Scripts\python.exe -c "<内联脚本>" <audio路径>
```
内联脚本：`from vidkit import transcribe` → `transcribe.transcribe(sys.argv[1], language='zh', domain='ai')`
→ `print(json.dumps(result, ensure_ascii=False))`，服务端读 stdout 解析 JSON。

**为什么不用它的 CLI**：CLI 的 `--out` **只写纯文本、丢掉时间戳**；模块调用能拿到完整
`{text, segments[{start,end,text}], language, duration, detected_domain}`，
而时间戳对"这一段在聊什么"很有用。

- **超时**：`音频时长 × 3 + 10 分钟`（拿不到时长就用固定上限，如 4 小时）
- 子进程 `stderr` 收进日志（截断），失败时把尾部错误回给前端
- **转写函数必须是可注入的**（形如 `transcribe_audio(path, cfg, runner=None)`）：
  测试传假实现，**绝不真跑 vidkit**（否则单测要跑几分钟）
- **不改 vidkit 的任何代码**（除了 §6.1 的词库）

### 6.1 给 vidkit 加 `ai` 领域词库（唯一的跨项目改动）

`src/vidkit/lexicon.py` 加两项：
- `DOMAINS["ai"] = {"name": "AI/数据标注", "hotwords": "...", "keywords": [...]}`
- `DOMAIN_PROMPTS["ai"] = "以下是关于大模型、机器学习、数据标注与评测的讲解，请使用正确的专业术语并添加标点符号。"`

词表至少覆盖：大模型 / LLM / 语言模型 / 参数 / 微调 / 预训练 / 对齐 / RLHF / 提示词 / 上下文窗口 /
Token / 幻觉 / 向量检索 / RAG / 多模态 / 推理 / 蒸馏 / 量化 / 标注 / 标注员 / 标注规范 / 质检 /
验收 / 抽检 / 一致性 / Kappa / 混淆矩阵 / 准确率 / 召回 / F1 / 首字时延 / ASR / TTS / OCR /
语音识别 / 语音合成 / 文本评测 / Bad Case / 归因 / 评测集 / 基线。

- CLI 的 `--domain` 用 `list(lexicon.DOMAINS)` 生成 → **自动包含 `ai`，CLI 不用改**
- 改完**跑它自己的 `tests/test_smoke.py`** 确认没破坏
- 该项目的改动**单独提交到它自己的仓库**（不混进本项目的提交）

## 7. AI 评估

一次模型调用（文本模型，`temperature` 沿用配置），输入 = 转写文本（含时间戳片段）+ 岗位 JD（若有）+ 岗位分类。

**输出 JSON（7 段，全部必出）**：

```json
{
  "summary": "一段总评",
  "questions": [{"q": "面试官原话或概述", "category": "AI基础技术|数据标注专业|运营能力|项目经历|行为面试|反问环节|其他",
                 "answer_quality": "好|一般|差|未作答", "comment": "点评"}],
  "focus_areas": [{"area": "AI基础技术", "share": 40, "evidence": "依据"}],
  "new_terms": [{"term": "…", "why": "为什么算新词", "definition": "一句话解释", "category": "…"}],
  "interviewer_quality": {"score": 1, "comment": "…", "issues": ["提问模糊/重复/无深度…"]},
  "answer_review": [{"topic": "…", "verdict": "答得好|答砸了", "what_went_wrong": "…", "better_answer": "…"}],
  "weak_concepts": [{"term": "…", "reason": "…"}],
  "next_round_prep": {"likely_followups": ["…"], "to_study": ["…"]}
}
```

- `share` 之和不必等于 100（允许"其他"），但要在提示词里要求尽量归一
- **长录音**：转写超长时（阈值如 40,000 字）先分块摘要再汇总（map-reduce），
  并在报告里标注"因篇幅做了分段分析"
- 复用现有的 **JSON 自动修复**机制（`llm.repair_json`），与 JD 分析同款容错

## 8. 反哺知识库（闭环）

### 8.1 "被问过"用**确定性匹配**判定，不靠模型

面试官/候选人嘴里出现了某个知识库概念 → 就是"被问过"。这一步**在 Python 里做**，不进模型提示词：

```
对每个 KB 卡片：若 normalize 后的 term 在转写文本里出现 → 命中
```

理由：① 确定性、可测、零额度；② 不会因为模型漏读而漏记。
（天然会有误命中，如"模型"这种短词 —— 用已有的 `_REVIEW_WEIGHT` 同款思路：
**长度 ≥ 2 的 term 才参与匹配**，并在报告里显示命中依据为"转写中提到"。）

### 8.2 写回规则

| 来源 | 判定方式 | 动作 |
|---|---|---|
| 被问到（任意） | §8.1 确定性匹配 | `asked_count += 1` |
| `weak_concepts`（AI 判定答砸了） | 模型输出 | `last_outcome = "没答上"`；**若 `state == "已掌握"` → 降为 `"学习中"`**（你以为会了，其实不会） |
| `answer_review` 里 `verdict == "答得好"` 的概念 | 模型输出 | `last_outcome = "答上了"` |
| `new_terms` | 模型输出 | **只列在报告里，不自动建卡**；每个词旁一个「➕ 加入知识库」按钮 → `POST /api/knowledge/add` → 复用 `kb.upsert_check(term, "待学习", {definition, category})` |
| `weak_concepts` 里**知识库中找不到卡片**的词 | 匹配失败 | 一并作为**待加入**项列在报告的新词区（标注"面试里答砸了，但知识库里还没有"），由用户点按钮决定 |

**顺序很重要**：先做 §8.1 的 +1，再做 AI 判定的 `last_outcome` 覆盖，
最后做"已掌握 → 学习中"的降级（保证降级不会被后续写回覆盖掉）。

**复习优先级公式加一个因子**（改 `kb._review_score`）：

```
旧: 状态权重 × (1 + 被多少岗位提到) × (1 + 久未复习加成)
新: 状态权重 × (1 + 被多少岗位提到) × (1 + 久未复习加成) × (1 + 被面试问过几次)
```

`asked_count` 字段**已存在**（`kb.py` 的 `DEFAULT_OUTCOME` / `asked_count`），本轮只是首次真正用起来。
现有排序测试会因此需要更新（新因子在 `asked_count=0` 时是中性的 1，所以大多数既有断言不变；
但要**补一条"被问过的排更前"的测试**，并验证它在移除该因子时变红）。

## 9. 复盘报告与呈现

### 模板

- 新增 **`web/interview_template.html`**（自带 CSS/JS，零依赖，与 `report_template.html` 同风格）
- 报告数据里带 **`kind: "interview"`**；`/reports/*` 的动态渲染**按 `kind` 选模板**（缺省 `jd`）
  → ① 老 JD 报告不受影响；② **复盘报告也能自动吃到以后的模板改进**
  （避免重演上一轮"老报告用不上新前端"的坑）
- 报告内容：总评 / 考察重点占比（条形）/ 问题清单+分类+回答质量 / 面试官提问质量 /
  逐题点评（含"更好的答法"）/ 新词（带「➕ 加入知识库」按钮）/ 答砸的知识点 / 二面准备建议 /
  **原始转写全文（可折叠）** / 音频时长与转写领域等元信息
- **「➕ 加入知识库」按钮需要服务端**：报告从工具里打开时正常；
  若用 `file://` 直接双击打开（拿不到 API），按钮要**明确提示"未连接到工具，无法入库"**并禁用，
  不能点了没反应、也不能假装加成功（与打钩持久化的降级口径一致）

### 岗位台账入口

- 每行加「🎤 面试复盘」按钮：
  - **没有面试记录** → 弹出上传面板（选文件 → 上传 → 进度轮询 → 完成后自动打开报告）
  - **已有** → 直接打开最近一份；多于一份时列出选择
- 行内显示：`面试 2 次 · 最近 没答上 3 个`
- 上传面板必须：显示进度、失败可重试、**失败绝不显示成完成**

## 10. 错误处理

- **vidkit 缺失/未装模型** → 上传时就明确报错（缺什么、怎么装），不进入任务
- **转写子进程失败/超时** → 任务转 `error`，保留已写入的音频，`retry` 可重跑
- **转写成功但 AI 分析失败** → 保留 `transcript.json`，`retry` 只重跑分析（**不重复花 27 分钟转写**）
- **程序中途关闭** → 重启后由 `status.json` 判定为"被中断"，提示可重试
- **上传中断/超限** → 删除半截文件并记日志（不留垃圾），返回明确错误
- **报告渲染失败** → 与现有 `/reports/*` 一致：退回文件本身，绝不 5xx
- **知识库写失败**（手动入库、回写 `asked_count`）→ 前端明确提示，**不假装成功**

## 11. 测试

### Python（stdlib `unittest`，继承 `tests/base.py` 的 `IsolatedCase`）

1. `store`：面试目录/文件的路径解析（含 `safe_name` 防穿越）、大小上限、半截文件清理

### 前端（本项目无 JS 测试设施，用 Node 探针）
