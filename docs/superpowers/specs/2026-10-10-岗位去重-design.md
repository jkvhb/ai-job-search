# 岗位去重（JD 原文判重）· 设计文档（阶段 3.6）

> 来源：阶段 3.1 计划的「3.2 待办」第 1 条 ——
> 「同一岗位重复分析会变成两个『来源岗位』……**multi_jd 被高估**，而『被 N 个岗位提到』
> 正是本功能的核心信号 → 建议改用『公司 + 职位』做去重键」

---

## 1. 目标与背景

### 问题**已经在用户真实数据里发生了**（实测确认）

用户知识库里 **6 个「被多个岗位提到」的概念，全部来自同一对岗位**：

```
20261003_语音文本评测_75分   ← JD 原文 125 字，10-03 分析，75 分
20261008_语音文本评测_72分   ← JD 原文 198 字，10-08 分析，72 分
同标题「语音/文本评测」· 同北京 · 同 13-26K · 同本科1-3年 · 要求开头逐字相同
```

这两条是**同一份 JD 分析了两次**（一次是截断/潦草的粘贴），
于是那 6 个概念记成了「被 2 个岗位提到」——而 `×(1 + 被多少岗位提到)` 是**复习优先级的乘性因子**。
**它在静默算错用户现在就能看到的排序**，且同一个 JD 反复调简历重分析会越叠越多。

### 为什么不用文档建议的「公司 + 职位」

**用户 6 个岗位的 `company` 全是空的**（只有示例数据填了）。只按职位名去重会把
**不同公司的同名岗位误并**（「语音/文本评测」这种是通用标题）。

### 为什么不能简单哈希（实测数据定的方案）

同一份 JD 的两次粘贴**长度不同**，所以：

| 指标 | 同一份 JD（用户那对） | 不同 JD（基线） | 结论 |
|---|---|---|---|
| 精确相等 | **False**（100 vs 163 归一化字） | — | 哈希**不可用** |
| 最长公共前缀 | 44 字（占短的 44%） | — | 前缀匹配**会漏** |
| Jaccard | 0.573 | 0.013 | 常见的 0.8 阈值**会漏** |
| **包含度** | **0.965** | **0.059** | **余量 16 倍 → 采用** |

---

## 2. 范围

### 本轮做

- **判定算法**：字符 bigram 的**包含度**（阈值 0.85），不存指纹、不加字段、不迁移
- **存量修复**：体检扫出疑似重复的岗位对 → 列出给你看 → **你确认后合并**
  （KB 的 `from_jds` 归并、面试记录 `job_id` 跟着改、被并的岗位**标记不删**）
- **分析前查重**：提交 JD 时命中已有岗位 → **不消耗任何模型/搜索额度**，返回提示让用户选
  **覆盖**（沿用原岗位身份重跑）或 **新建**（明确告知会重复计入）

### 本轮明确不做

- **自动合并** —— 永远由用户确认（宁可漏报也不误并）
- **改岗位 id 的命名方案**（id 里含分数，本身就是个 wart）——「覆盖」时**沿用原 id 不改名**：
  改名要同时改 3 处引用（`jobs.json` / KB 的 `from_jds` / 面试记录的 `job_id`），风险大于收益。
  代价只是**报告文件名里留着旧分数**（内页与台账显示的都是真实 `score` 字段）
- 「公司 + 职位」去重键（数据不支持，见 §1）

---

## 3. 判定算法

```
归一化：NFKC 折叠 → 小写 → 去所有空白 → 去中英标点
分块：  字符 bigram 集合（"abc" → {"ab","bc"}）
相似度：包含度 = |A ∩ B| / min(|A|, |B|)
阈值：  0.85
```

**保守边界（避免噪声误判）**：
- 归一化后**长度 < 40 字**（或 bigram 数 < 30）→ **不做判定**，直接视为"不重复"
  （极短文本的包含度天然容易偏高）
- 任一侧为空 → 不重复
- 只比较**能读到 JD 原文**的岗位（`jd/<岗位id>.txt` 缺失的跳过，并在体检报告里如实列出"跳过了 N 个"）

**为什么是包含度而不是 Jaccard**：包含度对「一份是另一份的截断/摘抄」友好（0.965），
而 Jaccard 会因为长度差被稀释到 0.573 —— 用 Jaccard 要么漏报，要么把阈值压到 0.4 那种危险区间。

---

## 4. 数据与引用（**不新增字段、不迁移**）

JD 原文**本来就已经按岗位落盘**：`data/profiles/<key>/jd/<岗位id>.txt`。
所以判重 = 新 JD 与磁盘上已有各份**逐字比对**，岗位数少时瞬间完成。

**引用岗位 id 的地方（合并时必须一起改）**：
1. `jobs.json` 里的记录（`id` / `report` / `jd_text_file`）
2. 知识库 `knowledge.json` 里每张卡片的 `from_jds[].id`
3. **面试记录** `interviews/<面试id>/status.json` 的 `job_id`
4. `outcome` 归因数据在岗位记录**内部**（无独立引用）

## 5. 存量修复：体检脚本 + 合并

**形态：命令行脚本 `岗位去重.py`**（与已有的 `报告体检.py` 同风格，**不做界面**）。
理由：这是**一次性维护**（分析前提示已能防止将来再产生），且项目里已有同类的维护脚本先例；
做成界面要多写一整个 tab，收益不匹配。

```
python 岗位去重.py                # 只列疑似重复的岗位对，不改任何东西
python 岗位去重.py --合并 <keep_id> <drop_id>   # 真的合并（先备份，逐个确认）
```

输出要求：每对列出 **两个岗位 id / 两个日期 / 两个分数 / 相似度 / 标题**，
并说明 `keep` 是**时间更早**的那条；**缺 JD 原文的岗位会被跳过并计数**（如实说"跳过了 N 个"）。

### 体检

`find_duplicate_jobs()` → 返回相似对列表：`[{keep, drop, score, both_titles, both_dates, both_scores}]`
（`keep` = 时间更早的那条，作为合并后的身份）

### 合并 `merge_jobs(keep_id, drop_id)`（**只做被确认的合并**）

1. **备份**（`jobs.json` + `knowledge.json` + 每个受影响的 `interviews/<id>/status.json`），
   备份文件名带时间戳，**保留不删**
2. **KB**：把 `from_jds` 里 `id == drop_id` 的项**改为 `keep_id`**；
   若该卡已有 `keep_id` 的项 → **去掉重复项**（不新增第二条）
3. **面试记录**：`job_id == drop_id` → 改为 `keep_id`
4. **`jobs.json`**：drop 记录加 **`merged_into: keep_id`**（**不删除记录、不删除报告**）
5. **互斥**：全程持一把**模块级 `threading.RLock()`**
   （与 `kb._KB_LOCK` 同理；本模块自己一把即可，但**不要绕过 kb 的锁去写 knowledge.json**
   —— 写 KB 那一步通过 `kb` 提供的入口做，或显式持同一把锁）
6. **失败回滚**：任一步失败 → **用第 1 步的备份把已改的文件恢复回去**（三个文件都有备份，可逐一还原）
7. **幂等**：对已合并过的对再调一次 → 直接返回（`drop` 已有 `merged_into` 就跳过）

### 合并后的一致性

- `multi_jd` 重新统计（用户那对合并后，6 个概念应回到「1 个岗位」→ `multi_jd` 变 0）
- **台账/统计里排除 `merged_into` 非空的记录**（列表与筛选都不显示；或显示为"已合并"灰行）
- **报告文件一个都不删**（用户报告是资产）

## 6. 分析前查重

在 `do_analyze` **之前**插入判定（此时**尚未调用模型、尚未消耗搜索额度**）：

| 情况 | 行为 |
|---|---|
| 未命中 | 照常分析 |
| 命中 且 请求带了 `allow_duplicate: true` | 照常**新建**（用户已在提示里选过"新建"） |
| 命中 且 请求带了 `overwrite: <job_id>` | **沿用那个岗位身份**重跑——具体是：**照常跑分析，但结果写回 `overwrite` 指定的那条已有记录**（`job_id` 与报告文件名**不变**，报告内容替换，`score` / `job_title` 等字段更新，**不新建记录**）→ `from_jds` 不会增长 |
| 命中 且 两者都没带 | **不分析**，返回重复信息让前端提示 |

**`overwrite` 的 job_id 必须校验存在**（不存在 → 400），且**必须真的是相似的那一条**
（防止前端传错 id 把结果写到无关岗位上；实现时用 §3 的判定复核一次）。

**返回形态**：HTTP **409** + `{ok: false, duplicate: {job_id, job_title, created_at, score, similarity, suggestions:["overwrite","new"]}}`
（用 409 而不是 200，语义明确、也好测；前端要单独处理这一支。）

**前端弹窗**（两行字说清代价）：
```
这份 JD 你在 10 月 3 日分析过（当时 75 分，相似度 97%）。
  [覆盖它（推荐）]  沿用原来那个岗位，不会再算成第二个岗位
  [仍然新建]        会让「被 N 个岗位提到」把它算两次
```

## 7. 测试

### Python（stdlib `unittest`，继承 `tests/base.py` 的 `IsolatedCase`）

1. **判定**：合成的「长文本 + 它的截断摘抄」→ 包含度 ≥0.85 命中；
   两段无关文本 → 不命中；**用例要复现实测形状**（截断而非前缀、长度差 ~40%）
2. **边界**：空、纯空白、纯标点、<40 字、一侧缺失 JD 原文 → 一律"不重复"
3. **体检**：扫出重复对、`keep` 取更早的那条、缺 JD 原文的岗位被跳过并计数
4. **合并**：KB `from_jds` 归并（含"drop 与 keep 同时存在于同一张卡"→ 去重不新增）；
   面试记录 `job_id` 跟着改；drop 记录加 `merged_into` 且**未删除**；**报告文件仍在**；
   **幂等**（合并两次结果一致）；备份存在
5. **台账过滤**：已合并的记录不出现在列表/统计里
6. **查重路由**：命中 → **409** 且 **模型调用数 0、搜索调用数 0**（在分析之前就返回）；
   `allow_duplicate` 跳过；`overwrite` 沿用原 id（断言新报告文件名 == 旧 id）

### 前端（Node 探针 + 无头 Chrome E2E）

⚠️ 本项目**假绿已累计 11+ 次**，机制含：平局掩盖（3）、错误路径满足断言（1）、
**字符串在 `<script>` 源码里也存在**（2）、通用兜底吃差异（1）、**断言粒度不够**（1）。
**断言必须读元素属性/渲染产物；断言要细到"个体"那一层，别停在"分组"那一层。**

前端只有一件事：**查重弹窗**
- 命中时出现，显示**具体日期与分数**、相似度
- 两个按钮各自的语义：点「覆盖」→ 请求带 `overwrite=<id>`；点「仍然新建」→ 带 `allow_duplicate: true`
- **不命中时绝不出现**（不能恒出现 —— 这是最容易写成恒真的地方）
- 弹窗里的 id/日期/分数**都要过 `esc()`**（它们来自岗位记录）

### 脚本（`岗位去重.py`）

- 无参数运行：**只读**，列出重复对、不写任何文件（断言跑完磁盘指纹未变）
- `--合并` ：先备份、再合并、再打印合并后的 `multi_jd` 变化
- 缺 JD 原文的岗位被跳过并计数

### 反向取证（"改坏看是否变红"）

至少 4 处：① 包含度改成 Jaccard（用户那对会漏）；② 去掉 <40 字门槛；
③ 合并时不改面试记录的 `job_id`；④ 查重命中时仍然照常分析（额度被消耗）。
⚠️ **陈旧字节码陷阱**：改坏前后文件长度相同时先摸 `mtime` 再跑。

## 8. 验收标准

- [ ] 体检能扫出用户那对（相似度 ≈0.965），并列出两个日期与两个分数
- [ ] 合并后：KB 里那 6 个概念的 `from_jds` **各只剩 1 个**（`multi_jd` 从 6 → 0）
- [ ] 合并后**报告文件一个都没少**；被并的岗位记录仍在（带 `merged_into`）
- [ ] 合并**幂等**（再调一次结果不变）
- [ ] 提交同一份 JD → **409 + 提示**，且**模型调用 0、搜索额度 0**
- [ ] 选「覆盖」→ 沿用原岗位 id（`from_jds` 不增长）
- [ ] 选「新建」→ 明确告知后果后照常新建
- [ ] 全部测试通过；**用户真实数据只在你确认后才被改**，且改前有备份

> ⚠️ **操作真实数据的纪律**：验收**先用真实数据的副本在隔离根上跑**；
> 真正对用户数据执行合并**必须单独征求同意**，并先备份。
