# 知识地图缓存（JD 级只算一次）· 设计与实施（阶段 4B）

> 目标：把一次分析里 **87% 的时间 + 全部搜索额度** 从"每份简历都要付"变成"**每个 JD 只付一次**"。

---

## 1. 背景：实测成本构成（用户真实日志）

```
analyze.model_done      {"ms": 32209}                   ← 主分析调用（只看这一份简历时也要跑）
analyze.knowledge_done  {"ms": 206206, "nodes": 53}      ← 知识地图：206 秒、53 次搜索
analyze.success         {"ms": 236186}                   ← 一次分析总计 236 秒
```

**知识地图占 87% 的时间与全部 ~53 次 Tavily 搜索额度，而它是纯 JD 级的**
（"这个岗位要会什么"，与哪份简历无关）。
`knowledge.build_for_jd(jd_text, cfg)` 本来就只吃 JD 文本 —— 缓存它非常自然。

**用户的决策**：只缓存知识地图（拿走 93% 的可省收益，且**模型看到的输入一个字不变**，
零质量风险）。**不拆主调用**（那 7% 不值重构提示词 + 重新验证质量的风险）。

---

## 2. 范围

### 做

- **JD 级事实缓存**：`jds.json` 每条 JD 记录里的 `jd_facts`（A 阶段已预留该字段）
- **知识地图**：JD 第一次分析时算一次并缓存；**同一 JD 之后再分析（换简历/重跑）直接复用**
- **免费播种**：新建/命中一个 JD 时，若它已有分析报告里有 `REPORT_DATA.knowledge` → **直接拿来当缓存**
  （用户现有数据不用重跑）
- **诚实标注**：复用时在报告里写清「知识地图：复用（首次生成于 X）」并把复用事件记进日志
- **强制刷新**：请求里可带 `refresh_jd_facts: true` → 忽略缓存重算（用户想更新时可以）

### 不做

- **不拆主分析调用**（用户已定：那 7% 不值风险）
- 不做简历段的独立缓存（`简历级` 字段本来就每份简历各算一次，没有可复用的东西）

---

## 3. 数据模型

`jds.json` 的 JD 记录新增/填充 `jd_facts`（**只放 JD 级产物**）：

```json
"jd_facts": {
  "knowledge": [ ... ],          // knowledge.build_for_jd 的原始输出（报告里那段知识地图）
  "knowledge_at": "2026-10-03 00:35",   // 首次生成时间（复用时显示给用户看）
  "knowledge_source": "computed | seeded:<报告id>",  // 它是算出来的还是从旧报告播种的
  "seeded_at": "…"
}
```

**为什么缓存 `build_for_jd` 的原始输出、而不是从知识库重建**：
知识库是**跨 JD 累积**的（`sources` 会并入其它岗位的、节点会被合并、`aliases` 会增长）——
拿它重建"这个 JD 当时的视图"已经不是同一份东西了。报告渲染要的是**这份 JD 的稳定快照** ✓。
（知识库那边照旧由 `kb.absorb` 累积，两者用途不同，不是"一件事两处存"。）

## 4. 流程改动（`do_analyze` 里那一处）

现状：

```python
know_nodes = knowledge.build_for_jd(jd_text, cfg)      # 206 秒 + 53 次搜索
d["knowledge"] = know_nodes
```

改成（顺序是契约）：

```
1. 先定 JD 身份（复用已有 JD / 新建）           ← 现有逻辑，不动
2. 读该 JD 的 jd_facts.knowledge
   ├─ 有 且 未要求刷新 → **复用**（0 秒、0 搜索），记录 analyze.knowledge_reused
   └─ 无 或 要求刷新   → ① 先尝试**播种**（从该 JD 已有分析的报告里读 REPORT_DATA.knowledge）
                          ② 播种不到才真算 knowledge.build_for_jd
                          ③ 存进 jd_facts（含 knowledge_at / knowledge_source）
3. d["knowledge"] = 复用或新算的那份
4. 报告里带上来源标记（复用/新算 + 首次生成时间）
```

**播种的边界（别过度）**：只读**该 JD 自己已有分析**的报告；读不出来（文件缺失/坏 JSON）
就静默跳过 → 走真算那条路。**绝不猜、绝不用别的 JD 的知识地图。**

## 5. 测试（stdlib `unittest`，继承 `IsolatedCase`）

### 接口（`jdfacts.py`）

```python
def get(jd_id): ...            # 读该 JD 的 jd_facts（缺失/垃圾 → {}）；岗位不存在 → LookupError
def knowledge_of(jd_id): ...   # 只取缓存的知识地图；没有 → None
def save_knowledge(jd_id, nodes, source): ...
    # 写 jd_facts.knowledge + knowledge_at（首次生成时间，已存在则保留）+ knowledge_source
def seed_from_reports(jd_id): ...
    # 从该 JD 已有分析的报告里读 REPORT_DATA.knowledge 播种。
    # 返回 (ok, source_report_id) 或 (False, None)；读不出来一律静默返回 False（绝不猜）
def resolve(jd_id, jd_text, cfg, refresh=False, builder=None): ...
    # **唯一的编排入口**：缓存 → 播种 → 真算，三级回退。
    # 返回 (nodes, source)；builder 可注入（测试绝不真跑 knowledge）
```

**`resolve` 的顺序是契约**（测试会钉住）：
```
if not refresh and knowledge_of(jd_id):        → 复用（不播种、不算）
if not refresh and seed_from_reports(jd_id):   → 播种（不算）
否则                                            → builder(jd_text, cfg) 真算 → save_knowledge
```

### 用例

1. `jdfacts` 层：读/写/缺字段容错/垃圾类型；`needs_compute(jd_id, refresh)` 的四种组合
2. **复用**：同一 JD 第二次分析 → `knowledge.build_for_jd` **调用次数 0**（注入假实现计数）、
   搜索调用 **0**、报告里的知识地图与第一次**逐字相同**、日志有 `knowledge_reused`
3. **不同 JD 不复用**：另一个 JD 第一次分析 → 仍然真算
4. **播种**：造一个已有分析且报告里有 knowledge 的 JD → 第二次分析复用它，
   且 `knowledge_source == "seeded:<报告id>"`；**不调** `build_for_jd`
5. **播种失败退化**：报告缺失/坏 JSON → 静默走真算那条路（不崩、不静默变空）
6. **强制刷新**：`refresh_jd_facts=True` → 即使有缓存也重算，并更新 `knowledge_at`
7. **报告与日志诚实**：复用与刷新两条路径都要能在报告/日志里看出来

### 反向取证（至少 4 处，贴红，**注明红在哪一行**）
① 忽略缓存每次都重算 → "第二次调用次数 0"那条应变红；
② 复用时不校验 JD（拿别的 JD 的缓存）→ 那条应变红；
③ 播种读不出来时静默返回空 → 那条应变红；
④ 复用了但报告里不标来源（假装是新算的）→ 那条应变红

## 6. 验收标准

- [ ] 同一 JD 第二次分析：**`build_for_jd` 调用 0 次、搜索 0 次**，报告知识地图与第一次逐字相同
- [ ] 报告里能看出知识地图是**复用**还是**新算**（含首次生成时间）
- [ ] 另一个 JD 不会误用别人的缓存
- [ ] 有旧报告的 JD 能**免费播种**（`knowledge_source = seeded:<报告id>`）
- [ ] `refresh_jd_facts` 能强制重算
- [ ] 全部测试通过；真实 `data/` 不被破坏
