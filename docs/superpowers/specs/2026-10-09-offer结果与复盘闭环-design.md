# offer 结果 + 未拿到原因 + 复盘 · 设计文档（阶段 3.5）

> 前置：`2026-10-09-面试记录上传与AI复盘-design.md`（面试复盘已就绪：`interview.py` + `kind="interview"` 报告）
> 这是用户描述的求职闭环的**最后一步**："最后还有一个是否拿到 offer，没拿到的原因是什么，再次进行复盘。"

---

## 1. 目标与背景

### 用户描述的闭环

> "每个岗位 JD 对应一个**面试前报告** → 面试者根据报告调整准备 → 去面试 → **上传面试记录** →
> 程序通过 AI 评估此次面试 → 复盘与准备二面三面 → **最后还有一个是否拿到 offer，没拿到的原因是什么，
> 再次进行复盘。最终要达到一个闭环。**"

前面几步都做完了。本设计做**最后一步**：记录结果 → 归因 → 复盘 → 反哺知识库。

### 已确认的决策

| 决策点 | 用户选择 |
|---|---|
| 下一步做什么 | **E：offer 结果 + 未拿到原因 + 复盘** |
| "原因"从哪来 | **AI 推断 + 你的补充**（你先写，AI 再结合面试复盘归因） |
| 呈现 | **独立的复盘报告**（挂岗位上，与面试复盘同规格） |

### 关键发现：状态词表**已经存在**

`store.py:26` 已有：

```python
STATUSES = ["未投递", "已投", "待回复", "面试中", "已拒", "Offer", "放弃"]
```

岗位记录里也已有嵌套结构 `application: {status, next_followup, notes}`（`app.py` 负责把它扁平化给前端）。
**所以本设计不另造状态体系**，只加"原因"与"AI 归因"。

---

## 2. 范围

### 本轮做

- 岗位台账里记录**结果状态**（复用现有词表）+ **自己写的原因**
- 基于「岗位 JD + 该岗位的面试复盘 + 你写的原因」做 **AI 归因**
- 生成**复盘报告**（HTML，`kind="outcome"`，走已有的"按 kind 选模板"机制）
- 归因里"要补的知识点"→ 手动「➕ 加入知识库」（**不自动建卡**）

### 本轮明确不做

- **跨岗位模式总览**（"你连续 3 次都栽在 Kappa 一致性上"）—— 这是闭环的最大收益，
  但用户现在 6 个岗位、0 场面试，**没有数据可聚合**。等有若干场面试记录后单独一轮做
- F 的大卡片 + 多简历子报告重构（用户已说明是**页面层重做**，单独一轮）

---

## 3. 数据模型

扩展岗位记录里**已有**的 `application`（不新增顶层字段）：

```
application: {
    status,             # 已有：store.STATUSES 里的值
    next_followup,      # 已有
    notes,              # 已有
    outcome_at,         # 新增：何时定的结果（本地时间字符串）
    outcome_reason,     # 新增：**用户自己写的原因** —— AI 绝不覆盖
    outcome_ai          # 新增：AI 归因结果（独立存放）
}
```

**为什么分开存 `outcome_reason` 与 `outcome_ai`**：报告里要**先显示用户写的、再显示标注为
"AI 推断"的部分**。混在一个字段里就再也分不清哪句是人说的、哪句是模型猜的 ——
那会让用户把自己的判断误当成机器的结论。

## 4. AI 归因

### 输入

- 该岗位的：`job_title` / `job_category` / JD 拆解 / 匹配打分 / 硬门槛
- 该岗位的**面试复盘**（若有）：问题清单 / 答砸的知识点 / 考察重点占比
- **用户写的 `outcome_reason`**（若有）
- 该岗位的知识库命中情况（`asked_count` / `last_outcome` / `state`）

### 输出（JSON）

```json
{
  "verdict_summary": "一段总评：这次最可能是输在哪",
  "possible_reasons": [
    {"reason": "…", "evidence": "引用面试复盘或 JD 里的具体依据",
     "confidence": "高|中|低", "controllable": true}
  ],
  "not_controllable": ["HC 取消、薪资不匹配、内部竞争者…"],
  "actions": [
    {"area": "简历|表达|知识|投递策略", "action": "具体到可执行的一句话", "why": "依据"}
  ],
  "to_study": [{"term": "…", "why": "…", "definition": "一句话解释"}],
  "next_time": "同类岗位下次怎么调（投递策略/简历侧重/准备重点）"
}
```

### 硬性要求（写进提示词，也要在验收里检查）

- **每条 `possible_reasons` 必须带 `evidence`**，且要**引用具体内容**（某个问题、某个答砸的点、
  JD 里的某条要求）。**禁止**输出"可能沟通能力不足"这种没有依据的话
- **没有 `evidence` 的条目 → 直接丢弃**（不为它编一段依据，也不留一条没依据的）。
  若全部被丢弃 → 报告里**如实说**"模型没有给出带依据的原因，可以重试"，
  **绝不用一句泛泛而谈填满这一节**
- 无面试复盘时（只有结果、没上传过面试记录）**允许归因，但必须在报告里说明
  "本次没有面试记录，归因只基于 JD 与你写的原因"** —— 不许假装看到了面试过程
- `controllable` 必须逐条标注（可控/不可控分开是这份复盘有没有用的分水岭）

### 同步执行（不做后台任务）

归因是**一次模型调用**（几秒到几十秒），与 JD 分析同量级 → **同步执行**即可，
不需要像转写那样做后台任务。前端在等待期间显示"归因中…"，失败给明确提示 + 可重试。
（对照：转写是 0.9× 音频时长，所以那边必须后台化。）

## 5. 呈现

### 岗位台账

- 每行加「🏁 结果」按钮 → 面板：状态（复用现有词表下拉）+ 原因输入框 + 保存
- 行内显示：状态徽章（已有）+ 复盘状态（如 `已拒 · 已复盘`）
- **只有到终态（已拒 / Offer / 放弃）才允许「🔍 让 AI 归因」**；
  未到终态（未投递 / 已投 / 待回复 / 面试中）时按钮**禁用并说明"还没有结果"**

### 复盘报告

- 新模板 `web/outcome_template.html`（自包含、零依赖，与现有两个模板同风格）
- 报告文件名：**`oc_<岗位id>.html`**（面试复盘用的是 `iv_<面试id>.html`，前缀区分开）
- 报告数据带 `kind="outcome"` → **复用已有的"按 kind 选模板"机制**
  （`app.report_template_for(data)`，写盘与 serve 共用同一份规则）
- 结构：页头（岗位/公司/状态/时间）→ **你写的原因（原样呈现，优先显示）** →
  AI 总评 → 可能原因（带依据与置信度、可控/不可控）→ **具体改进动作** →
  要补的知识点（每个带「➕ 加入知识库」）→ 下次怎么调 → **原始依据**（折叠：面试复盘要点 + JD 要点）
- `esc()` 转义一切模型输出；入库按钮的成功/失败/离线三态与面试复盘报告一致
- 打印友好（`@media print`）

---

## 6. 错误处理

- **归因失败** → 报告不生成，前端明确提示 + 可重试；**用户写的 `outcome_reason` 已在保存时就落盘，不会因归因失败而丢**
- **归因时岗位/面试记录被删** → 静默降级（少喂一块），不崩
- **重复归因** → 允许（结果可能变），但**不重复写知识库**（`to_study` 永远只列、不自动建卡，所以天然幂等）
- **`outcome_reason` 为空** → 允许提交结果，报告里说明"你没有填写原因"

## 7. 测试

### Python（stdlib `unittest`，继承 `tests/base.py` 的 `IsolatedCase`）

1. `application` 新字段的默认值与容错（缺失/垃圾类型）；**`outcome_reason` 不被归因覆盖**
2. 归因：**注入假模型**（绝不真调）；缺段补空默认值；**没有面试复盘时仍能归因且带降级说明**
3. **`possible_reasons` 里缺 `evidence` 的条目被丢弃**；**全部被丢弃时报告如实说明**（不填泛泛之谈）
4. 路由：保存结果（状态非法 → 400；未到终态要求归因 → 400 并说明）、归因、报告 `kind="outcome"`
5. `report_template_for` 对 `kind="outcome"` 选对模板；缺省仍 JD；**老 JD / 面试报告不受影响**

### 前端（Node 探针 + 无头 Chrome E2E）

⚠️ **本项目已抓到 10 次假绿**，其中**同一个坑出现过两次**：
**断言"页面里没有某句文案" —— 但那句话也在 `<script>` 源码里 → 恒真。**
**所以断言必须读「元素状态 / 渲染产物」，不许读「整页 HTML 里有没有这个字符串」。**

- 结果面板：状态下拉来自 `store.STATUSES`；保存后行内徽章更新
- **未到终态时归因按钮禁用且给出理由**（断言 `disabled` 属性，不是文案里有没有"还没有结果"）
- 报告：你写的原因**原样出现**；AI 部分**明确标注**；`esc()` 生效；入库按钮三态
- 归因失败 → 明确提示 + 可用重试 + **不显示成完成**

### 反向取证（"改坏看是否变红"）

至少 4 处：① 未到终态也允许归因；② `outcome_reason` 被 AI 覆盖；
③ `kind="outcome"` 选成 JD 模板；④ 归因失败仍画成完成。
⚠️ **陈旧字节码陷阱**：改坏前后文件长度相同时先摸 `mtime` 再跑
（否则"还原后仍红"，会把**正确测试误判成坏的** —— 本轮已踩过）。

## 8. 验收标准

- [ ] 台账里能选状态并写原因，**刷新/重开程序后仍在**
- [ ] **自己写的原因在报告里原样出现**，且**不会被 AI 的归因覆盖**（重复归因也不覆盖）
- [ ] 未到终态时归因按钮**禁用**并说明原因
- [ ] 有面试复盘时，归因的每条原因**都引用了具体依据**；没有面试复盘时**明确说明降级**
- [ ] 报告 `kind="outcome"` 走对模板；**老 JD 报告与面试复盘报告不受影响**（三条各测一次）
- [ ] 归因里的知识点**不自动进知识库**；点「➕ 加入知识库」后才进，状态「待学习」
- [ ] 归因失败：明确报错、可重试、**不显示成完成**
- [ ] 全部测试通过；用户真实 `data/`（`knowledge.json` 271,307 字节 / 97 卡、`jobs.json`、
  日志、报告）不被破坏
