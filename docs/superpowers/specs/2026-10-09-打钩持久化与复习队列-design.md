## 1. 目标与背景

### 用户报的问题（原话）

> "每次关掉程序会导致打的钩消失，能否做到每次我的打钩都能够被记录？"

### 实证的根因

报告里的勾选状态**只存在浏览器 `localStorage`** 里（`web/report_template.html:183`
`const SKEY = 'report_state:' + RID`），而 `localStorage` 是**按「协议 + 主机 + 端口」隔离**的。
报告里其实有**四类**勾选框，全都如此：

| 键前缀 | 含义 | 位置 |
|---|---|---|
| `know:<节点id>` | 知识点的「已掌握」 | `report_template.html:407` |
| `gate:<i>` | 硬门槛核对 | `:748` |
| `iq:<i>` | 面试问题准备 | `:835` |
| `cl:<i>` | 重点清单 | `:852` |

所以下面任何一条都会让用户"打的钩消失"：

- 用 `file://` 双击打开报告（Chrome 经常根本不持久化 file:// 的 localStorage）
- 换了端口启动（`python app.py --port 8001` → 换了 origin）
- `localhost` 与 `127.0.0.1` 混用
- 浏览器清理过站点数据
- 重新分析生成了 `xxx(2).html`（换了 `RID` → 换了 `SKEY`）

**而知识库 tab 的状态是存服务端的（`knowledge.json`），它不丢。** 同一件事两个地方存、
一个丢一个不丢 —— 这本身就是设计缺陷。本设计把它统一。

### 用户已确认的需求决策

| 决策点 | 用户选择 |
|---|---|
| 先做哪一块 | **打钩持久化 + 复习队列**（不是先做面试记录 AI 分析） |
| 复习节奏 | **优先级队列**（实时算优先级，不排日期；不做 Leitner 间隔重复） |
| 复习交互 | **翻卡自测**（先只显示术语 → 看答案 → 答上了/没答上） |
| 打钩范围 | **聚焦报告自己的重点内容**（不是让报告变成浏览全部 97 张卡的入口） |
| 大卡片重构 | 同意拆分方案，但**本轮不做**，单独一轮（见附录 A） |

## 3. A. 打钩持久化

### 3.1 核心决定：`know:` 的勾就是知识库那张卡的 `state`

「报告里勾了『已掌握』」与「知识库 tab 里标『已掌握』」是**同一件事**，所以**只存一处**：
知识库节点的 `state` 字段。

- **勾上** → `state = 已掌握`
- **取消勾** → `state = 待学习`
- `学习中` 无法从报告的二态勾选框表达（它由知识库 tab 或自测会话设置）；
  报告里 `学习中` 与 `待学习` **都渲染为未勾选**（诚实：你没说已掌握）

这样报告与知识库永不打架，且**复习队列能直接用上报告里的勾**。

### 3.2 其余三类勾：报告专属进度

`gate:` / `iq:` / `cl:` 是本报告专属的进度，存：

```
data/profiles/<profile>/report_state/<报告id>.json
{ "version": 1, "report_id": "20261008_语音文本评测_72分", "checks": { "gate:0": true, "cl:3": true } }
```

- **报告 id 必须过 `store.safe_name()`**（它来自客户端，不校验就是路径穿越漏洞）
- 每份报告一个文件 → 避免单文件无限增长与写竞争

### 3.3 报告如何找到自己的知识库卡片（不需要重新生成报告）

报告里的节点 id 是**模型生成的**（如 `ellipsis_resolution`），与知识库的**归一化 id**（`省略恢复`）不同。

**不要求重新生成已有报告**：报告打开时把自己的**术语列表**发给服务端，
由服务端用**同一个 `kb.normalize_id`** 做映射 —— 归一化规则只有**一份实现**（在 Python 侧），
不会出现 JS/Python 两份规则漂移。

> **两个节点归一化后撞车时**（同一份报告里「Transformer 架构」与「transformer架构」）：
> 它们会**共用同一个状态** —— 这正是对的（同一个概念只有一份掌握度），不需要特殊处理。

### 3.4 术语在知识库里还没有卡片时：自动建卡

勾选一个知识库里不存在的概念 → **自动建一张卡片**，而不是报错或静默丢弃。
理由：**用户的勾绝不能丢**；而且"报告里出现过的概念"本来就该进知识库。

为了不让建出来的卡是空壳，**报告的写请求要带上它能提供的字段**：
`definition` / `plain_explanation` / `category`。这样新建的卡在知识库 tab 里
有定义可看，而不是一张只有术语的「待查证」空卡。

### 3.5 降级：服务不可达时

（`file://` 打开报告、或服务没开）

- 继续用 `localStorage` 缓存，**功能不残**
- 页面顶部显示**明确提示**：「⚠️ 未连接到工具，本次打钩只存在这个浏览器里」
- **不假装存好了** —— 这是本设计的诚实底线

## 4. B. 复习队列 + 翻卡自测

### 4.1 新增字段（现有 97 张卡自动补默认值，无需迁移脚本）

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `review_count` | int | `0` | 被自测过几次 |
| `last_reviewed_at` | str | `""` | 上次自测日期 `YYYY-MM-DD` |
| `last_result` | str | `""` | 上次结果：`答上了` / `没答上` / `""` |

`ensure_kb` 负责补默认值并容错（非 int → `_as_int`，非 str → `""`）。

### 4.2 优先级公式（实时算，透明可解释）

```
状态权重:  待学习 = 3 · 学习中 = 2 · 已掌握 = 1
age      = min(距上次复习天数, 30)        # 从没复习过 → 30
score    = 状态权重 × (1 + 被多少个岗位提到) × (1 + age / 7)
```

排序：`score` 降序；同分按 `(term)` 升序保证确定性。

UI 必须**显示排序理由**（如「待学习 · 被 2 个岗位提到 · 21 天没复习」），
让用户能理解"为什么这张排前面"——黑箱排序会让人不信任它。

### 4.3 翻卡自测流程

1. 知识库 tab 点「🎯 开始自测」→ 前端拉 `GET /api/knowledge/review?limit=N`
2. **只显示术语**（逼自己先回想），下方有「看答案」按钮
3. 点「看答案」→ 展开：专业定义、通俗解释、来源链接、来源岗位
4. 点「✅ 答上了」或「❌ 没答上」→ 立即 POST 落盘 → **自动递下一张**
5. 顶部：进度（`第 7 / 20 张`）+ 剩余张数；答完显示本轮小结（答上 N / 没答上 M）
6. **随时可以退出**：每答一张就落盘，退出再进会重算队列（已推进的状态自然让它往后排）

### 4.4 状态推进规则

| 结果 | 状态变化 |
|---|---|
| **答上了** | → `已掌握` |
| **没答上** | **退一档**：`已掌握 → 学习中`、`学习中 → 待学习`、`待学习 → 待学习`（不变） |

两种情况都：`review_count += 1`、`last_reviewed_at = 今天`、`last_result = 结果`。

## 5. API（**4 条新增**，另有 2 条复用已有）

| 方法 | 路径 | 请求 | 响应 |
|---|---|---|---|
| POST | `/api/report_state/read` | `{report_id, terms:[...]}` | `{ok, checks:{键:bool}, know:{术语:状态}}` |
| POST | `/api/report_state/write` | `{report_id, checks:{键:bool}, know:{术语:{state, definition?, plain_explanation?, category?}}}` | `{ok, saved:int, created:int}` |
| GET | `/api/knowledge/review` | `?limit=20` | `{ok, queue:[节点+score+reason], stats:{due, mastered, reviewed_today}}` |
| POST | `/api/knowledge/review` | `{id, result}` | `{ok, node}` |
| *(复用)* | `GET /api/knowledge` | — | 知识库 tab 的列表/筛选/统计（已有） |
| *(复用)* | `POST /api/knowledge/state` | `{id, state}` | 知识库 tab 的状态切换（已有） |

**`/api/report_state/write` 的 `know` 分支走 UPSERT**（不存在则用请求里带的
`definition` / `plain_explanation` / `category` 建卡），`created` 告诉前端新建了几张。
`know` 的值也**允许退化成一个纯字符串**（如 `"已掌握"`），此时建卡只带术语 —— 便于老模板与调试。

**`report_id` 一律先过 `store.safe_name()`**；结果为空（空串 / `..` / 含分隔符）→ 400，不写盘。

**`GET /api/knowledge/review` 的 `due`** = 队列里 `limit` 之内的张数（即"这轮要看的"），
`reviewed_today` = `last_reviewed_at` 等于今天的卡片数。

## 6. 错误处理

- **服务端写盘**：复用阶段 3.1 已建立的 `_KB_LOCK`（RLock）+ `store.write_json` 原子写。
  `report_state` 的写也要走同一把锁（同一进程内的文件写互斥）。
- **`report_state` 文件损坏**：`read` 返回空 `checks` 并记 warn，**不崩**；**不在读到坏文件时覆盖它**
  （沿用知识库 `_quarantine_corrupt_kb` 的失败方向：宁可这次不保存，也不清空用户积累）。
- **自测落盘失败**：前端**不推进本地状态**并提示「未记录，请重试」——
  **绝不出现"UI 显示已记住但服务端没写"**。
- **报告读不到状态**：降级 `localStorage` + 明确提示（见 3.5）。
- **`report_id` 非法**（空、`..`、含路径分隔符）：`safe_name` 后为空 → 返回 400，不写盘。

## 7. 测试

### 7.1 Python（stdlib `unittest`，继承 `tests/base.py` 的 `IsolatedCase`）

`kb.py` / `store.py` 新增逻辑全部 TDD：

1. `review_queue` 排序：待学习优先于已掌握；被多岗位提到者优先；久未复习者优先；同分按术语稳定
2. `record_review`：「答上了」→ `已掌握`；「没答上」逐档退（三种起始状态各一条）
3. `record_review` 累加 `review_count`、更新 `last_reviewed_at` / `last_result`
4. **UPSERT**：`know` 写入一个知识库里不存在的术语 → 建卡成功且 `state` 正确
5. 新字段默认值与容错（缺失/`None`/字符串数字/垃圾类型）
6. `report_state` 读写往返；**损坏文件不被覆盖**；`report_id` 路径穿越被拒
7. 并发：review 写入与知识库合并同时发生**不丢更新**（复用已有并发测试的形态）

### 7.2 前端（本项目**无 JS 测试设施**，如实认账 —— 用 Node 探针）

- 报告：勾选 → 发写请求；失联 → 降级 `localStorage` 且**出现提示**；`know` 勾选正确映射三态
- 自测：翻卡流程（未翻面时答案不出现）、答上/没答上分别 POST 什么、
  **落盘失败时不推进本地状态**、进度计数正确

**关键不变量照样用「把实现改坏，看测试会不会红」验证** —— 这是阶段 3.1 学到的教训
（本期共抓到 6 次"假绿"测试）。

## 8. 验收标准

- [ ] 在报告里勾选知识点 → **关掉程序、重开、重新打开报告** → 勾还在
- [ ] 在报告里勾选 → 切到知识库 tab → 那张卡显示「已掌握」（**同一件事，两处一致**）
- [ ] 在知识库 tab 标「学习中」→ 回到报告 → 该知识点**未勾选**（诚实：没说已掌握）
- [ ] 勾选一个知识库里没有的概念 → **自动建卡**，勾不丢
- [ ] 用 `file://` 打开报告 → 出现**明确提示**说未连接工具，勾仍能用（存本地）
- [ ] 知识库 tab 点「🎯 开始自测」→ 只看到术语 → 点「看答案」才展开答案
- [ ] 答上 → 状态变「已掌握」；没答上 → 退一档；都能在知识库 tab 立刻看到
- [ ] 自测中途关掉程序 → 重开后**已答的记录还在**（每答一张就落盘）
- [ ] 自测界面显示**排序理由**
- [ ] 全部测试通过；用户真实 `knowledge.json` 的 97 张卡不被破坏（只增字段）
- [ ] 断网/服务停 → 自测明确报错，**不假装记住**

## 附录 A：F（大卡片 + 多简历子报告）的拆分结论

**本轮不做，但决策已定，下一轮直接用。**

用户原话：
> "做成大卡片（显示共同内容），卡片下面有针对这一个岗位JD，多个简历和这个岗位生成的独立报告。
> 这里需要讨论下哪些需要细分卡片报告中，哪些放进大卡片即可。"

### A.1 拆分（已与用户确认）

**大卡片 = 岗位级（换简历不用重看）**

| 模块 | 为什么是岗位级 |
|---|---|
| ★ 岗位信息与联系方式 | 公司/HR/电话/地址，与简历无关 |
| 03 JD 拆解 | 纯 JD 内容 |
| 📚 知识学习地图 | "这个岗位要会什么"，**与简历无关**；且「已掌握」是**用户级**掌握度 |

**子报告 = 简历 × 岗位（每份简历一份）**

| 模块 | 为什么是简历级 |
|---|---|
| 01 硬门槛 | 判定"你**是否符合**"依赖简历 |
| 02 匹配打分 + 总分 | 简历 vs JD |
| 04 简历大纲 | 基于你的经历 |
| 05 简历优化方向 | 针对你的简历 |
| 06 面试准备 | 围绕**你**的背景会怎么被问 + 答案骨架 |
| 投递 checklist + 状态 | 每次投递一条 |

### A.2 一个关键结论（它让 A+B 可以先行）

**知识点的「已掌握」是用户级的**（同一概念在不同岗位是同一张卡），
所以它天然归在**大卡片**的知识地图下，**无论 F 怎么重构，它的位置都不会变**
→ 本轮的 A（打钩持久化）配的存储方案**不会被 F 推翻**。

### A.3 F 的真实代价（下一轮要单独出规格）

- `jobs.json` 结构要变：一个岗位挂多份报告
- 报告数据要**拆成两份**（岗位级 / 简历级），分析管线分两段生成
- 岗位台账的展示要重做
- **已有 6 份报告要迁移**（老结构）
