# 知识库（Knowledge Base）· 阶段 3.1 设计文档

> 所属总设计：`2026-09-19-知识学习地图-design.md` 的「阶段 3」
> 本文只覆盖阶段 3 的**第一刀**：**自动沉淀 + 🧠 知识库 tab 浏览**。
> 批量建库、复习队列/面试反哺、模型自动归并同义词留给 3.2 / 3.3。

---

## 1. 目标与背景

### 要解决的问题

阶段 1/2 之后，知识点只活在**各自报告的 JSON 快照**里。后果：

- 同一个概念在 5 个岗位里出现过 5 次，你就要在 5 份报告里分别看 5 遍；
- 没法回答「**哪些概念是这批岗位的刚需**」——恰恰是"被多少个岗位提到过"这个信号最有价值；
- 学过的概念没有统一去处，无法推进掌握度。

### 用户已确认的用途（决定一切设计取舍）

> **刷题式复习：把概念当卡片反复看、推进掌握度。**
> 一个概念 = 一张卡，跨岗位把来源累加；"被几个岗位提到过"就是重要程度信号。

### 用户明确强调的硬性要求

> **知识库必须完整保存卡片视图里的信息，`sources`（来源）尤其关键。**
> 不能只存术语和定义，否则来源信息会在跨 JD 合并时丢失；知识库里必须能直接点进原文。

## 2. 数据模型

存储：`data/profiles/<key>/knowledge.json`（沿用 profile 隔离；`store.py` 已有 `knowledge_path/load_knowledge/save_knowledge` 骨架）。

```json
{
  "version": 1,
  "nodes": [
    {
      "id": "省略恢复",
      "term": "省略恢复",
      "aliases": [],
      "definition": "……",
      "plain_explanation": "……",
      "category": "NLP",
      "layer": 0,
      "sources": [{ "title": "", "url": "", "date": "", "accessed": "", "snippet": "" }],
      "timeline": [{ "year": "", "text": "" }],
      "related": [{ "id": "", "relation": "" }],
      "interview_questions": ["……"],
      "confidence": "verified",
      "from_jds": [{ "id": "", "job_title": "", "company": "", "date": "" }],
      "state": "待学习",
      "last_outcome": "未面试",
      "asked_count": 0,
      "first_seen": "2026-10-08",
      "last_seen": "2026-10-08"
    }
  ]
}
```

### 2.1 身份口径

`id = normalize_id(term)`，规范化：**小写 → 去空白 → 去标点（中英文标点、全角半角统一）**，保留 CJK 与字母数字。

- 于是「Transformer 架构」与「transformer架构」是**同一张卡**；
- `term` 保留**首次看到**的写法用于显示（稳定、不churn）；
- 报告里模型生成的 id（如 `ellipsis_resolution`）是**报告局部**的，进知识库时一律按 `normalize_id(term)` 重新定身份。

### 2.2 合并规则（确定性、幂等、零模型调用）

| 字段 | 规则 | 理由 |
|---|---|---|
| `sources` | 按 **URL** 并集去重；同 URL 保留 date/snippet 更全的一条 | 来源累积是核心价值 |
| `sources[].snippet` | **截断到 400 字**（完整摘要仍在报告快照里，URL 是原始出处） | Tavily snippet 实测可长到 1400+ 字，跨岗位累积会膨胀到数 MB |
| `timeline` | 保留**条数更多**的；相等则保留原有 | 更全的历史 |
| `definition` / `plain_explanation` | **不用更短的值覆盖现有非空值** | 保留更全的；不因后来的岗位而退化 |
| `layer` | 取 **min**（0=核心） | 在任何岗位是核心概念 → 就是核心 |
| `category` | 保留首个非空 | 避免无意义抖动 |
| `related` | 按 `id` 并集（同 id 保留首个 relation） | 关系累积 |
| `interview_questions` | 并集去重，**上限 8** | 防无限膨胀 |
| `confidence` | 由合并后的 `sources` **重算**（有来源即 `verified`） | 来源累积后置信度应提升 |
| `from_jds` | 按 `job_id` 追加去重 | 驱动「被 N 个岗位提到」 |
| `aliases` | 手动合并时记录被并入的其它写法 | 可追溯、可撤销 |
| `first_seen` / `last_seen` | 首次/最近一次被吸收的日期 | 排序用 |
| **`state` / `last_outcome` / `asked_count`** | **绝不覆盖**，`asked_count` 只增 | **用户进度神圣**：合并方向永远是「你的操作 → 库」，绝不「库 → 覆盖你」 |

**字段容错**：历史数据里 `sources[]` 可能缺 `snippet`（旧报告只存了 title/url/date/accessed），
`date` 也可能为空 —— 合并与展示都必须容忍缺失，**不得因此丢整条来源**。
`timeline` / `related` / `interview_questions` 若非 list，按空处理（沿用 `knowledge.py` 的韧性风格）。

## 3. 模块边界

新增 **`kb.py`**，与生成管线 `knowledge.py` **职责分离、互不依赖**：

| 模块 | 职责 | 依赖 |
|---|---|---|
| `knowledge.py` | **从 JD 生成知识**（拆解 → 头脑风暴 → 校验来源 → 时间线） | `llm` / `search` |
| `kb.py`（新） | **跨 JD 累积与复习**（合并、查询、统计、疑似重复、回填） | `store`（纯数据，不调模型不调搜索） |

`kb.py` **不调用模型、不调用搜索**——它只做确定性的数据运算，因此可以完全离线、可测、零额度。

### 3.1 接入点

`app.py` 的 `do_analyze` 在 `render_report(d)` **之后**：

```python
try:
    added, merged = kb.absorb(know_nodes, job_meta)
    log.log_event("kb.absorb_done", added=added, merged=merged, total=len(know_nodes))
except Exception as e:
    # 知识库失败绝不影响出报告（沿用现有知识管线同样的容错风格）
    log.log_exc("kb.absorb_error", e)
```

## 4. 回填已有报告

动作：从 `reports/*.html` 的 `const REPORT_DATA = ` 里提取 `knowledge`，逐份吸收进知识库。

- **纯本地、零 API 额度**；
- **幂等**：`from_jds` 按 report_id 去重，重复执行不重复计数；
- 定位用 `json.JSONDecoder().raw_decode()`（比正则可靠，JS 后续代码里也有 `}`）；
- 提供 UI 按钮「从已有报告导入」，并可由 CLI 调用一次。

用户当前 6 份报告中，只有 `20261008_语音文本评测_72分.html` 带来源（53 节点 / 127 条来源），
其余为 `ai-generated` 无来源 —— 回填后应能真实反映这一点。

## 5. UI：🧠 知识库 tab

在 `web/index.html` 的 `<nav>` 加 `data-tab="know"` 按钮 + `#p-know` section（现有 tab 机制：`nav button[data-tab]` ↔ `#p-<tab>`）。

布局为**主从（master-detail）**：

- **顶部工具条**：统计（`N 个概念 · M 个有来源 · K 个已掌握`）+ 搜索框 + 筛选（掌握状态 / 分类 / 来源岗位）+ 排序（被提到次数 ↓ / 最近出现 ↓ / 术语）
- **左列表**：每条 = 术语 + 徽章（`来源 3` / `被 2 个岗位提到` / 状态色）
- **右详情**：专业定义、通俗解释、前世今生时间线、**来源链接（`target="_blank"` 可点开原文）**、关联概念、面试会怎么问、状态切换（待学习／学习中／已掌握）
- **「疑似重复」整理区**：启发式列出可能同一概念的术语对，每对一个「合并」按钮

### 5.1 疑似重复启发式（确定性，零模型调用）

两个术语 `a`、`b` 判为"疑似同一概念"，满足任一：

1. 去标点小写后**一方包含另一方**且长度差 ≤ 4（如「省略恢复」⊂「省略识别及恢复」）；
2. 去掉常见后缀词（`体系/机制/方法/流程/策略/规范/标准/系统`）后**完全相同**；
3. 共有前缀 ≥ 4 个字符 **且** 共有后缀 ≥ 2 个字符 **且** 两者长度都 ≥ 6
   —— 加长度门槛是因为短术语（4 字以内）极易共享首尾字，会产生大量假配对淹没界面。

只**提示**，绝不自动合并——避免错并（用户已确认走"精确匹配 + 提示 + 手动合并"路线）。
提示区按"相似度"降序、**上限 20 对**，避免刷屏。

## 6. API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/knowledge` | 返回 `{nodes, stats}`；`stats` = 总数 / 有来源数 / 各状态数 / 被多岗位提到的数量 |
| POST | `/api/knowledge/state` | `{id, state}` 切换掌握状态（**只改 state，不碰别的**） |
| POST | `/api/knowledge/merge` | `{keep_id, drop_id}` 手动合并（被合并方记入 `aliases` 后移除） |
| POST | `/api/knowledge/import-reports` | 回填已有报告，返回 `{files, nodes_added, nodes_merged}` |

不做 `DELETE`（本轮 YAGNI；误操作可用备份恢复，且知识库文件在 profile 目录里）。

## 7. 错误处理

- `kb.absorb` 任何异常 → 只记日志，**绝不影响报告生成**（最坏情况是这次知识没沉淀）
- `knowledge.json` 损坏/非预期结构 → `load_knowledge` 返回 `{"nodes": []}` 并 warn 日志，**不崩**
- 报告 HTML 读不出 `REPORT_DATA`（旧格式/被改过）→ 跳过该份并计数，**不中断回填**
- 手动合并 `keep_id == drop_id` 或 id 不存在 → 返回明确错误信息，**不写入**
- 术语为空/仅标点 → `normalize_id` 返回空串，**跳过该节点**（不产生垃圾卡）

## 8. 测试

新增 `tests/test_kb.py`（stdlib `unittest`，继承 `_Isolated` 以隔离真实 `data/`）：

1. `normalize_id`：大小写/空白/标点/全角半角归一；空与纯标点 → `""`
2. 合并：新术语 → `added`；同术语 → `merged`
3. **来源按 URL 去重累积**；同 URL 保留更全的一条
4. **`state` 不被覆盖**（关键回归：先设 `已掌握`，再 absorb 同术语，state 必须仍是 `已掌握`）
5. `asked_count` 只增不减
6. `timeline` 取条数更多的
7. `definition` 不用更短的值覆盖
8. `layer` 取 min
9. `related` / `interview_questions` 并集 + 面试题上限 8
10. `from_jds` 按 job_id 去重（**幂等**）
11. `confidence` 随来源累积重算
12. 疑似重复启发式：正例（省略恢复 / 省略识别及恢复）+ 反例（Transformer 架构 / 抽样检验）
13. `absorb` 容错：传入畸形节点（非 dict、缺 term、sources 非 list）不抛异常
14. 回填：伪造报告 HTML → 正确提取并吸收；坏 HTML 被跳过
15. `load_knowledge` 遇到损坏 JSON → 返回空结构不崩

## 9. 明确不做（YAGNI）

- 批量建库（3.2）
- 复习队列、面试反哺闭环、`asked_count` 自动增长（3.3）
- 模型自动归并同义词（用户已否决：有额度成本且错并难发现）
- 跨 profile 共享知识库（与 profile 隔离设计冲突）
- 知识库的删除/编辑单个节点（先观察真实使用再说）
