## 2026-10-08 · 阶段 2.2：列表位置记忆 + 搜索领域约束

- 背景（用户反馈）：

     非 AI 领域的知识**这是绝对不可以出现的**，而且这会**浪费大量的搜索 tavily 额度**"

### 问题 1 · 列表视图位置记忆
- `state.listScroll` 记录 `.klist` 的 `scrollTop`，`state.lastKnow` 记住最后打开的条目
- 点条目时**先存位置再切视图**（切完 DOM 就没了，顺序不能反）
- 切回列表时恢复位置；`.klist` 上用 `box.__bound` 守卫只绑一次 scroll 监听
  （**内存即时更新 + 250ms 节流落盘**——否则滚动时每秒几十次 localStorage 同步写会卡）
- 上次打开的条目加 `.last` 琥珀色高亮；无历史位置时 `scrollIntoView({block:'center'})` 兜底
- 用遍历 `[data-kopen2]` 比对 id，而不是拼接属性选择器（规避 id 含引号时的注入）
- 验证：无头 Chrome + CDP 21 项断言全过（滚到底 2875px → 点最后一条 → 切回仍是 2875px 且高亮在可视区；刷新后也恢复）

### 问题 2 · 搜索来源跑偏（根因 = 查询没有领域锚定）
- **根因**：`attach_sources` 的查询就是 `n["term"] + " 是什么"`，**没有任何领域限定**；
  且搜回来的结果**不做相关性校验**就直接当来源用。歧义术语必然跑偏。
- **实测影响面**（只读扫描用户现有 6 份报告）：最新那份 53 节点 / **159 条来源，其中 30 条（18.9%）非 AI 领域**。
  铁证：「省略恢复」→`基础：恢复和重做操作 | Microsoft Support`；
  「Transformer 架构」→`What is a Transformer?（电力变压器，plcblog.in）`；
  「裁决权限」→司法部/美国最高法院；「升级路径」→`Windows 版本升级 | Microsoft Learn`
- **修复**（三层）：
  1. `build_query()`：查询锚定领域 → `"{term} 大模型 AI"`
  2. `filter_relevant()`：结果必须命中 `DOMAIN_KEYWORDS`，否则丢弃；全被丢弃 → `ai-generated` + `sources=[]`
     （守住"无来源绝不编造"，**宁可不给来源，也不给错来源**）
  3. `max_searches`（默认 40，可配置）：核心节点 layer 0 优先，超出不发起搜索 → 直接省额度
- 关键决策：**先锚定查询（治本），再用过滤兜底（治标）**。 ~~只做过滤会把额度浪费在注定被丢的坏查询上。~~
  ⚠️ **这条决策当天即被实测推翻，见下方「修正」——最终是"查询不动、过滤做唯一护栏"。留在这里作为反面记录。**
- 踩坑 1：过滤词表**只放中文会误杀正确的英文来源**——实测 `Transformer (deep learning)`
  （en.wikipedia）因标题无中文关键词被丢 → 补 `machine learning` / `deep learning` / `transformer` /
  `neural` / `language model` 等英文词，误杀从 30 降到 26
- 踩坑 2：**纯 ASCII 短词会子串误命中**——`"ai"` 命中 `available` / `email` / `retail`；
  `"rag"` 命中 `storage` / `paragraph` → 对所有 ≤4 字母的纯 ASCII 关键词统一加词边界
  （`(?<![a-z])kw(?![a-z])`），中文字符不受影响（「AI标注」仍命中）
- 踩坑 3：补词后又发现「自然语言处理」「强化学习」**在中文下无任何关键词命中**（`nlp`/`reinforcement`
  是英文），会被误杀 → 补 `自然语言` / `强化学习` / `多模态` / `大语言模型` / `openai` / `gpt` 等
- 踩坑 4：改动让旧测试 `test_attach_sources_marks_verified` 失败——夹具来源 `title="T"` 无领域关键词，
  被新过滤丢弃。**修夹具（换成真实感的「大模型数据标注规范 / 语料标注流程」）而不是放宽断言**
- 新增「临界丢弃」审查：人工逐条复核 30 条被丢来源，确认方向正确；
  其中 6 条属"临界"（医学 Kappa 统计、软件回归测试、大数据用户画像标签）——
  它们确实**不属于 AI 领域**，按"宁缺毋滥"丢弃是对的，代价是节点降级为待查证

### ⚠️ 修正（同日）：**上面第 1 条 `build_query` 领域锚定已被实测证伪，已撤销**
（详见 `docs/superpowers/plans/2026-10-08-知识学习地图-阶段2.2.md` 的「阶段 2.2 修正（Task 2.3）」整节）
- 实测：5 个真实术语 × 2 种写法、10 次真实 Tavily 搜索，指标 =「既切题（字面含术语）又属本领域」：
  `{t} 是什么` **8/15** vs `{t} 大模型 AI` **5/15**（「省略恢复」3→0、「抽样检验」1→0）
- 机理：查询带「大模型 AI」时，Tavily 返回泛 AI 页面（「15款大模型透明度测评」），与术语无关；
  过滤**只验领域、不验切题** → 这类页面会通过过滤被标成「有来源」，**比 Microsoft 那条更危险**
- 因此 `build_query()` 改回 `"%s 是什么"`、删除 `DOMAIN_TAG`；护栏全部交给 `filter_relevant()`
- 同时把 `filter_relevant()` 升级为**强/弱关键词 + 否决词**（修 `transformer` 同名漏洞：
  电力变压器丢、`Transformer (deep learning)` 留），`max_results` 3→5（按请求计费，多拿候选纯赚）

### 新增：`报告体检.py`（零成本维护历史报告）
- 代码修好后**已生成的报告仍带旧来源**，重新分析要花钱花额度，而过滤是纯本地计算
- `python 报告体检.py` 只体检；`--fix` 清理非本领域来源；`--刷新模板` 用新模板重渲染
  （两者都会先整目录备份；`--刷新模板` 只换骨架、`REPORT_DATA` 原样保留）
- **为什么需要"刷新模板"**：报告是**快照**，模板改了旧报告不会自动更新。
  列表位置记忆这类纯前端改动要作用到已有报告，就得重新注入一次 `REPORT_DATA`——零额度成本
- `--fix` 只删判定为非本领域的来源，**绝不新增来源、绝不编造**；来源被清空的节点降级为 `ai-generated`
- 安全前置验证：最终规则下有 4 个节点（「抽样检验」「错误类型学」「裁决权限」「影响面评估」）
  会被清空全部来源，**而这 4 个节点的时间线都是 0 条**
  → 清空它们不影响全报告 130 条时间线中的任何一条，方案安全
- 用 `json.JSONDecoder().raw_decode()` 定位 REPORT_DATA，比正则可靠（JS 后续代码里也有 `}`）

## 2026-10-09 · 阶段 3.2：打钩持久化（服务端）+ 🎯 翻卡自测复习队列
- 类型：`功能` + `修复` + `决策`
- 目标：修掉用户报的「关掉程序再开，报告里的勾就没了」；顺手把知识库做成能翻卡自测的复习队列

### 根因（用户报的 bug）
- 报告里的勾选**只写 `localStorage`**（`web/report_template.html` 的 `SKEY = 'report_state:' + RID`），
  而 `localStorage` 是**按「协议 + 主机 + 端口」隔离**的 → 用 `file://` 双击打开报告、换个端口（8000→8001）、
  清一次站点数据，勾全丢
- 真正致命的是**同一件事被存了两份**：报告里 `know:` 的「已掌握」勾在浏览器，
  而知识库 tab 的掌握度（`state`）在服务端 `knowledge.json` → 所以「知识库显示已掌握、报告里却没勾」
  这种自相矛盾迟早出现。用户体感就是「知识库里的进度还在，报告的勾没了」
- 四类勾选框全在报告里：`know:`（知识点）/ `gate:`（硬门槛）/ `iq:`（面试题）/ `cl:`（重点清单）

### 关键决策
- **`know:` 的勾与知识库 `state` 统一（同一件事只存一处）**：勾上 = 已掌握，取消 = 待学习；
  「学习中」与「待学习」都渲染成未勾选（**你没说已掌握，就不给你打勾**）。
  「掌握度是用户级的」这一点让它天然只有一份真相
- 另外三类（`gate:` / `iq:` / `cl:`）存服务端 `data/profiles/<key>/report_state/<报告id>.json`（一份报告一个文件，避免单文件无限增长与写竞争）
- **身份口径复用唯一实现**：卡片 id = `kb.normalize_id(term)`，服务端做映射，前端不再写第二套归一化规则。
  核实过：真实 97 张卡的 `id` 与 `normalize_id(term)` **逐张相等** → 报告只要把**术语列表**发上去就能找回自己的卡
  （报告节点自带的模型生成 id 不参与映射）
- 知识库里没有这个概念 → **自动建卡**（把报告能提供的 definition / plain_explanation / category 一并写进去，
  不是空壳）；宁可多一张卡，也不能丢用户的勾
- 复习优先级 = `状态权重 × (1 + 被多少岗位提到) × (1 + 久未复习天数/7)`（权重 待学习3/学习中2/已掌握1，
  age 上限 30 天），**全乘性**（任何一维为 0 都不会把分数压成 0）；排序理由**显示在界面上**（黑箱排序没人信）
- 答辩推进：答上 → 直接「已掌握」；没答上 → **退一档**（已掌握→学习中→待学习，待学习留在原地）

### 诚实原则（写进实现，不只是口号）
- **失联时降级本地但明确告示**：`file://` / 工具没启动 → 顶部告示条「未连接到工具，本次打钩只存在这个浏览器里」，
  底部提示也改成真话「保存在本机浏览器」；**绝不假装存好**
- **写失败回滚勾选框**：提示「没存上，勾选已还原（未同步到工具）」
- **服务挂掉时自测不推进**：提示「未记录，请重试」，停在当前卡（实测点击后 `KB_RV.i` 不变、`busy=false`）
- 「重置我的勾选」只清本机缓存（服务端没有删除路由），**确认文案改成真话**

### 实测到的假绿（本期抓到）
- `ReviewQueueTest` 的排序断言**在权重全 1 时依然全绿**：两张卡同分，平局由术语升序决定，
  而「学习中」恰好排在「已掌握」前面 → 把权重改成全 1（等于删掉「状态权重」这一维）测试照样通过
- 补了一条**对照测试**（让「已掌握」的术语排在前面）才把这个断言钉住
  —— 教训：**排序测试里的「平局」是假绿高发区**，对照组必须让被测维度真正决定顺序

### ⚠️ 方法论陷阱（踩到、已写进计划）
- 做「把实现改坏，看测试变不变红」时，**如果改坏前后文件长度不变**（`3/2/1` → `1/1/1` 都是单字符数字），
  Python 判 `.pyc` 是否过期用的是 `(mtime, size)`：两个都没变 → **复用 `__pycache__` 里的旧字节码**，
  于是「把原文还原后测试仍然是红的」，很容易把**好测试**误判成坏的、去改一个本来正确的断言
- 判据：**还原之后仍然红，第一反应不该是「测试写错了」，而是「我读到的是不是旧字节码」**；
  改完先摸一下 mtime（或改成会变长度的写法、或跑前先 `touch` 一次）

### 为什么复用 vidkit，而不是自己写转写
- 本机已有 `video-link-extractor`（`vidkit`）：faster-whisper + 领域词库 + `models/medium` 都就绪，
  转写是它已经调通并实测过的能力
- 本项目**零第三方依赖**（Python 3.13 仅标准库）是硬约束：把 faster-whisper / CTranslate2 引进来 =
  几十个依赖 + 模型下载 + 打包体积，与"零依赖可分享"的定位冲突
- 走**子进程调它的 venv + 它的模块**，而不是调它的 CLI：CLI 的 `transcribe` 输出是**纯文本（时间戳全丢）**，
  我们需要**带时间戳的完整 JSON**（报告里的「原始转写全文」要正文，`duration`/`language` 要给报告表头）。
  于是 `python -c "from vidkit import transcribe; print(json.dumps(...))"`，并把 `cwd` 设成 vidkit 目录
  （让它的 `models/` 相对路径生效）
- 代价（诚实）：多了一个**外部依赖**和"用户得先有 vidkit"的门槛 → 所以配了自动探测同级目录 +
  `vidkit_dir` 配置项 + 缺失时**可操作的报错**（缺目录 / 缺 `.venv` 是两句话，用户要做的事不同）

  加入知识库 / 新词不会自动建卡 / window.print()」标记**与转写正文**；`GET /reports/iv_<id>.html` → 200
- 结论：**第一次真跑就通过**，子进程调用写对了

### 0.9× 音频时长 → 决定了"必须后台任务 + 状态落盘"
- vidkit 自己的实测（2026-09-10 测试报告）：**683.2 秒音频 → 613.488 秒，实时系数 0.898**（含领域预扫与模型加载）
- 但那次是 `domain` **自动识别成「通用」**（没启用领域词库）。我们固定 `domain='ai'` = **83 个热词**，
  真机复测明显更慢：**60 秒片段 86.3 / 116.2 / 140.8 秒（1.4～2.35×）**，同一片段 `domain='none'` 只要 21.4 秒（0.36×）
- 所以规格 §5 定的界面系数 `TRANSCRIBE_RATE = 0.9` 对"带领域词库"这条路是**偏乐观**的：
  30 分钟录音真实可能要 **40～60 分钟**，不是 27 分钟。**本轮没改**（规格钉了 0.9，且它只用于"预计"提示，
  不是承诺），但如实记在这里，交给后续决定
- 另一个观察（未改动、仅记录）：同一个 60 秒片段、同一参数，两次跑出 **15 段 / 160 字** 与 **1 段 / 71 字**
  两种结果（int8 + 多线程 + 热词的非确定性；该片段内容是八字命理，与 `ai` 提示词**不同域**）。
  domain 合适的 `daily.wav` 三次结果**完全一致** → 硬编码 `domain='ai'` 是"对 AI 面试内容最合适"的取舍，
  但不是对任何录音都合适
- 结论：**必须是后台任务 + 状态落盘**。`status()` 的判据是「文件里停在 transcribing/analyzing
  **但没有活动线程**」→ 重启后显示"上次被中断，可重试"，而不是永远转圈；
  重试见到 `transcript.json` 就跳过转写（实测：把 runner 换成"一调用就抛"的实现，重试后仍 `done`，
  `transcript.json` 的 sha256 一字未变）

### 「被问过」为什么用确定性匹配，而不是让模型判
`kb.interview_hits(text)`：知识库里每个**术语**是否出现在转写里（≥3 字出现即命中；2 字词要出现 ≥3 次，
因为"模型""标注"在口语里遍地都是）。理由：
- **可测**：一条纯函数，测试能钉住每种边界；交给模型就成了"不可测、看运气"
- **零额度**：不用为"找出被问过的词"再花一次模型调用
- **不会漏记**：模型漏读一个术语就漏记一次复习优先级，而且**没人会发现**

### 两个只有真 socket 才能发现的缺陷（计划里的沙箱测试结构上不可能发现）
1. **`rfile.read(256KB)` 在 socket 上会阻塞到凑满或对端关闭** → 上传**永远卡死**。
   计划的沙箱用例用 `BytesIO` 当 `rfile`，`BytesIO.read(256*1024)` 有多少给多少、立刻返回 ——
   阻塞这种"套接字语义"在 `BytesIO` 上根本不存在。修法：`ContentLengthReader` 按 `Content-Length`
   精确限量读、兼容 EOF，并补了**真 socket + 真 `http.client`** 的回归测试
2. **客户端中途断开被当正常结束** → **半截录音当上传成功**。`ContentLengthReader` 拿不到声明的字节数
   就返回 EOF，`save_stream` 只当正常结束。修法：`written != length` → 400「上传中断：只收到 X/Y 字节」
   + 清理半截文件。本轮验收用真 socket 复现：声明 1000 字节只发 12 字节 →
   `{"ok": false, "error": "上传中断：只收到 12/1000 字节，请重新上传"}`，目录里没有留下半截文件
- 教训：**换掉 `rfile` 的测试替你验的只是"协议之上"的逻辑**；凡是依赖"读多少、什么时候 EOF、
  对端还在不在"的行为，必须拿真 socket 验一次

### 一次真实数据误写事故与根因
- 现象：跑测试时**用户真实 data 根**被写进了面试记录/日志
- 根因：`store.DATA_ROOT` / `log.LOG_FILE` 是**模块级全局**，测试隔离靠"改全局 + `addCleanup` 还原"，
  而**后台线程的生命周期不受测试控制** —— 上传用例把 `interview.start` 换成真实现（或实现被改坏、
  漏了 413 判断继续往下走）时会**真起一条流水线线程**，它在路径还原**之后**才跑完，于是写进真实根
- 加固：凡碰上传路由的用例，**一律先调 `_no_external_calls()`**（换掉 `interview.start` 与
  `interview.ffprobe_duration`），哪怕那条路径"按理说走不到 start"
- 本轮验收遵守同一条：**只调同步的 `run_pipeline`，绝不用 `start()` 起线程**；跑完复核
  `data/` 仍是 **42 个文件**、`knowledge.json` 指纹未变、真实目录里没有 `interviews/`
- 通用教训：**"隔离"要靠"没有线程活过还原点"，不能靠"我记得还原"**

### 假绿（本轮抓到 4 次，本项目累计计数 → 9 次）
1. 计划里的 `unquote` 断言：`unquote("中文名")` **恒等** → 去掉 `unquote` 照样绿。

### 一处诚实的设计取舍

## 2026-10-12 · offer 结果 + 未拿到原因 + 复盘（阶段 3.5，闭环收口）

- 类型：`功能` + `决策` + `问题`
- 背景 / 目标：用户描述的求职闭环**最后一步** ——「最后还有一个是否拿到 offer，没拿到的原因是什么，
  再次进行复盘。最终要达到一个闭环。」
- 做了什么：
  - 岗位台账记录**结果状态**（复用 `store.STATUSES`）+ **你自己写的原因**（`outcome_reason`）
  - 到**终态**（已拒 / Offer / 放弃）后才允许 AI 归因；归因结果**单独存** `outcome_ai`
  - 复盘报告 `oc_<岗位id>.html`（`kind="outcome"` → 复用既有的「按 kind 选模板」机制，写盘与 serve 同一份规则）
  - 归因里的知识点**只列不建卡**，点「➕ 加入知识库」才进库（状态「待学习」）
- 提交：`87bc30c` `46371b8`（`outcome.py`）、`8b8be5d`（3 条路由 + `outcome_template.html`）、
  `a0bb53d`（台账「🏁 结果」面板 + 「🔍 让 AI 归因」入口）

### 为什么不另造状态词表
`store.py` 里**早就有** `STATUSES = ["未投递","已投","待回复","面试中","已拒","Offer","放弃"]`，
台账行内徽章、按状态筛选、`/api/jobs/update` 读写的全是它。所以本轮只加了 `TERMINAL = ("已拒","Offer","放弃")`
——它**只是 `STATUSES` 的子集**，不是第二套词表（有一条专测 `test_terminal_is_a_subset_of_the_existing_statuses` 钉住）。
另造一套的代价是「同一件事两处各说各话」：面板里存「已拒」、台账里还显示「未投递」。
**决策：复用已有词表，前端也绝不硬编码**（状态下拉与终态判据都从接口回，探针 A1 断言 7 个 option 全来自接口）。

### 为什么 `outcome_reason`（你写的）与 `outcome_ai`（机器推的）分开存
报告里要**先原样显示你写的、再显示标注为「AI 推断」的部分**。混在一个字段里，就再也分不清
哪句是人说的、哪句是模型猜的 —— 那会让人**把自己的判断误当成机器的结论**。
`save_result` 只写 `status` / `outcome_reason` / `outcome_at`；`attribute` 只写 `outcome_ai`；
`outcome_reason` 连 `outcome_ai` 的键都不是。验收里专门让假模型在回复里塞
`{"outcome_reason":"AI 编的原因","status":"Offer"}` 并**重复归因两次** → 用户原话一字未变、
状态也没被改成 Offer（见下「本轮验收」）。

### 为什么没有 `evidence` 的原因要丢弃
提示词里明写「每条 `possible_reasons` 必须带 `evidence`，且要引用具体内容；禁止『可能沟通能力不足』这种话」，
但模型仍然会给没依据的条目（验收里 4 条给了 1 条空的）。
`_normalise_outcome` 的做法是**直接丢弃**，并把「一条都没剩下」标成 `reasons_all_dropped` →
报告如实说「模型这次没有给出带依据的原因，可以重试……不做归因也好过给你一堆放之四海皆准的废话」。
**宁可这一节空着并说明，也不替它编一段依据、也不用泛泛之谈填满。**
同一类错误还有「可控性」：见下「`controllable` 的三态」。

### 为什么把「路由」与「模板」合成一个任务（上一轮「单独不是绿的提交」是计划缺陷）
上一轮把「路由」和「模板」拆成两个任务，结果造出一个**单独不是绿的提交**：路由测试要断「用的是哪个模板」
的标记，而模板要到下一个任务才存在 —— 那个提交本身跑不通，事后还得解释「下一个提交才绿」。
**这是计划缺陷，不是实现问题。**本计划把两者合并成一个任务，
所以 `8b8be5d`（3 条路由 + `web/outcome_template.html` + 报告标题）**自己就是绿的**。

### 计划作者写错的数据形状：岗位记录其实是**扁平**的
规格初稿写的是「岗位记录里有嵌套 `application: {status, next_followup, notes}`」，
并据此设计了读写。实现时去核对**真实** `jobs.json` 才发现：`status` / `notes` 都在**顶层**，
**没有任何一条记录有 `application` 键**（验收时我复核了一遍真实数据：6 条记录，`application` 键数 = 0）。
实现者没有照错的写，而是去查了真实数据。修法（写进规格 §3）：
**写的时候两处都写（扁平为准），读的时候扁平优先、嵌套兜底** ——
这样既不会有「面板存了已拒、台账仍显示未投递」，也不会在老记录上凭空归零。
反向的坑也钉了一条用例：`application.status="已拒"` 而顶层说「面试中」→ **以顶层为准**，绝不误开归因。

### 终态门槛从「宽松」改成「严格」的经过
计划里的测试**自相矛盾**：`NeverRecordedGateTest` 要求「没记过状态的岗位也要拦」，
而 `EvidenceFilterTest` 的 helper `_job()` 不写状态却要求归因成功 —— 严格实现会让
**计划自带的 9 条用例 error**。实现者带着**实测证据**来问（而不是猜），最后裁定**严格版**，
理由是：宽松版会给一个「从未记录过结果」的岗位写出「你为什么没拿到 offer」——
**没有依据却言之凿凿**，正是本设计要防的那一类错误。
拦住的体验反而正确：看到「还没有结果」→ 去记录结果 → 再复盘，这就是「先记结果，再复盘」的顺序。
计划文档随后同步（`5913bab docs(plan): sync Task 1 test snippet with the strict terminal gate`）。
验收复核：从没记过结果 / 记过非终态 / 状态是垃圾类型（`5`）**三种都 400**，
且**一次模型调用都没发**（`_llm_calls.jsonl` 增量 = 0）。

### `controllable` 的三态：模型漏给时是 `None`（未判断），**不默认成「可控」**
`_as_bool` 读不出来就返回 `None`。默认 `True` 等于**在没有依据的情况下宣称「这事你能控制」** ——
与「没有 evidence 的原因要丢弃」是同一类错误。报告模板把 `None` 单列成
「❔ 未判断的原因（模型没有标注可控性）」并附一句「不是『可控』」。
（对照测试：显式标了就必须原样保留，否则「永远返回 None」也能蒙过。）

### 一起「改动丢失」事故：永远不要用 `git checkout` 还原一个**还没提交**的"改坏"
反向取证时实现者用 `git checkout -- app.py` 去还原「改坏」的版本，但**那份改动还没提交 → 全部丢失**。
它按编辑历史重建，用**双重证据**自证等价：① 与事故前备份的 **sha256 一致**；② 测试结果**逐字相同**。
此后一律改成**先备份文件**再改坏/还原。
本轮验收沿用这条纪律：4 处反向取证都是「读原始**字节** → 存备份 → 精确字符串替换 → 跑 → **原样写回字节**
→ 校验 sha256 与改坏前一致」，4 处全部字节级还原成功（`app.py` `a5e2085f72ad66dc…`、`outcome.py` `46d2260b7b668c91…`、
`index.html` `6e8a1f8d2eb56fd6…`）。

### 探针自身的假绿（本项目累计 11+ 次）
1. **断言粒度不够**：探针只断言了「分组头 + 三桶分类」，**没断言「每条原因自己那颗标签」** →
   把 `null` 混进「可控」那一桶时，探针 **59/59 全绿**漏过。
   **教训：断言要读到「个体」那一层，别停在「分组」那一层。**
   本轮验收就按这个口径写：单独渲染每条原因（`reasonBlock`），读**它自己那颗 pill** 的文案
   （`controllable=true → 可控` / `false → 不可控` / `null → 未判断`）。
2. **textarea 是 RCDATA**：拿「往 `textarea` 里放 `<img onerror>`，看它有没有生成元素」去证明 `esc()` 生效
   是**白测** —— RCDATA 里本来就不会生成元素。改用「**脏标题**」才有效（本轮读 `#ocTitle.innerHTML`：
   没有真的 `<img>`、原文以 `&lt;img` 保留）。验收里我特意把「脏原因进 textarea 保持原样」这条标成
   **对照说明**、注明它**不算** `esc` 的证据。
3. 我自己写这两个探针时也踩了两次同类假绿，如实记下：

### 根因：岗位身份 = 报告文件名（嵌了日期 + 分数）

原来的身份就是报告文件名 —— `20261003_语音文本评测_75分.html`，里面**嵌了日期与分数**。
于是「换一份简历重新分析同一份 JD」**必然**产生一个新身份：同一个岗位在系统里裂成两个。
后果不是「显示难看」，而是**算错**：知识库 `from_jds` 把同一份 JD 的两次分析记成两个岗位 →
`multi_jd`（「被 N 个岗位提到」）虚高，而它是**复习优先级的乘性因子**。
真实数据实测（阶段 3.6）：**6 个概念的 `multi_jd` 全部来自同一份 JD 的两次分析**。
3.6 用模糊指纹做了补救（**治标**），本阶段把**身份本身**改对（**治本**）。

### 用户提出的解法

**给 JD 稳定的结构化 ID**（`本科_金沙人力_数据标注质检_视频_成都_6-8K_0001`），
身份与「哪一次分析、哪一份简历、几分」彻底解耦。**顺带落地了「一个大块页面下挂多份简历小报告」**：
台账一行 = 一个 JD，大卡片上是 JD 身份串 + N 份分析 + 最高分，展开看每一份。
**同一份 JD 被分析两次而变成两个岗位，从此从结构上不可能**（不再依赖事后判重）。

### ID 的字段现在就有 → 不需要改提示词

| ID 字段 | 现有来源（`REPORT_DATA` 里本来就有） |
|---|---|
| 学历 / 单位 / 职责 / 城市 / 薪资 | `education` / `company` / `job_category` / `location`(`address`) / `salary` |
| 领域 | **没有现成字段** → 关键词规则（语音/文本/视频/图片/多模态/Agent）推不出就 `【未知领域】` |

所以**提示词一个字都没改**：`jdid.derive_fields(REPORT_DATA)` 直接派生。
只有「领域」这一段的规则是新增的（在 `jdid.py` 里，不是让模型多说一个字段 —— 改提示词要重跑、
要模型配合，而这是**纯本地可测**的）。

### 为什么分隔符用 `_`

**因为薪资里本身就有 `-`**：`13-26K`。用 `-` 拼出来的 ID 根本分不清字段边界
（`13-26K-0001` 是薪资+编号，还是薪资就是 `13-26K-0001`？）。

### 为什么 JD 级字段必须**整体**搬走

`status` / `company` / `salary` / `title` 这些字段如果两边各留一份，就是本项目**反复栽的同一个坑**
（「同一件事两处各存一份」）。所以本阶段的**分界是硬的**：

- **JD 级**（投递状态 / 结果 / 公司 / 薪资 / 地址 / JD 原文）**只住** `jds.json`
- **分析级**（分数 / 简历 / 报告文件 / 时间）**只住** `jobs.json`，靠 `jd_id` 挂上去
- 覆盖是在 `_analysis_fields()` 那一层做的：`jobs.json` 里出现 JD 级字段就说明分界漏了

**迁移时 `derive_fields` 会丢掉原始表述**：`6-8K（入职五险，提及一金7k+）` → `6-8K`、
`四川金沙人力资源开发管理有限公司（金沙人力）` → `金沙人力`。所以定了一条**分界**：
**JD 记录里存原始值（人看的），ID 里用归一化值（身份用的）**，并且**有断言钉住这条分界**
（迁移后 `jds.json.salary == "6-8K（一金7k+）"` 而 ID 段是 `6-8K`）。
把归一化值当展示值用，用户在台账里就再也看不到「一金 7k+」这条谈薪信息了。

### 公司名归一化：来回五轮，每一轮都是拿**真实数据**试出来的

这是本轮**最有价值的一条经验**（`f56f16c` `8e53372` `cd51dc6` `2e04c0e`）：

1. **我规格里的「非法字符白名单」会把用户的真实公司名与薪资判非法**
   （`四川金沙人力资源开发管理有限公司（金沙人力）` 里的全角括号）→ **自动生成的 ID 存不进自己的库**，
   接线当天就会在真实数据上崩。修法：`validate_id` 的判据从「白名单」改成
   **「`build_id` 清洗后是否原样」** —— `build_id` 生成什么，校验就必须接受什么。
2. **量了 ID 长度：70 字符**，当文件名根本没法用 —— 我的规格**漏写了「要归一化」**。

3. **按长度截断会切出半个「有限公司」**（`…开发管理有限`）→ 改成**先剥法定后缀再截断**。
4. **`阿里巴巴（中国）有限公司` 与 `腾讯（中国）有限公司` 都归成「中国」→ 撞 ID**。

5. **裸限定词形态（`阿里巴巴（中国）`，没有「有限公司」）同一个 bug 还在** ——

**教训：测试全绿 + 规格写完，都不等于在真实数据上能用。每一步都要拿真实数据跑一遍。**

## 2026-10-12 · 知识地图按岗位缓存：换简历不再重烧搜索额度（阶段 4B）

### 成本构成是**量出来的**，不是估的

一次真实分析的日志（用户机器）：

```

analyze.knowledge_done  {"ms": 206206, "nodes": 53}
analyze.success         {"ms": 236186}
```

**206,206 / 236,186 = 87.3%**，而且 `knowledge.build_for_jd(jd_text, cfg)` 本来就**只吃 JD 文本** ——

### 用户的决策过程：给了两个方案，用户选了 A

| 方案 | 收益 | 代价 |
|---|---|---|
| **A：只缓存知识地图** | 拿走 **93% 的可省收益**（87/93），模型看到的输入**一个字都不变** | 无（零质量风险） |

### 三级回退，以及「播种」是为**老数据**设计的

```
① jd_facts.knowledge 有 → 复用（0 秒 0 搜索）
② 没有 → 从该 JD **自己**已有分析的报告里读 REPORT_DATA.knowledge → 播种（0 秒 0 搜索）
③ 都没有 → builder(jd_text, cfg) 真算一次 → 存进 jd_facts（下次就是①）
```

**「播种」不是为新流程设计的，是为已经躺在盘上的老报告设计的**：那些报告的 `REPORT_DATA` 里
**本来就带着那份知识地图**（它当时真算过），不拿来用就得为同一份 JD 再烧一遍 53 次搜索。
播种的边界是硬的：只读 `jdid.analyses_of(jd_id)` 里**该 JD 自己**的分析；
读不出来（文件缺失 / 坏 JSON / 没有 REPORT_DATA）**静默退回真算** —— **绝不猜、绝不用别的 JD 的。**

### 为什么缓存 `build_for_jd` 的**原始输出**，而不是从知识库重建

知识库（`knowledge.json`）是**跨 JD 累积**的：`kb.absorb` 会把**别的岗位**的 `sources` 并进同一条卡、
把节点**合并**、让 `aliases` 继续增长。拿它重建「这个 JD 当时的视图」，重建出来的**已经不是同一份快照**了。
报告渲染要的是**这份 JD 的稳定快照** → 缓存 `build_for_jd` 的原始输出。
（知识库那边照旧由 `kb.absorb` 累积，两者用途不同，**不是「一件事两处各存一份」**。）

### ⚠️ 一个**未核实的前提**被独立审查者纠正

父 agent 在任务书里写过一句（当作交接事实）：「`jdfacts.save_knowledge` 把异常捕获了」
（暗示写缓存失败会被静默吞掉）。审查者去查代码后**否掉了它**：
`jdfacts.py` **全模块只有一处 `try/except`，包的是「读报告」**（`_seed` 里那处）；
**写路径一处都不吞异常**，`store.write_json` 是**原子写**且失败必 `raise`
（`save_knowledge` / `_store` 里没有任何 `except`）。

**教训：不要把「看起来合理」的转述当事实用。** 一句听起来合理的交接前提，
如果没人去代码里核对过，它就会以「已知事实」的身份进入下一轮设计 ——
而这条会直接决定「写失败要不要补守卫」这种实现选择。

### 第 13 种假绿（新）：Node 模板探针切错了脚本段

模板那一行的渲染验证用一个 **Node 探针**真跑模板里的 JS。第一版探针按
「**最后一个 `<script>`**」去找模板脚本 —— 但报告里注入数据的那一行
（`const REPORT_DATA = {…}`）**本身就在同一个 `<script>` 里**，按标签找会切错段落：
切到了**数据段**，于是一个模板函数都没跑。表现是「**老报告那条绿**（它本来就该不显示那一行）、
其它全红」—— 看起来像「模板没写那一行」，**其实整个功能根本没被执行**。

- 修法：探针改成按**数据行的锚点**（`const REPORT_DATA = `）定位，取它所在的那个 `<script>`。
- 它还有个并发的坑：模板以 `boot()` 结尾（async：先 `await` 服务端状态再 `render()`）→
  读一次恒空（同样是假红）→ 必须**反复让出事件循环**等渲染完。
- **如果当时把「老报告不显示那一行」当成通过就收工，就会把「整行功能没被执行」漏过去。**
  **教训：断言通过的原因必须是「事情做对了」，不能是「什么都没发生」。**

### 并发测试怎么避免「因串行执行而恒绿」

第一版并发测试靠 `sleep` 猜「第二个线程已经在等了」→ 换成 **`Event` 证明**，
而且刻意把**前置状态**也钉住：先跑一次把该 JD 的知识地图**算成空的**
（空列表既不算可用缓存、也播种不出东西）→ 于是并发那两个请求**必然**走到 ③ 真算那一步。

- 断言 1：`waiting` 事件被置上 = 第二个线程**真的进了单飞等待**（不是各算一遍、也不是串行跑完）
- 断言 2：`calls == ["first"]` = **只有一个线程进了 builder**
- **退化成串行会怎样**：第二个请求那时会走**缓存分支** → 盘上有缓存、`waiting` 事件为 0 →
  **这条直接红**（它测的正是「等待者拿到了领导者的结果」而不是「反正最后有缓存」）。

### 一条「报告要说真话」的口径裁定：等待者按**复用**报

并发等待者一度被报成「本次新算」（它确实参与了那次真算的结果）。**父 agent 裁定改成「复用」**：
报告里那一行小字的**全部意义**是「**本次有没有重新搜索**」（模板原文就是这么写的），
而等待者**确实没有重新搜索** —— 它只是在旁边等领导者的那一次。
写「本次新算」会让用户**以为又烧了约 53 次搜索额度**，而那正是这一行要传达的信息。
（「这是等待者、不是缓存命中」由日志事件 `analyze.knowledge_joined` 分辨，报告不承担这个区分。）

### 严格真值口径：`bool("false")` 为真 → 手写 API 会**意外重算 206 秒**

HTTP body 里的布尔值写成字符串是常态（`"false"` / `"0"`），而 `bool("false") is True` ——
一句 `{"refresh_jd_facts": "false"}` 会**白烧一次 206 秒 + 约 53 次搜索**；
`{"allow_duplicate": "false"}` 会**悄悄跳过查重**（本该 409）。

- **先写「现状钉住」测试**：`assertTrue(app._as_bool("false"))` —— 把**改前**行为钉住，
  这样改完能一眼看出「哪一类值真的翻面了」，而不是「测试跟着实现改」。
- 最终只有**字符串假值**这一类翻面：`""` / `"0"` / `"false"` / `"no"`（含大小写与空白变体）；
  而 `"maybe"` / `2` / `[1]` **保持原语义**（`2` 从真改成假同样是行为变化，既有语义不能悄悄翻面）。
- 注释里写死了它**不是** `outcome._as_bool`：那个是**三态**解析（读不出来＝`None`「未判断」），
  两者契约不同，**绝不合并**（合并必然改掉一边的语义）。

### 孤儿 JD 善后，以及一处**刻意保留**的缺口

知识地图缓存要有个挂靠点，所以 `do_analyze` 在「定下 JD 身份」之后**先落一条只有 id 的 JD 记录**。
如果异常落在这之后、报告之前，盘上就留下一条孤儿：`jds.json` 里只有 `id/seq/created_at/updated_at/id_history`
—— **台账里看不见它**（台账的行来自 `jobs.json`），但 `_similar_saved_jd` 会通过盘上那份 `<id>.txt` 命中它
（similarity 1.0）→ 用户重提同一份 JD 只会拿到 **409**，而前端**没有** `allow_duplicate` 出口。

- 善后：只删**「本次这次调用刚建」且「没有 `jd_facts`」且「没有分析挂在它下面」**的那一条，
  **只删 `jds.json` 里的记录、绝不删任何文件**（用户贴过的原文照旧留在 `jd/` 下），并记 `analyze.jd_orphan_cleaned`。
- **刻意保留的缺口**：孤儿判据要求「**无 `jd_facts` 且无分析**」。若**知识地图已算成功、而写记录那一步炸了**，
  记录上已经有 `jd_facts` → 按裁定**不删**。
  代价（如实）：一个**极窄窗口**下重提同一份 JD 仍会 **409**，且前端暂无出口。
  理由（代价不对称）：删它就**白丢一次 206 秒算出来的知识地图缓存**，而留它只是「换个新身份再分析一次」。
- **该缺口会在下一阶段自动消失**：下一阶段把查重粒度改成 **JD × 简历**，并给真正重复的情况一个**前端出口**
  （用户可以选「仍然新建」）—— 那时 409 不再是死路，这个缺口自然不存在了。

### 验收措辞的一条硬事实：**播种只对已跑过 `身份迁移.py` 的岗位生效**

`jdid.analyses_of` **只认 `jd_id`**，而用户真实的 `jobs.json` 是 **6 条 / 0 个 `jd_id`**、

| 保存简历 | **截断覆盖**（非原子） | `POST /api/resumes` → `store.write_text` |
| 删除简历 | `os.remove` **永久删、无副本** | `DELETE /api/resumes` |
| 报告里能不能找到"当时那份简历" | **完全不能**：报告**不嵌简历原文** —— 20 行抽检 **0/20 命中**；`resumes/` 也没有下载路由 | `REPORT_DATA` 里没有 `resume` / `resume_id` 键 |

| **查重** | ⚠️ **只看 JD 文本** → 同一个 JD 换**第二份**简历被判重复（409），**而前端全仓没有 `allow_duplicate` / `overwrite` 入口** | `find_analyze_duplicate`；`web/index.html` |

**最后一条是"卡死用户"级别的**：用户 C 阶段的核心用法正是「**几份简历比同一个岗位**」——
他换个简历再点分析，只会拿到一句"重复"，而且没有任何按钮能继续。

### 用户 5 条决策（本阶段的全部设计依据）

| # | 决策点 | 用户选择 |
|---|---|---|
| 1 | 删简历 | **「移出列表」**（母版快照保留）+ 另给「彻底删」入口（二次确认） |
| 2 | 「子简历」含义 | **母** = 从多份里「**选定继续优化**」的那份；**子** = 母的修改版；"选定"是个**新动作** |
| 3 | 多份比对 | 加一张 **6 维度并排表**（不做报告文字 diff） |
| 4 | 每个族谱在磁盘留几份内容 | **2 份：母版 + 最新版**；其余版本**只留元数据与 AI 变更说明** |
| 5 | 变更说明 | 上传子简历时**和母版比对，AI 写出"改了哪些地方"** |

**由 #4 直接推出的诚实边界（写进了界面与 README，不美化）**：
**旧版原文不保留** —— 历史版只能看「改了哪些（AI 写的）+ 那一版当时的分数」，**取不回原文**。
这是**用户明确选的取舍**（不是实现者省空间）：他要在"磁盘上最多两份内容文件"与"每一版都能取回"之间选，
选了前者。所以取回历史版时界面**明确说「旧版原文未保留」**，**不是**一个空文件、也**不是**假装能取回。

### 快照的**唯一触发条件**与「一经生成即不可变」

> **当且仅当**「母版的内容 == 此刻 `<名字>.md` 的内容」**且**它即将被覆盖时，
> 才先把它复制到 `resumes/快照/<母版id>.md`。**已存在就不重写**。

推论：族谱 `母(v1) → 子(v2) → 孙(v3)` 里，v2 生成时已把 v1 留成快照；
v3 生成时 `<名字>.md` 里是 v2、母版是 v1（快照已在）→ **不产生新快照、也不重写 v1 的快照**。
「不可变」是它能当**参照原点**的前提：如果每次延续都重写，它记的就成了"上一次覆盖前的内容"，
不再是"母版原文"。另有一条防写歪：**延续必须沿用族谱的名字** —— 换了名字，
"即将被覆盖的 `<名字>.md`"就不是母亲那一份，条件永远不成立（`resumelib.create_version` 直接报错）。

快照**不是**无条件写的还有一层：母版原文读出来是 `missing`（没保留）/ `mismatch`（与记录 sha 不符）时
**不写快照** —— 拿空串或"被程序外改过的内容"当母版原文存进不可变快照，就是**假装留了档**。

> **【Task 1.8 / 1.9 / 1.10 更正】** 上面这段（含本节开头的「**当且仅当**母版内容 == 盘上内容」）
> 记的是**当时（Task 1.1 那一轮）的口径，已被推翻**；原文**故意留着不改**，免得篡改历史记录。
> 现在生效的口径见 `resumelib.py` 模块开头与 design 文档 §3。被推翻的正是这两条：
> 1. **"与记录不符就不写"是错的（这句话当年还写进了界面）**。Task 1.8 改成**按字节留**：
>    只要盘上有字节、而盘上那份**就是这一版的原文**，`mismatch`（程序外改过 / 非 UTF-8 读不出来）时
>    **字节照样存** —— 那是用户写的东西，覆盖掉就没地方找了；但**不记 `mother_file`**、
>    不声称它是母版原文，界面如实提示「内容与记录不符」（**存档 ≠ 冒充**）。
>    **不留**只有两种（Task 1.10 第 3 条把主语说清，免得被读成无条件的）：
>    ① 这一版原文**从来没保留过**（`missing`）；② 盘上那份**已经不是这一版**的原文
>    （快照已经是好的 / 快照与盘上那份都不是这一版）—— 那时存进来就是张冠李戴。
>    （老实现用文本读：非 UTF-8 解码失败 → 0 字节"假存档"，CRLF → 被归一成 LF，
>    两种都与原文不逐字节相等。现改成 `store.read_bytes`。）
> 2. **"已存在就不重写"补了一条「按记录判断」的例外**（Task 1.9）：**按记录判断**快照装的不是这一版
>    （记录 `sha256` 与快照内容不符）、而盘上那份**恰好就是** → 修正快照。
>    不加它，坏字节会**永久占位**（盘上与记录一致了 `read_version` 还喊 `mismatch`，真原文再也补不进去）。
>    记录**没有** `sha256` 时**没有依据 → 一个字节都不动**。
>    ⚠️ 这条例外的**证明力全在记录里**：记录被人工改坏（把 `sha256` 改成盘上那份）时它会指错 ——
>    所以 Task 1.10 第 2 条起，**覆盖旧快照前先把旧快照改名留档**
>    （`<id>.md.stale-<旧字节 sha 前 8 位>`：不删除、也不冒充母版），
>    否则真快照会被**不可逆**地覆盖掉（复查实测）。
> 3. Task 1.9 修了读侧一句假话：快照**有字节却读不出来**（非 UTF-8）时，原来会变成
>    "`mother` + 空串"（界面显示一份**空简历**）；现在如实报 `mismatch`。
>    **Task 1.10 第 1 条**把这道闸补全：记录里**没有** `sha256` 时也**不许**转头去认
>    `<名字>.md` 里那份**别人的内容**（那会以 `latest` 报给用户）；而"`<名字>.md` 自己有字节
>    却读不出来"时同样不是 `latest` + 空文本，而是 `mismatch` —— **"读不出来"永远不等于"文件是空的"**。
>    合法边界照旧：0 字节 / 纯空白的快照（1.8 之前的实现真能写出 0 字节）是**合法空档** →
>    `mother` + 空文本，不是 `mismatch`（判据是**原始字节** `strip()` 后是否为空）。

### 反复出现的假绿 / 假红（本轮新增的实例，都是实测抓到并改掉的）

1. **「同一份 JD 换简历」那条 409 是死路** —— 旧实现只看 JD 文本判重，前端又没有出口：
   这不是"测试没覆盖"，是**功能上真的走不通**。粒度改成 **(JD 指纹 × `resume_id`)** 才修掉。
2. **「下拉把每一版都做成同名选项」会写出"这次用了哪一版"的假话** —— 一个族谱里有 v1/v2/v3，
   下拉里出现三个一模一样的名字，用户根本分不清选的是哪一版，而记录里却写着"钉住了版本"。
   改成**一份简历一个下拉项**、分析**钉在当前版**（`resumelib.current_of`）。
3. **写侧净化 / 字面量撞车（实现者自己抓到并收紧）**：断言"下拉真的给了版本 id"用
   `'<option value="'` 会**在占位选项**（`'<option value="">（无简历，请先新建）'`）里也匹配 →
   把真选项的 `value` 删掉，用例**照样绿**。改成从**渲染出来的** `innerHTML` 里解析 option 逐条断言。
4. **`overwrite=<job_id>` 会覆盖错记录** —— 一个 JD 下可以挂好几份分析（用户就是一个岗位对三份简历），
   而 `_job_in_ledger(<JD id>)` 只能取该 JD 下**最新**那条 → 「覆盖」写到了**另一份简历**的记录上
   （实测：B 那份的版本号与报告被改写成 A 的，弹窗上写的却是 A 的报告名）。**E2E 抓到**，
   改成 `overwrite` 必须用 `duplicate.analysis_id`（命中那条**分析**的 id）。**这是父 agent 的原话写错了**
   （计划里写的是 `overwrite=<job_id>`）。
5. **两道闸只测一道** —— `app.py` 的「只在延续时调模型」那道 `continue` 闸拿掉后用例**仍然绿**
   （库里 `ai_diff_of` 自己还有第二道"没有母版就不调"的闸）→ 补了 **spy 断言**（调用计数）。
6. **`Read` 顺序盲区**（**测试证明不了的**）：没有测试能证明"快照是在**覆盖之前**写的" ——
   覆盖之后再用内存里的旧内容补写快照，也能过所有用例。**只能靠读代码**。
   （这是本轮的诚实缺口之一，见下。）

### 两处真回归 / 真 bug（都修了，并留了承重证据）

1. **隔离漏洞：测试线程活过还原点 → 真实 `events.jsonl` 被污染（真发生过）**。
   根因不是"某个用例写错了"，而是 `IsolatedCase` 的清理顺序：**先还原路径、后杀线程**，
   于是还在跑的后台线程拿着**真实** `DATA_ROOT` / `LOG_FILE` 又写了一行。
   结构性修法：把「**有界等待后台线程排空 → 还原路径 → 删临时目录**」变成**一个** cleanup，
   等不到就**响亮失败**并且**不还原路径、不删临时目录**（宁可留一条"隔离没拆干净"的红）。
   证明守卫在承重：**把守卫拆掉 → 逐字节复现出那行污染**（`tests/base.py`）。
2. **`overwrite` 覆盖错记录**（上面假绿第 4 条）：E2E 实测到"覆盖的是 A、写坏的是 B"。
   改成 `analysis_id` 之后，弹窗说的那条与真正被改写的那条**必须是同一条**（测试直接断言）。

### 纪律升级：还原"改坏"时要备份【改后】那一份 + 核对 sha

本轮**真发生过一次**：为了做变异取证，把实现文件备份错了（拿的是**改前**的副本），
一还原就把**还没提交的修复退回去了**。修订后的纪律（与"绝不用 `git checkout` 还原"同一条线）：

1. 动手之前先 `Copy-Item` 一份**当前（改后）**状态到 `%TEMP%`，**记下 sha256**；
2. 变异 / 复原一律用 `Copy-Item` 覆盖回来，**再用 sha256 核对**（相等才算还原成功）；
3. **绝不用 `git checkout` / `git restore`** —— 它会把未提交的实现一起退掉（前几轮已有两位实现者踩过）。

## 2026-10-14 · 阶段 D：真删除一个 JD —— 以及**独立审查抓到的两条数据丢失路径**

**【大白话】** 这一条是"**删除岗位**功能做完之后，被两个独立检查者挑毛病"的记录。
**最值得看的是"两条数据丢失路径"那一节** —— 它讲的是"程序在什么情况下会把你的数据弄丢，
以及现在为什么不会了"。两条的根子是同一个坏习惯：**把"读不出来"当成了"没有"**。

- 类型：`功能` + `修复`
- 提交：`a2c9f3a`（功能）→ `5d6b4d4`（复核修复）
- 测试：**862 / OK**（本轮 +25）

### 用户选的语义（本阶段的全部设计依据）

**【大白话】** 你选的删除语义是"**连报告和 JD 原文一起真删**"。
所以这个功能天生危险，工具必须做三件事：**删之前先把要删的东西逐条列出来给你看**
→ **动手前先备份一份** → **任何一步失败就完整还原回去（绝不删一半）**。

删一个岗位 = **连它的分析记录、那些分析的报告文件、这个 JD 的原文一起真删**，不可恢复。
用户原话选的就是"连报告与 JD 原文一起真删"。工具能做、也必须做三件事：
① **先列清单**（只读预演，逐条）；② **先备份再删**；③ **失败逐字节回滚，绝不半删**。

### 为什么"少列"是本模块最贵的错

**【大白话】** 那份清单是你**唯一**一次看清"我到底在删什么"的机会。
**少列一个文件 = 你在不知情的情况下把它删了**（或者以为删干净了、其实还留在盘上）。
所以这里的规矩是：**算不出来就说"算不出来"，绝不猜、绝不漏**。

预演是用户**唯一**一次看清"我到底在删什么"的机会。少列 = 用户在不知情的情况下删掉东西，
或者以为自己删干净了、而 `jd/` 下的原文还躺在盘上。所以本模块的每条注释都在重复一句话：
**算不出来就说算不出来，绝不猜、绝不少列**。

实跑时抓到过这个形态的真 bug：迁移前的记录把 `jd_text_file` / `jd_image` 挂在**分析记录**上，
只读 JD 记录会**少列**原文与截图 —— 用户以为删干净了，`jd/` 下的文件还在。

### 🔴 独立审查抓到的两条**数据丢失**路径（都已修）

**【大白话】** 这两条是**这次最重要的发现**。它们解释了"为什么一个功能测试全过、却仍然危险"：
测试全过只说明"我想到的情况都对"，不说明"我没想到的情况安全"。

- **第一条**：你的岗位记录文件如果**坏了**（手改错 / 存成了别的编码 / 被杀毒软件临时锁住），
  程序读它得到的是"空的"；而删除操作会把这个"空的"**写回去** ——
  结果**所有岗位的所有分析记录，一次性全没了**，而且它当时不在备份里，**救不回来**。
  → 现在改成：**读不出来就拒绝删除**，让你先去修文件。
- **第二条**：删除失败要"还原"（从备份把文件放回去）时，程序把"**读不出来**"和"**本来就没有**"
  当成同一件事 —— 而对"本来就没有"它的动作是**删掉它**。于是**一次读取失败，
  "还原"反而把你的岗位记录删了**。→ 现在改成：读不出来就**碰都不碰**，并如实告诉你"这条我没把握还原"。

这是本阶段最重要的事：**功能上线的那一刻它是绿的（838 测试全过），但它有两条能把用户
数据抹掉的路**。两条都不是"边界情况"，两条都源自同一个思维习惯 —— **把"读不出来"当成"没有"**。

**F1：`jobs.json` 读不出来 → 整份台账被覆盖成 `[]`（不可恢复）**
`store.load_jobs()` 在**任何**读/解析失败时都返回 `[]`（`store.read_json` 吞掉所有异常）。
删除的第 2c 步是 `store.save_jobs(kept_jobs)` —— 它把整个文件**重写**成"读到的那个列表"。
于是：用户手改坏了 JSON / 用 GBK 存了一次（本项目已经在别的脚本上栽过 GBK）/ 杀毒软件
短暂锁文件 → `jobs_before = []` → 落盘 `[]` → **所有岗位的所有分析记录一次没了**。
而 `jobs.json` **原先不在备份里**，所以回滚也救不回来。
修法：`_jobs_or_error()` 明确区分"文件不存在"（空台账是对的）与"读不出来"（必须停下来），
后者让预演给出 `can_purge=false`、执行抛 `code=unreadable`。**宁可拒绝删，也绝不覆盖成空。**

**F4：回滚会**删掉**它只是读不出来的文件**
留底用的是 `read_text(p, None)`：读失败与"文件不存在"都得到 `None`，而回滚对 `None` 的动作是
`os.remove(path)` —— 于是一次读失败就会让"回滚"把用户的 `jobs.json` 删掉。
修法：`_snapshot()` 返回 `(留底前存在吗, 字节 | None)`；"读不出来"记 `ok=False` 并**碰都不碰**，
让它走 `rollback_failed` 由人处理 —— 既不删，也不假装还原成功。

**同一族的另外三处（也都修了）**
- **F2 少列**：原文按约定叫 `jd/<JD id>.txt`、但**没有任何字段点名它**时，预演原先不列它，
  删除还会**报成功**而原文留在盘上。`app._jd_text_path` 一直有这条兜底，本模块没有 ——
  两边对"这个 JD 的原文叫什么"有两种答案。补上兜底（`fallback=`）。
- **F7 越界**：报告有"别的 JD 还在用就不删"的闸门，`jd/` 原文与截图**没有** ——
  两个 JD 点名同一份原文时，删 A 会把 B 的原文删掉（违反文件头铁律 3"不删别人的东西"）。
- **F9 判据错位**：删记录用的是"`id` 落在一个集合里"，而**身份**是"这是谁的记录"
  （`_jd_id_of_record`）。本 JD 只要有一条没有 `id` 的记录，集合里就混进一个空串，
  于是判据会把**所有**没有 id 的记录一起删掉（别的 JD 的、根本不属于任何 JD 的）。
  改用与 `_analyses_of` **同一口径**的身份判断。

**F5：备份原先**不够用**
事务会整份重写三份 JSON 与面试记录，而备份里只有报告与 JD 原文。进程被 kill 时
（`except` 根本没机会跑）用户手里没有**任何**原样副本；`rollback_failed` 的文案还让用户
"手工从备份恢复"——那句话当时是**做不到的**。现在 `_state/` 下按原目录结构存一份，
外加 `manifest.json`（相对路径 + sha256 + 删的是哪个 JD）。

### 界面必须分开说话（F6/F8）

原来只有一句失败提示，而且**无条件**写"删除失败（已回滚）"。后端其实有 4 个 `code`，

### 一条基线口径的修正：追加型文件的"不变"不是"大小不变"

**【大白话】** 你那些数据文件里，**日志这个文件只会往后加行、不会改前面的**。
所以检查它"有没有被不该动的人动过"，正确的办法是看**前面那一截的防伪码变没变**，
而不是"整个文件大小没变"。这一节记的就是当初把口径写错、导致虚惊一场的经过
（那次"变化"其实是**你自己启动了程序**留下的日志）。

上一轮交接把 `logs/events.jsonl` 的基线写成"大小 30510 / 149 行不变"。本轮核对发现它变成了
32438 / 159 行 —— 一开始像是测试泄漏（本项目真出过线程活过拆解、把日志写进真实
`events.jsonl` 的事）。核对后是**良性的**：前 30510 字节的 sha256 **逐字节一致**
（`B929D8009092`），新增的 10 行是 `server.start` + 9 条 `http`，
时间戳落在交接提交之后 16 分钟 —— 是**用户自己启动了程序**。
所以正确的不变式是 **"前缀逐字节不变、只允许追加"**，不是"大小不变"。
（顺带确认：本轮全量测试跑完后该文件**一字节未变** → 隔离守卫有效。）

### 阶段 2（代码质量）审查：又抓到 **2 个我自己引入的真 bug**

规格审查跑完之后补跑代码质量审查，又出 14 条 —— 其中两条是**这一轮修复自己引入**的，
都属于"**默认 profile 下看不出来**"这一类：

- **备份基准混用**（最隐蔽的一条）：`base = store.profile_dir()`（无参 = `profiles/default`，
  `store.py:38-41`）而快照路径来自 `store.p_path()`（无参 = `profiles/<当前 profile>`，
  `store.py:69-71`）。默认 profile 下两者**碰巧是同一个目录**，所以 862 个测试全绿；
  非默认 profile 下每个相对路径都算成 `..\..\...`、全部退回 basename →
  **所有面试记录的 `status.json` 撞成备份里的同一个文件** —— 有记录的字节从备份里丢了，
  manifest 里还出现两条**同路径、不同 sha** 的条目（自相矛盾），
  而成功弹窗正跟用户说"里面连这次改过的 JSON 与面试记录都有**原样**副本"。
  审查者那句话很准：这个变异（`profile_dir()` → 硬编码 `profiles/default`）**语义等价、
  测试零影响** —— 只有"**真的换一个 profile 跑一遍**"才发现得了。
- **备份阶段的错误码**：`_copy_into_backup` 抛的是默认 `code="failed"`，于是"备份 sha 不符"
  会被前端说成"删除失败（**已回滚**）"—— 而那时**什么都没删、也没回滚**。

**【大白话】上面第一条为什么"最隐蔽"**：程序里有两个几乎同名的函数，一个默认返回"默认用户目录"，
另一个默认返回"当前用户目录"。**你的电脑上只有一个用户目录，所以这两个碰巧是同一个地方** ——
于是所有测试都通过。但只要哪天有第二个用户目录，备份就会把多条面试记录**压成同一个文件**、
把内容丢掉，而且备份清单自己都会前后矛盾。
审查者有句话很准：**这种错误"改坏了等于没改"，只有真的换个用户目录跑一次才发现得了。**
所以现在有了一条**非默认 profile** 的测试专门盯它。

同一族还补了两个"和 F1 一步之遥"的洞：
- **`jds.json` 读不出来**时，第 2b 步会把整个 JD 库覆盖成空、**还回 `ok:true`**
  （与 F1 完全同构，只是晚一个文件）。今天够不到（`jds.json` 不存在），
  `身份迁移.py` 一跑它就会存在 —— 现在就堵上。
- **`knowledge.json` 读不出来**时预演报"**0 命中**"（看着完全正常），引用却悄悄没清。
  它**不阻止**删除（不会被覆盖、坏着也不丢数据），但必须如实说 —— 这条划出了原则的边界：
  **会被覆盖的必须拦住，不会被覆盖的只需说清楚。**

还有两处更细的：
- **事务中途新出现的面试记录**会被第 2d 步改写，而它**既不在快照也不在备份里** ——
  等于改一份没有留底的用户文件。现在只动**留过底的那些路径**（不再重新 glob），
  并在动手前先比对一次，不一致 → 拒绝（半截备份也清掉）。
- **`jds.json` 本来不存在**时，删除会顺手**造一个空库**出来 ——
  删除的副作用只该是"东西变少"，不该"平白多一个文件"。

### 这一轮真正学到的一条：**断言的作用域**

**【大白话】** "断言"就是测试里那句"我要求它必须是 X"。
这一轮我犯了三次**同一个错**：**"我要求的那个 X，范围写大了"** ——
比如我本意是"确认清单里每个文件**各自一行**"，却写成了"整段文字里出现过这些文件名"，
而另一处本来就逐条列了文件名，于是我的检查**被别的地方满足了**，等于没查。
**教训：每条检查都要问一句"我这句话到底约束了哪一块文本／哪一个对象？"**

本轮出现的三个假绿**全是"断言写在了错的范围上"**：
① F9 那条插错了记录形状（真正会触发的那条路径根本没走到）；
② 二次确认"逐条"那条扫了**整段文案**（被 ① 区满足）；
③ ④ 区那条扫"从 ④ 往后"（把名字印到 ⑤ 里也能过）。
修法都是同一句话：**把断言限定在它真正声称的那一小块** —— 那一区、那一行、那条记录。
"变异能过"说明测试没测到；但**"变异不红"也不等于测对了**，
所以每条新断言都要问一句"我这句话到底约束了哪一块文本 / 哪一个对象"。

### 未做的（诚实缺口）

1. **硬 kill（进程被杀）会留下半删状态**：文件先删、JSON 后写，而恢复只存在于进程内的
   `except` 里。现在备份**够用**了（含三份 JSON 与面试记录 + manifest），但**恢复仍需人工**。
   要做成真崩溃安全得改成"先写意图日志、启动时重放"，本轮**没做**。
2. **F1 的取舍**：台账读不出来时，**整个删除功能都不可用**（不只是那个岗位）。
   这是刻意的（宁可拒绝也不覆盖成空），界面也如实说了"请先把台账修好"，
   但没有做"只读地尽力修/隔离坏记录"的救援路径。
3. **非 UTF-8 / 坏 JSON 的其他入口没查**：本轮只把删除路径钉住了；`store.load_jobs()`
   在**别处**（台账渲染、查重、分析）依旧会把"读不出来"报成空 —— 那些路径不改文件，
   所以不会造成丢失，但会**显示成"台账是空的"**，属于误导性显示，**未处理**
   （要改得动 `store` 的公共契约，面比本轮大）。
4. **真实数据仍是"迁移前"形态**（`jds.json` 不存在）：F2 / F7 的两条路径在真实数据上
   **目前够不到**（已引用集合 == 盘上集合，8/8），
   它们在隔离夹具上验证；跑完 `身份迁移.py` 后应再走一遍。
5. **真实数据上从未执行过删除**（**故意**：这个功能只能由用户自己点）。
6. `app.py` / `resumelib.py` / `web/index.html` 注释里的 `⚠️` 仍是非 GBK 字符（不在输出路径上），
   本轮仍未动。
7. **`merged_into` 死记录**仍带 JD 级字段且无 `jd_id`（简历迁移给它补了 `resume_id`）——
   建议后续清理，本轮不动。
