# 批 2（并发 / 原子性）实施计划

> 来源：`docs/全项目体检报告-2026-10-15.md` §5（P3-1…P3-7）+ 独立复查补的一条（复合读-改-写仍无锁）。
> **这一批的风险与其他批不同**：失败模式是**死锁**与**锁序反转**（不是丢数据就是卡死），
> 而本项目的锁序断言是 **AST 级**的（`tests/test_jdid.py::LockingTest`、`tests/test_jdfacts.py::ModuleHygieneTest`），
> 它们只保护**已知的**调用链 ⇒ 新加的锁必须自己证明**可重入**与**无环**。

## 一、锁序总表（动手前先背下来）

| 锁 | 归属 | 保护什么 |
|---|---|---|
| `store._JOBS_LOCK` / `store._CONFIG_LOCK` | store.py | **每一次** `load_jobs`/`save_jobs`/`load_config`/`save_config`（`upsert_job` 的 RMW 在同一临界区） |
| `jdid._JD_LOCK` | jdid.py | `jds.json` 的整份读-改-写（含 `rename_jd` 的跨文件联动） |
| `jobdup._MERGE_LOCK` | jobdup.py | 合并（jobs + knowledge + interviews 的快照/回滚） |
| `kb._KB_LOCK` | kb.py | knowledge.json 的整份读-改-写（`_with_kb_write` 已收口五个入口） |
| `resumelib._LOCK` / `log._LOG_LOCK` | 各自 | 版本库 / 日志 |

**获取顺序（一律从外到内）**：`_JOBS/_CONFIG` → `_JD`/`_MERGE` → `_KB` → （文件写）/`resumelib`/`log`。
**铁律**：
1. **不许在持锁时去获取"外层"锁**（那是死锁的经典形状）；
2. 跨模块调用（A 持锁 → 调 B）必须证明 B 只取**更内层**的锁，或把 RMW **收进内层模块**（推荐）；
3. 每个新锁都写成 `RLock`（重入）并在 docstring 写明"谁调我、我在谁里面"。

## 二、逐项

### 2.1 `_KB_LOCK` 跨模块缺口（P3-3）—— **先做这一项**
- **现状**：`jddelete.py:859-865`、`jdid.py:694-731`、`jobdup.py:318-354` 各自 `load_knowledge → 改 → save_knowledge`，
  **完全不取 `_KB_LOCK`**（那把锁只在 `kb.py` 内生效）⇒ 与分析（20–60s）并发时**后写的整份盖掉先写的**。
- **做法（推荐：把 RMW 收进 kb.py）**：在 `kb.py` 加三个窄接口——
  `kb.purge_jd_refs(jd_id, …)` / `kb.repoint_jd_refs(old_id, new_id)` / `kb.merge_jd_refs(drop_id, keep_id)`，
  内部用既有的 `_with_kb_write`（它已经持 `_KB_LOCK` + 哨兵 + 归一化）⇒ 三个模块改成**调接口**，不再自己读改写。
  ⚠️ 这同时消灭"三份 `_repoint_kb` 实现"（§7.2 的重复项）—— **一箭双雕**。
- **必须复跑的既有断言**：`tests/test_jdid.py::LockingTest`、`tests/test_jdfacts.py::ModuleHygieneTest`（锁序 AST）、
  `tests/test_kb.py`（五入口哨兵）、`tests/test_jddelete.py`、`tests/test_jobdup.py`、`tests/test_jdid.py` **全绿**。
- **新测试**：三个接口各自"坏库时拒绝/留档"（复用 `_with_kb_write` 的既有口径）+ **并发用例**：
  一个线程反复 `absorb`、另一个反复 `purge`/`repoint`，跑 N 轮，断言**一条更新都不丢**（当前必红）。
- **变异**：① 接口里去掉 `_KB_LOCK`（退回各自读改写）→ 并发用例必须红；② 把顺序改成"持 `_KB_LOCK` 时去取 `_JD_LOCK`"→
  必须有一条**死锁探测**用例红（用 `threading` 超时 + `assertFalse(t.is_alive())`）。

### 2.2 报告文件名 TOCTOU + 非原子写（P3-1）
- **现状**：`app.py` 用 `os.path.exists` 找空位 ⇒ 并发两次分析**拿到同一个 `(3).html`**（后写的覆盖先写的，丢一份花过钱的分析）；写盘还非原子。
- **做法**：`open(path, "x")`（独占创建）循环 + `O_EXCL` 语义；写盘走 `store.write_text` 的**原子**版本（或 `write_bytes` + `os.replace`）。
- **依赖**：`app.py` 现在被批4b 占用 ⇒ **等它收工**。
- **新测试**：两个线程同时渲染同名报告 → 断言**两个文件都存在且内容各自完整**；变异：退回 `exists` 检查 → 必须红。

### 2.3 `kbreuse.build_index` 无锁读取（P3-2）
- **现状**：它是**新增的无锁读者**（每次真算都读 knowledge.json），与"用户点掌握度/别的 JD 的 absorb"并发时
  Windows 上 `os.replace` 抛 `WinError 5`，而 `kb.absorb` 只在边界记一条日志 ⇒ **用户的沉淀静默丢失**。
- **做法**：`build_index` 读取时持 `_KB_LOCK`（短、只读）；或改用 `store.read_knowledge_strict` 的重试语义（判断后选一种并写清理由）。
- **依赖**：`kbreuse.py` 正被批5b 占用 ⇒ **等它收工**。
- **新测试**：一个线程反复 `absorb`、另一个反复 `build_index`，跑 N 轮断言**零丢失 + 零异常**。

### 2.4 复合读-改-写仍无锁（独立复查补的）
- **现状**：`app.py:2642 load_jobs()` → `:2665 save_jobs(rest)`（`DELETE /api/jobs`）、
  `jdid.rename_jd`、`jobdup._merge_jobs_locked`、`jddelete._purge_locked` 都是"load → 改 → save"跨了多次 store 调用。
- **做法**：给 store 加"事务"式的窄接口（`store.update_jobs(fn)`：在 `_JOBS_LOCK` 内 `load → fn → save`），
  让上述四处改用它 ⇒ 每一次复合改动都是原子的。**这也是 §7.2"读不出来先留档"两份实现统一的机会**。
- **新测试**：`update_jobs` 的并发用例（两个线程各改一条记录，断言都保留）+ `fn` 抛异常时**不写盘**（原子性）。

### 2.5 `jdfacts._join_inflight` 无超时（P3-4）
- **现状**：`Event.wait()` 无超时 ⇒ `builder` 卡死则所有等待者**无限挂起并占住线程**。
- **做法**：给 `wait` 加上限（读代码定一个与"一次分析最坏耗时"匹配的值）+ 超时后**如实降级**（自己算或报错，别静默返回 None）。
- **新测试**：mock 一个永不返回的 builder → 断言等待者在 T 秒内**返回/抛错**，而不是挂住（用线程 + `join(timeout)`）。
- **可并行**：`jdfacts.py` 现在空闲 ⇒ 这一项**可以最先派**。

### 2.6 非原子写盘（P3-5/P3-6/P3-7）
- `store.write_text`/`write_bytes` 是**截断后写** ⇒ 改成"同目录 mkstemp + `os.replace`"（照 `write_json` / `resumelib._atomic_write_bytes` 的现成实现，
  **别写第二套**）；`write_json` 加 `fsync`；`save_stream` 失败时**不许删旧文件**。
- **新测试**：写失败（mock `os.replace`）时**旧文件逐字节不变**；`save_stream` 失败后旧文件仍在。

**运维约定（本批已立为纪律）**：
- ⚠️ **别让多个实现者同时跑全量**（实测三方同时 `discover tests` 会**死锁**，卡 5 分钟）⇒
  **主控串行跑全量**，实现者只跑自己那个模块 + 需要时**申请一个时段**跑一次全量。
- ⚠️ 每个实现者报 DONE 后，主控**先确认 mtime 静下来 + 状态 inactive** 再去验（并发变异会让证据失真）。
- ⚠️ **锁序改动必须成对复跑**（`test_jdid.LockingTest` + `test_jdfacts.ModuleHygieneTest`）——它们是 AST 断言，
  改了一处锁而不跑这两条，等于没有证据。
